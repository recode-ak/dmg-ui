# Решения (ADR-список)

**Назначение:** реестр архитектурных решений пакета `dmg-ui`. Новое решение — строка `D-UI-N`, номер следующий после максимального в этом файле. Решение не правится задним числом: заменяется новой записью, а старая получает пометку «заменено D-UI-N». Серия `D-UI-N` принадлежит только пакету; решения платформы — `D-NN` в `node_modules/dmg-core/docs/decisions.md`. Формат записи: `**D-UI-N. Название.** Текст: что решено, почему, что отвергнуто.`

Правила графа — в [каталоге правил](./reference/rules.md), открытое — в [реестре долга](../debt.md). Как писать экраны и каналы — [гайд по сторис, экрану и уведомлению](./guides/story-screen-notification.md) и [гайд по пакету канала](./guides/channel-package.md).

## Поставка и состав

**D-UI-1. Монорепо с одним устанавливаемым пакетом.** Репо содержит каталог `packages/`, но наружу выходит один пакет `dmg-ui` с одной версией; его входы — подпути в `exports` корневого `package.json`. Пакет-каталог видит соседа только по имени входа, а не по пути (`PackageDirections`): так каталоги можно резать и склеивать, не ломая потребителей. *Почему:* каналы (`web-ui`, `tg-bot`) придут отдельными пакетами, и их удобно вести рядом.

**D-UI-2. Поставка — git по тегу, `dmg-core` ставится той же командой.** `dmg-ui` и `dmg-core` в npm не лежат; `dmg-core` у `dmg-ui` — peer, а Bun ищет peer в npm и получает 404. Поэтому потребитель ставит оба пакета, `valibot` и `@valibot/to-json-schema` одной командой `bun add`, указывая git-адреса с тегами. Версия — тег; обновление — правка тега. Репо ставится целиком, потому что поле `files` при установке из git не действует.

**D-UI-3. Peer-зависимости — `dmg-core` и `valibot`; опора примера — именованный вход `dmg-core/testing/example`.** В `peerDependencies` стоят `dmg-core ^0.6.1` и `valibot ^1.5.0`. Учебный пример `dmg-ui/testing` строится на учебном приложении платформы, а оно доступно потребителю через именованный вход `dmg-core/testing/example` (D-101 пакета `dmg-core`), а не через путь в её файлы. Других зависимостей у пакета нет.

**D-UI-4. Четыре входа; корень не тянет `dmg-core/app` и `dmg-core/graph`.** `dmg-ui` — манифесты, адрес, исполнитель, код экрана, порты. `dmg-ui/graph` — поставщик графа и виды. `dmg-ui/server` — сессия, уведомитель, привязки к `ApiApp` и `ModuleApi`. `dmg-ui/testing` — пример, два канала, помощник примеров. *Почему:* код экрана и исполнитель работают в браузере, а `dmg-core/app` и `/graph` — серверный код. Граница держится не соглашением, а проверкой импортов (`CoreImportScanner`, см. [проверки репо](./reference/rules.md)). *Отвергнуто:* всё в корне — корень потянул бы серверный код в браузер. *Заменено D-UI-34 в части состава входов: входов восемь, диалоговый канал вышел из `dmg-ui/testing`.*

**D-UI-5. Версия `0.1.0` — не заморозка контракта канала.** Контракт между ядром и каналами (порты, исходы, вид экземпляра) пока определён одним учебным диалоговым и одним учебным страничным каналом. Он правится релизом с записью в этом файле; открытое ведётся в [реестре долга](../debt.md).

## Манифесты и адрес

**D-UI-6. Шесть видов Def.** `UiSetDef` (набор UI одного доменного приложения), `UiAppDef` (набор в одном канале: сторис, уведомления, входы), `UiModuleDef` (экраны, сторис и уведомления области), `StoryDef`, `ScreenDef`, `NotificationDef`. Значения `dmg` — `uiSet`, `uiApp`, `uiModule`, `story`, `screen`, `notification`. Действие экрана — не Def, а `ScreenAction` под экраном. *Отвергнуто:* имя `UiDef` для набора: неоднозначно с приложением UI.

**D-UI-7. Манифест статичен, код экрана отдельно.** Манифест (`ScreenDef`) описывает параметры, данные, действия, выходы и примеры, но не знает, как экран работает. Работу описывает `ScreenCode`: загрузка, шаги действий, начальное состояние, доступность, варианты и начальные значения полей, локальные действия. Связь манифеста с кодом — реестр `CodeLoaders` в корне сборки: каждому экрану и уведомлению набора ровно один `CodeLoader`, иначе бросок со списком имён. *Почему:* у браузера и сервера могут быть разные реестры, а манифест остаётся читаемым без кода. *Отвергнуто:* поле `code: () => import()` в манифесте — манифест ссылался бы на путь кода; декларативные пути выбора полей — не выражают логику анкеты.

**D-UI-8. Ссылки между экранами — thunk с аннотацией возврата.** `to` действия и `links` уведомления — функции `(): readonly AnyScreenDef[] => […]`. Без отложенного вызова взаимные ссылки экранов (список и карточка) падают при импорте, а без аннотации возврата TypeScript выдаёт TS7022. Переход на свой экран в `to` не пишется: он разрешён неявно (листание, перечитывание). *Отвергнуто:* ссылки строкой по имени — теряется проверка типом и принцип «адрес — ссылка на Def».

**D-UI-9. Адрес — экран и параметры по схеме.** `Address` — ссылка на `ScreenDef` и выход его схемы `params`. `id` экрана, сторис и уведомления — `<набор>/<модуль>/<имя>`, действия — `<экран>/<действие>`, приложения UI — его имя; их считает один класс `UiIds`, им же пользуется граф. Повтор `id` — ошибка программиста, бросок. `AddressCodec` переносит адрес через JSON кругом: `encode` для своего адреса, `decode` для внешних данных. Отказ декодирования — значение `Result` с `AddressRejection` (`malformed`, `unknownScreen`, `invalidParams`), не бросок. Страница списка — параметр адреса, а не отдельный экран.

**D-UI-10. Действие вправе не вызывать UC; не более одного command UC.** У действия одно необязательное поле `uc`. Без него действие — переход (меню, листание, первый шаг мастера), UC оно не вызывает. Что `uc` — command, проверяет UI-09. *Почему:* один UC на действие делает шаги кода (`command`, `done`, `caught`) типизируемыми.

**D-UI-11. «Только чтение» применяет исполнитель.** Код экрана вызывающего не видит, поэтому признак не может быть «функцией данных и состояния». При `RenderContext.readOnly` исполнитель делает недоступными все действия с `uc` (исход `unavailable`, причина `readOnly`); действия-переходы остаются. Платформа независимо отказывает заместителю `readOnly` в command UC, поэтому устаревший признак влияет только на вид. *Отвергнуто:* признак в данных query UC и третий аргумент `available` — оба втягивают вызывающего в код экрана.

## Граф

**D-UI-12. Виды узлов и рёбер ядра; три корня.** Узлы: `uiSet`, `uiModule`, `story`, `screen`, `action`, `notification`, `uiApp` (имя вида — это `dmg` Def; у действия Def нет). Рёбра: `includes`, `entry`, `reads`, `recipients`, `invokes`, `leadsTo`, `refreshedBy`, `notifiedBy`, `links`, `catches`, `presents`. Действие — узел под экраном, локальное действие — свойство узла экрана. В графе три независимых корня: доменное приложение, набор UI и приложение UI; совпадение имён корней — `duplicate-node` и ARC-13 «граф не собран». Ссылки на домен строятся только через `DomainIds`. *Отвергнуто:* префикс в имени вида (`uiScreen`) — хуже читается и расходится с `dmg`.

**D-UI-13. Префикс `UI`, 23 правила.** Правила ядра — `UI-01…UI-23`, у каждого пакета канала свой префикс (ARC-13). UI-14 (описание полей схем UI) и UI-23 (форма сторис) проверяют форму манифеста. UI-06 покрывает и уведомления. UI-10 дублирует UI-08 для узлов ядра и нужен узлам каналов. Переход проверяет UI-03 (нет общей сторис с целью), выход — UI-04 (выход без исхода). Каталог — [rules.md](./reference/rules.md). *Отвергнуто:* набор без UI-14, UI-23 и UI-10 — форма манифеста осталась бы без проверки. Уточнено D-UI-57: префиксы пакетов каналов — `PG` (учебный страничный канал), `CH` (общая часть мессенджеров), `TG` (за `tg-bot`).

**D-UI-14. Представление пишет в граф канал ребром `presents`.** Ядро не знает, как экран показывается, поэтому ребро `presents` от приложения UI (или узла под ним) к экрану, уведомлению или набору UI целиком ставит пакет канала своим поставщиком графа. UI-06 проверяет, что у каждого экрана и уведомления приложения представление есть. *Отвергнуто:* поле `defaultPresentation` в `UiAppDef` — тогда представление объявлял бы проект, а не канал; узел представления в ядре — не нужен: пакет канала вправе добавить его сам.

**D-UI-15. UI-03 исключает экран-вход; семена UI-07 — входы и `links` уведомлений.** Меню — обычный экран, ведущий на экраны разных сторис, общей сторис с ними у него нет, поэтому экран, на который ведёт `entry`, из UI-03 исключён. Достижимость (UI-07) считается от целей `entry` и от ссылок `links` уведомлений приложения: уведомление со ссылкой — тоже вход для человека. *Отвергнуто:* сторис «Навигация», включающая все экраны; правило-предупреждение вместо нарушения.

## Исполнитель и контракт канала

**D-UI-16. Две части: исполнитель и серверная часть.** Исполнитель (`dmg-ui`: `ScreenRuntime`, `ScreenInstance`, `CodeLoaders`) работает на стороне клиента, серверная часть (`dmg-ui/server`: `UiServer`, `UiSession`, `UiNotifier`) лежит рядом с приложением. Между ними проходит только JSON: порты `UcPort` и `RefreshPort`. Исполнитель не знает вызывающего, шину и приложение. *Почему:* то же ядро должно работать и в браузере за проводом, и в процессе бота.

**D-UI-17. Контракт канала — порты и объекты ядра, без `interface Channel`.** Канал получает от ядра порты и объекты (`CallerSource`, `RecipientCallers`, `NotificationDelivery`, `UiObserver`; `ScreenRuntime`, `ScreenInstance`, `InstanceView`, исходы действий) и сам решает остальное: представления, хранение, показ. Что канал обязан дать, описывает [гайд по пакету канала](./guides/channel-package.md). *Отвергнуто:* единый интерфейс со всеми методами — он навязал бы каналам структуру, которой у страницы и мессенджера разная форма.

**D-UI-18. Код действия — шаги `command` / `done` / `caught`.** `command` строит вход UC (по умолчанию вход действия идёт как есть), `done` получает результат и возвращает переход, `caught` — то же при отказе UC с объявленным кодом. Порта вызова у шагов нет: UC вызывает исполнитель, поэтому «один UC на действие» следует из структуры. У каждого действия обязателен `done`; это проверяет `ScreenUnit` при первом открытии экрана. *Отвергнуто:* обработчик `run(ctx)` с `ctx.call(input)` — один UC проверялся бы только в рантайме, а неперехваченный отказ приходилось бы прерывать броском.

**D-UI-19. Ревизия, очередь, порядок проверок `act`, исходы.** У экземпляра есть ревизия: она растёт при каждой загрузке (открытие, перечитывание, перечитывание после действия), локальное действие её не меняет. Действие адресовано ревизии: несовпадение — исход `stale`. `act`, локальные действия и перечитывание идут по одному через очередь экземпляра; пока перечитывание ждёт очереди, новые сигналы лишь заменяют его след. Порядок проверок `act`: закрыт, ревизия, имя, «только чтение», доступность, подтверждение, вход, `command`, UC, `done` или `caught`, проверка перехода. Исходы: `moved`, `stayed`, `exited`, `rejected`, `refused`, `stale`, `unavailable`, `confirm`. Бросок кода экрана — дефект: исход `refused` с `SERVER_INTERNAL`.

**D-UI-20. Отказ UC — исход с `ErrorText`; перехват только объявленных кодов.** Отказ UC превращается в исход `refused` с `Refusal`: код, главная строка `ErrorText` и признак `caught`. Экран перехватывает только коды из `catches`, объявленных на экране, а не на действии; для них вызывается шаг `caught`. Строки полей валидации человеку не показываются: сообщения valibot повторяют введённое значение (DEBT-3 пакета `dmg-core`; запись пакета — [DEBT-UI-2](../debt.md)). Дефект кода экрана выходит отказом `SERVER_INTERNAL` без текста броска.

**D-UI-21. Состояние не по схеме — начальное; адрес не восстановился — отказ каналу.** Канал хранит снимок экземпляра (`InstanceJson`: адрес, состояние, ревизия) и восстанавливает его через `ScreenRuntime.restore`. Состояние, не прошедшее схему, заменяется начальным: схема могла измениться между запусками. Адрес, который не декодируется, или ревизия не целая `≥ 0` — отказ `Result` каналу, а не молчаливое открытие другого экрана.

**D-UI-42. Предел ревизии снимка.** `ScreenRuntime.restore` отвергает ревизию больше `2³¹ − 1` отказом `malformed`, как ревизию не целую `≥ 0` (дополняет D-UI-21): ревизия + 1 остаётся безопасным целым, и проверка устаревшего действия (`stale`) не замерзает. Ревизия экземпляра в памяти не ограничивается: 2³¹ загрузок одного экземпляра недостижимы, а снимок с большей ревизией при следующем восстановлении будет отвергнут, и канал откроет вход.

**D-UI-22. Событие перечитывает экран по сопоставлению payload; по событию UI только читает.** Экран объявляет `refresh`: событие, соответствие параметров экрана полям payload, `subject` или `any`. Сессия сверяет payload с параметрами экземпляра и субъектом сессии и выдаёт сигнал без payload; не совпало — экземпляр не перечитывается. Перечитывание выполняет загрузка экрана, то есть только query UC. Вызов command UC с причиной-событием сервер отклоняет отказом `SERVER_INTERNAL` и записью `warn`: реакция на событие — дело домена, а не интерфейса.

**D-UI-49. Ожидание очереди экземпляра.** `ScreenInstance.settled()` исполняется, когда отработали задачи, поставленные в очередь экземпляра до вызова: действия, локальные действия и перечитывание по сигналу; отказ задачи ожидание не рвёт. Сигнал порта ставит перечитывание в очередь сразу, поэтому `settled()` после сигнала дожидается и его. *Почему:* каналу нужно дождаться перечитывания по событию без таймеров — при выгрузке беседы и в тестах, а промис перечитывания ядро наружу не отдаёт. *Отвергнуто:* «пустое» локальное действие ради ожидания очереди; счёт сигналов в канале — ломается на склеенных сигналах и на закрытом экземпляре.

## Уведомления

**D-UI-23. Уведомление читает от имени получателя.** `UiNotifier` по событию находит получателей и для каждого строит данные заново: `RecipientCallers` даёт вызывающего, `NotificationCode.load` читает query UC из `reads` от его имени. Данные уведомления читает query UC, а не берёт из payload. Получатели — из полей payload (`from: 'payload'`) или из query UC (`from: 'query'`): UC вызывается от `SystemCaller` `{ kind: 'app' }` с именем набора UI, значения его входа берутся из payload. Связь с UC — ребро `recipients`, а не `reads`: иначе UI-12 сработал бы на служебный UC. Согласованность проверяет UI-18. *Отвергнуто:* получатели только из payload — часть событий несёт одного участника, а получателей знает домен.

**D-UI-24. Ядро передаёт `cause.eventId`; отсев повтора и предел — политика канала.** Каждое `DeliveredNotification` несёт `cause: { event, eventId }`. Ядро не хранит, кому что доставлено, поэтому отсев повторной доставки по `eventId` и его предел (размер, срок жизни) определяет канал. Беседа держит отсев с пределом в снимке (D-UI-56); страничный канал — множество без предела, допущение учебного канала, оно вынесено в долг ([DEBT-UI-10](../debt.md)).

## Наблюдение, след, контекст

**D-UI-25. Наблюдатель — порт.** `UiObserver.record(entry)` синхронен и не бросает, как `logger`. Запись `UiRecord` несёт `id` узла графа, `TraceJson` и вид события: открыт, перечитан, действие, исход, отказ, уведомление, дефект. Входа, данных, payload и текстов замечаний в записи нет. Сырой бросок кода экрана уходит в необязательный приёмник `faults` (`UiFault`) — для разработчика, не для лога UI. Лог UI — дело потребителя; в ядре есть только точка записи. В тестах — `MemoryUiObserver` из `dmg-ui/testing`.

**D-UI-26. След — `TraceJson` корня; `correlationId` клиента — заявление.** Тип `TraceJson` лежит в корне `dmg-core` (D-102 пакета `dmg-core`), поэтому исполнитель переносит след через JSON, не входя в `dmg-core/app`. Клиент следа не шлёт: он называет причину вызова — `requestId` или `eventId`, а сервер строит след сам (`Trace.fromRequest` или выданный сигналу след; сессия помнит выданные следы в пределах 256 штук). `correlationId`, пришедший от клиента, — заявление, а не доказательство: по нему нельзя судить о личности и правах. *Отвергнуто:* принимать след целиком от клиента — подделка цепочки в логах операций.

**D-UI-27. `RenderContext` строит канал; `ViewChange`, `ScreenViewOf<D>`, `ScreenPreview` — в корне.** `RenderContext` — язык, часовой пояс, признаки заместителя и «только чтение». Канал собирает его из своих данных и `RenderFlags.of(caller)` (вход `dmg-ui/server`). Вид экземпляра `InstanceView` типизирован слабо (`data` и `state` — `unknown`); `ScreenViewOf<D>` даёт его в типах схем экрана — только тип, приведение канал делает один раз. `ViewChange` (`refreshed`, `acted`, `local` и ревизия) сообщает об изменении вида. `ScreenPreview` строит вид и данные уведомления по именованному примеру без портов — для каталогов, снимков и тестов представлений.

**D-UI-41. Место личности — порт и сборка контекста рендера.** `Place` — язык и часовой пояс (корень `dmg-ui`); `ActionContext` — его псевдоним. Порт `PersonPlaces.place(uuid, trace)` даёт место человека, источник места (профиль, язык транспорта) — дело проекта. `RenderContexts.of(uuid, trace)` (вход `dmg-ui/server`) собирает `RenderContext` из места и `RenderFlags` вызывающего; вызывающий не разрешился — признаков нет (`delegate` и `readOnly` — `false`), вызов UC сервер всё равно отклонит. Место — того, кто работает (личность транспорта), а не замещаемого. Дополняет D-UI-27: канал может собирать контекст сам, но общая сборка — здесь. *Почему:* место — свойство человека, а не канала; сборку контекста каналы повторяли. *Отвергнуто:* место в итоге `RecipientCallers.resolve` — `Caller` принадлежит платформе, контракт ломается; константа на канал.

## Граница с клиентом

**D-UI-28. Вызов UC — `{ module, uc, input, requestId | eventId }`.** `UcCall` — простая команда без узла графа, следа и вызывающего. Исполнитель строит её по `useCases` модулей приложения набора (`UcCalls`). Сервер сверяет пару `(module, uc)` по объединению объявленного узлами сессии: экранами (`reads`, `uc` действий) и узлами канала (`uses`) (`UcRoutes`); для уведомителя — `reads` уведомлений. Один UC из разных узлов — один маршрут; два UC с одним именем в модуле, UC вне приложения, повтор узла — ошибки сборки. Не объявлено — `OPERATION_NOT_FOUND` и запись `warn`. Платформенный `DeclaredSet` внутри `dmg-core/app` в контракт не входит. Исполнитель сверяет вызовы кода экрана с манифестом по идентичности Def.

**D-UI-29. Клиент за проводом недоверен.** `available`, `confirm` и `readOnly` — подсказки для показа, а не граница. Граница — Policy UC и `callers` в манифестах (UI-01), которые проверяет платформа при каждом вызове. Сервер проверяет форму и длину строк клиента, причину вызова (`ClaimedCause`, до 256 символов), объявленность пары `(module, uc)`; личность и вызывающего берёт из источника сессии, а не из сообщения. Отказ — значение `SerializedResult`, не бросок. Что ещё держать в голове автору канала — в разделе безопасности [гайда по пакету канала](./guides/channel-package.md).

**D-UI-30. Обходы дыр контракта.** Три места, где ядро не даёт нужного, канал обходит публичными средствами. Повтор загрузки экрана после отказа — открыть адрес заново. Адрес, куда перешёл экземпляр (`moved.address`), — разобрать `AddressCodec.decode`. Подписи действий и выходов по `id` экрана — `UiIds.findScreen`, а не `normalize()` (он стирает thunk и схемы). Сигналы канала не от экрана (вход в группу, команда) ядро не знает: `on` узла канала — вне ядра. Дополнено D-UI-59: у мессенджеров сигналы и реакции сообщества — манифесты `chat-ui` и `Communities`; узлы канала ядра (`ChannelNode`, `UiSession.on`) прочих каналов в граф не попадают — граница правила UI-12 ([Ограничения правил](./reference/rules.md)).

## Мессенджеры

**D-UI-35. Сообщение — данные для порта.** Сообщение `Message` (пока это только `TextMessage`) — неизменяемый простой объект, JSON по построению, а не класс; классы работают над ним. Вид задан в типе: `MessageKind` объявляет пять видов (`text`, `image`, `audio`, `video`, `document`), показывается только `text`. Остальные виды добавятся расширением объединения: тот, кто строит сообщения, ничего не правит, а разбор вида у мессенджера с веткой `never` перестанет компилироваться намеренно — вид добавляется вместе с его показом. `FormattedText` — плоские фрагменты `{ text, styles, link? }`: строка как есть, без разметки и экранирования; стили — пересечение мессенджеров (`bold`, `italic`, `strike`, `code`, `codeBlock`, `quote`) в порядке `TEXT_STYLES` без повторов; `link` — адрес, `text` — подпись; перевод строки — `\n` внутри `text`. Вариант `MessageOption` — подпись и короткая ссылка беседы. Форму держит построитель `TextBuilder`: пустое пропускается, соседи с теми же стилями и ссылкой склеиваются, вложенный построитель накладывает стиль на все свои фрагменты, строчный код берёт снаружи только цитату, блок кода — ничего, цитата и блок кода стоят на целых строках (перевод строки ставится только при нужде, отдельным фрагментом без стилей). `PlainText` даёт видимый текст: подпись ссылки остаётся, адреса нет. Своё у мессенджера (отключённый вариант, цвет, язык блока кода, дата и время) — только необязательные поля поверх общих типов, так общее `Message` остаётся допустимым сообщением мессенджера. *Почему:* порт, снимок беседы и свойства графа получают JSON; плоские фрагменты прямо переводятся в разметку сущностями со смещениями, а при разбиении обе половины фрагмента сохраняют стили сами. Экранирует мессенджер, когда переводит текст в свой формат: только он знает свою разметку. *Отвергнуто:* строка с разметкой — у каждого мессенджера своя разметка и экранирование, а длину нужно мерить по видимому тексту; блоки (абзац, цитата, блок кода) со строчными фрагментами — инвариант «целые строки» виден в типе, но типов и кода разреза больше, а сущности строятся расплющиванием.

**D-UI-36. Длина и помощники лимита.** Мера — видимый текст (`PlainText`) в единице лимита: подпись ссылки считается, адрес нет. Единица задана у каждого лимита (`TextLimit`: `max` и `unit` — графема, кодовая точка, UTF-16 или байт UTF-8), а не одна на мессенджер. `TextLength` меряет текст и строку; графемы считает `Intl.Segmenter` по всему тексту, а не по фрагменту, поэтому графема на стыке фрагментов одна; одиночный суррогат — своя графема, в UTF-8 — 3 байта, как U+FFFD. `TextTrimmer` и `TextSplitter` режут только по границе графемы всего текста; уложился — тот же объект. Обрезка: бюджет — `max` минус длина `…` в единице (в UTF-8 это 3 байта), графемы берутся подряд, пока укладываются; хвостовые пробелы последнего оставленного фрагмента снимаются (как `trimEnd`, с переводами строк), и `…` дописывается в этот фрагмент, наследуя его стили и ссылку: блок кода остаётся блоком, у ссылки укорочена подпись, адрес прежний; не осталось ничего — одно `…` без стилей. Поэтому `max` не меньше длины `…` в своей единице. Разбиение — жадно: окно — самый длинный префикс из целых графем не длиннее `max`; в нём берётся последний разделитель по приоритету — абзац `\n\n`, строка `\n`, пробел (начаться разделитель должен в окне, влезать в него не обязан), если часть до него не короче `max/2` в единице лимита; иначе пробуется следующий приоритет, в последнюю очередь — граница графемы, уже без порога. Снимается ровно найденный разделитель, поэтому склейка частей и снятых разделителей даёт исходный текст. Внутри ссылки и строчного кода, что укладываются в `max`, границ нет — фрагмент целиком уезжает в следующую часть; на блок кода это не распространяется. Стиль на разрезе продолжается в обеих частях, графема длиннее `max` уходит отдельной частью. Что делать с текстом сверх лимита — обрезать, разбить или переписать экран — решает проект; помощники дают способ. *Почему:* у одного мессенджера разные лимиты меряются по-разному; составной символ (семья, флаг, тон кожи, буква с акцентом) собеседник видит одним знаком, и разрезанный он портит текст; порог половины лимита не даёт частям мельчать, а приоритет разделителей сохраняет абзацы и строки. *Отвергнуто:* одна единица на мессенджер; счёт исходника с разметкой в общей части — мессенджер, чей API считает разметку, объявит меньший `max` или получит свой счётчик; резать по кодовым единицам; отдельная зависимость для графем.

**D-UI-37. Порт мессенджера — намерения к собеседнику.** `MessengerPort` объявляет намерения общей части: `show` (новое сообщение), `update` (показанное сообщение должно выглядеть так), `retire` (варианты больше не действуют), `answer` (нажатие принято) и `notify` (уведомление, всегда по инициативе). Способ выбирает мессенджер: `update` без правки на месте даёт новое сообщение и `edited: false` с новым handle, `retire` без правки ничего не делает, `answer` без ответа на нажатие в возможностях — `ok`. Общая часть не спрашивает «умеешь править?», а читает `edited` из итога. Итог — `Delivery<T>` (`Result` из `dmg-core`) с причиной недоставки без данных: `window` (нет права писать первым), `blocked` (собеседник недоступен), `rejected` (мессенджер отверг форму или лимит — дефект показа), `unavailable` (сбой транспорта или предел частоты). Недоставка — значение, а не бросок; бросок порта — дефект. `MessageHandle`, `peer` и `press` — непрозрачные строки мессенджера, общая часть хранит их как есть. Признак `initiative` в `SendOptions` отличает перечитывание по событию от ответа на сигнал собеседника. *Почему:* одни и те же намерения ложатся на мессенджеры с правкой и без, с окном инициативы и без; проверка «умеет ли» перед каждым вызовом размножила бы ветки в беседе. Сообщество — отдельный порт: он добавится необязательным полем `community?` без ломки, а в возможностях место для него есть уже сейчас. *Отвергнуто:* один порт со всеми операциями сразу и `unsupported` у тех, кто не умеет, — форма операций сообщества объявлялась бы до проектирования; недоставка броском — ожидаемый исход смешался бы с дефектом. Дополнено D-UI-59: порт сообщества `CommunityPort` (`exclude`, `invite`, `approve` — handle группы и личность транспорта, итог `Delivery<void>`) появился необязательным полем `MessengerPort.community?`; способ исполнения (например, исключить насовсем или мягко) выбирает мессенджер.

**D-UI-38. Возможности мессенджера — JSON-данные по схеме.** `MessengerCapabilities` — простой объект: имя, виды сообщений (`kinds`, содержит `text`), правка на месте (`edit`), лимиты текста без вариантов (`text`) и с вариантами (`textWithOptions`), число, подпись и длина короткой ссылки вариантов (`options`), ответ на нажатие (`pressAnswer`, нет — ответ не показывается), форма целиком (`form`, место), право писать первым (`initiative`: всегда, после первого контакта или окно в мс), сигналы и операции сообщества (место). Все лимиты — числа; мессенджер без объявленного предела ставит практическое число по своей документации. Схема `MessengerCapabilitiesSchema` проверяет: пределы — целые не меньше 1, у лимита текста предел не меньше длины `…` в его единице (в UTF-8 — 3 байта), окно — целое число мс не меньше 1, виды, единицы, сигналы и операции — из известных. Схема нестрогая: пакет мессенджера вправе добавить свои поля. *Почему:* возможности — свойства узла графа и вход стража при сборке; одна схема служит обоим, а JSON-представимость позволяет хранить их в графе без преобразований. *Отвергнуто:* методы «умеешь ли» у порта — их не положить в граф; строгая схема — пакет мессенджера не смог бы объявить своё. Дополнено D-UI-59: сигналы и операции сообщества больше не место — их читают CH-03 и сборка `Communities`; вид сигнала — `CommunitySignalKind`, к четырём добавлен `requested` (человек подал заявку на вступление: без него операция `approve` мертва); `CommunitySignal` — данные сигнала.

**D-UI-39. Страж лимитов перед портом.** `MessageFit` — чистая подгонка сообщения под возможности, без лога (её переиспользует правило графа): лишние варианты отбрасываются с хвоста, ссылка оставленного варианта сверх лимита — бросок (дефект общей части), подписи обрезаются по `options.label`, текст — по `textWithOptions`, если варианты есть, иначе по `text`; ответ на нажатие — по `pressAnswer`. Уложилось — тот же объект и разрезов нет. `LimitedMessenger` — декоратор порта: подгоняет каждое сообщение и ответ, пишет по записи на разрез — обрезка `warn`, лишние варианты `error`, источник `chat-ui` — и отдаёт итог порта как есть. В записи — мессенджер, операция, лимит, единица, предел и длина (у подписи — номер варианта); ни текста, ни подписей, ни собеседника, ни handle, ни ссылок (ERR-07). Возможности порта не по схеме — бросок при сборке. Беседа держит стража, а не голый порт. *Почему:* обрезанный текст с `…` и усечённый список вариантов собеседник прочтёт, а отвергнутое мессенджером сообщение потеряется; запись в лог показывает разработчику, какой экран не уложился. Лишние варианты — `error`: экран потерял действие. *Отвергнуто:* бросок на лишних вариантах — показ падал бы у собеседника; обрезка без `…` — собеседник не видит, что текст не весь.

**D-UI-40. Подставной мессенджер в памяти.** `MemoryMessenger` (`dmg-ui/chat-ui/testing`) — одна реализация порта с журналом `MessengerEntry`, поведение выводится из возможностей. Два набора — статическими фабриками: `editing()` — «правит, вариантов много, писать первым можно всегда» и `windowed(clock)` — «не правит, три варианта, окно инициативы на сутки, ответа на нажатие нет». Окно — по часам теста, без таймеров: инициатива проходит при открытом окне, ответ собеседнику проходит всегда и сам открывает окно, `heard` отмечает входящее. Подставной мессенджер строгий: сообщение, которое страж изменил бы, и пустой текст без вариантов отвергаются (`rejected`), так тест видит, что без стража сообщение теряется; `failNext` задаёт следующую недоставку. *Почему:* общая часть видит разницу мессенджеров только через возможности; два набора с противоположными свойствами ловят код, который полагается на одно из них. *Отвергнуто:* класс на каждый набор — поведение разошлось бы с возможностями.

**D-UI-43. Беседа: сигналы, очередь, отсев.** Сигнал беседы — данные мессенджера: `enter` (вход и место под параметр), `text`, `press` (ссылка и id нажатия), `attachment` (место: вид и непрозрачный идентификатор, до действия не доводится), `cancel`, `back` (D-UI-53); у каждого `id`, `peer`, `sender`. Сигналы и проактивные показы одной беседы идут по одному; беседы разных собеседников друг друга не ждут. Повтор `id` отсеивается — не исполняется и не отвечается, в снимке — 128 последних id; id длиннее 256, текст длиннее 64 Ки и пустой или длиннее 256 собеседник — отказ с `warn` без данных. На каждое нажатие — один `answer`, после показов (текст ответа — D-UI-54). Личность — только `people(sender)` транспорта; отправитель без личности и чужая личность беседу не трогают (`warn` и ответ на нажатие). Бросок порта (`people`, сборка беседы, порт мест) — дефект: `error` без данных, на нажатие — `answer`, узел не бросает. Показ — на месте или новым по положению живого места (D-UI-51), проактивный показ — по инициативе. След — один на сигнал собеседника: действие, выход и открытие входа «в начало» после него идут одним запросом; проактивный показ — своим следом: перечитывание идёт следом события, выданным сервером, нового запроса беседа не берёт. Узел `Conversations` — и вход уведомлений: он доставляет `NotificationDelivery` собеседнику получателя в той же очереди (D-UI-56). Узел `Conversations` держит беседы в памяти не больше предела (по умолчанию 1000): давняя нетронутая выгружается — очередь дождана, снимок записан, подписка снята. *Почему:* мессенджер повторяет апдейты и шлёт их параллельно, а экран и таблица ссылок беседы — общее состояние; без выгрузки подписки живых экранов копятся. *Отвергнуто:* очередь на весь узел — один медленный UC задерживал бы всех; личность из данных сигнала.

**D-UI-44. Таблица ссылок — данные; ссылка не повторяется.** Запись — вид цели, номер экрана или черновика беседы, ревизия, имя действия, поле шага, подпись; ссылка — эпоха воплощения (5 знаков) и счётчик в base36, `[a-z0-9]`, до 16 знаков. Эпоха новая при создании беседы и при каждом восстановлении, поэтому ссылка не повторяется ни после восстановления, ни после вытеснения, ни при потерянной записи снимка. Предел — 256 записей, вытесняются старейшие. *Отвергнуто:* счётчик в снимке (повтор при потерянной записи), запись снимка до показа (две записи на сигнал), резерв блоками.

**D-UI-45. Снимок беседы и хранилище.** `ConversationSnapshot` — JSON по схеме `ConversationSnapshotSchema` (версия, владелец, номера, ссылки, `seen`, живой экран с отпечатком и полями живого места — `handles`, последнее сообщение, хэш ключа следа, положение (D-UI-51, D-UI-52), черновик, путь переходов (D-UI-53), `notified` — ключи отсева уведомлений (D-UI-56)); снимок экземпляра внутри проверяет ядро. Снимок не по схеме не принимается целиком: беседа заново, `warn` без данных. Массивы и строки схемы ограничены, у `handles` предел — 32. Порт `ConversationStore` (`load`/`save` по `peer`, одно хранилище на приложение мессенджера, доверенное); `MemoryConversationStore` хранит строку JSON. Снимок пишется после каждого сигнала, и при дефекте беседы тоже, и после проактивного показа — в очереди собеседника. Сбой чтения хранилища — сигнал не исполняется: беседа не создаётся, снимок не перезаписывается, `error` без данных, собеседнику — заметка «Сейчас не получилось. Попробуйте позже.», на нажатие — `answer`; следующий сигнал читает хранилище заново. Сбой записи — `error` без данных, беседа работает в памяти. Перед записью снимок проверяется той же схемой: снимок не по схеме не пишется (в хранилище прежний), в лог — `error` без данных. *Почему:* частичное принятие снимка сложнее и опаснее, чем новая беседа; круг через строку JSON доказывает, что снимок JSON-представим; разовый сбой чтения не должен стирать черновик, ссылки и отсев и пропускать чужую личность мимо сверки владельца.

**D-UI-46. Нажатие после перезапуска — по отпечатку показанного вида.** Беседа хранит SHA-256 показанного вида (текст без заметки, варианты с видом и именем цели, без ссылок). Экран снимка поднимается лениво, на первом сигнале собеседника; после восстановления экземпляра отпечаток совпал — ссылки экрана переносятся с ревизии снимка на ревизию + 1, экран заново не показывается, нажатие исполняется; не совпал — нажатие действия встречает `stale` ядра, у локального действия ту же проверку ревизии делает беседа, и экран показывается с пометкой «Экран обновился.». Экран снимка не восстановлен — заметка, и любой сигнал, кроме `enter`, поглощается входом «в начало». Ядро не меняется. *Отвергнуто:* сравнение данных и состояния экземпляра — меняющееся скрытое поле дало бы ложную пометку; правка ядра (`restore` без роста ревизии) — ядру нужно было бы знать прежние данные.

**D-UI-47. Сбор входа по шагам.** Вход действия с полями собирает черновик беседы — данные в снимке (`DraftJson`: номер, экран, цель с ревизией показа, поля на момент начала, ответы, страница вариантов); экраны и черновики нумеруются одним счётчиком беседы, ссылки шага — номер черновика и поле. Свободный текст — текущему полю, без черновика — первому полю доступного основного действия; действие без полей текст не запускает («Выберите вариант.»). Вариант — нажатием, подписью или номером `1…n` по всему списку (подпись важнее номера, номер вне списка — вопрос заново). Сверх лимита мессенджера (`OptionLayout`) — страницы кнопок и одна кнопка «Ещё» по кругу, а у поля, где на странице не остаётся двух вариантов, — номера в тексте вопроса по 10; варианты экрана листаются так же, но номеров не получают: свободный текст на экране идёт основному действию. `cancel` сбрасывает черновик («Ввод отменён.» и вид). Отвергнутый вход повторяет поле из первого замечания с его текстом — только в беседу автора значения, не в лог. Ссылка шага сброшенного или чужого черновика — «Действие сейчас недоступно.»; любой вариант вне шагов черновик сбрасывает. После восстановления ревизия цели черновика переносится вместе со ссылками экрана, если вид совпал с показанным. Форма целиком — место в возможностях, не реализуется. *Почему:* черновик в снимке переживает перезапуск, а раскладка под лимит не даёт стражу лимитов отбросить варианты. *Отвергнуто:* обрезка вариантов стражем — действия пропадали бы молча; номера у вариантов экрана — номер там читался бы как текст основному действию.

**D-UI-48. Учебный диалог — без фасада.** Фасада над беседой нет: сторис, приёмка и тесты политик идут на беседе (`Conversations`, `Conversation`) с двумя подставными мессенджерами, уведомления доставляет узел бесед (D-UI-56), снимок беседы — `ConversationSnapshot` (D-UI-45). От учебного диалога остались имя канала `DIALOG_CHANNEL` (канал приложения UI и след; поставщик графа — `ChatGraphProvider` с именем `CHAT_PROVIDER`, D-UI-57) и рендерер примеров `DialogRenderer` (возможности по умолчанию — просторные, тексты примеров не режутся). Правила беседы: ссылка локального действия, выданная до перечитывания, даёт «Экран обновился.»; ссылка действия с полями на закрытом экране — «Экран уже закрыт.» сразу, без вопросов полей; текст без живого экрана открывает вход «в начало»; выход и вход «в начало» после него — один запрос, а не два (след — один на сигнал, D-UI-43). *Почему:* политики исходов живут в одном месте — в беседе; вторая форма показа рядом удваивала бы тесты. *Отвергнуто:* оставить фасад ради снимка экземпляра — код, который читают одни тесты. Заменено D-UI-57 в части поставщика графа: поставщик учебного диалога удалён, граф общей части мессенджеров ставит `ChatGraphProvider` (`dmg-ui-chat`).

**D-UI-50. Представление беседы — сообщения с вариантами-намерениями; реестр с перекрытием.** Представление экрана пишется один раз на общей части и возвращает одно сообщение или список (`ViewOutput`): текст типом и варианты-намерения без ссылок (`action`, `local`, `back`, `retry`, `home`); ссылки ставит беседа. Представление получает вид в типах экрана и набор показа `ViewKit`: возможности мессенджера (лимиты — решать ему) и варианты по умолчанию — доступные действия и локальные с подписями из Def, «Назад», если путь не пуст. Варианты — только у последнего сообщения и только из вариантов по умолчанию, без повторов и пустых подписей; сообщений — от 1 до 32; подписи и порядок — представления; нарушение — дефект представления, бросок с id экрана без данных вида. Короткая форма `ScreenPresenter.for` — текст тела и варианты по умолчанию; полная `ScreenPresenter.of` — вывод, свои тексты отказов и ключ следа в истории. Вид в отказе собирает сборщик показа беседы: текст отказа, «Повторить», «Назад» (путь не пуст), «В начало»; шапка заместителя и «только чтение» — первым абзацем первого сообщения. Отпечаток показанного (D-UI-46) считается от сообщений показа. Реестр `ChatViews` — на одно приложение мессенджера; `over` даёт новый реестр, где представления пакета мессенджера перекрывают общие по `id`; `presented()` — для рёбер `presents`. *Почему:* представление не знает таблицы ссылок, а скрыть и переставить «Назад» должно. *Отвергнуто:* представление возвращает только текст (нельзя скрыть «Назад»); сообщение со ссылками через обратный вызов (ссылки в представлении, отпечаток зависит от ссылок); ключ перекрытия — имя мессенджера в одном реестре (узел бесед и так одного приложения); параметр типа порта под поля мессенджера — до первого такого поля. Уточнено D-UI-57: `presented()` реестра каждого приложения — источник его рёбер `presents` у поставщика `dmg-ui-chat`.

**D-UI-51. На месте или новым — по положению живого места.** Живое место — сообщения последнего показа живого экрана или его шага (вид, вопрос поля, подтверждение, страница «Ещё»). Показ правит место на месте (`update`), если оно последнее в беседе, число сообщений совпало и место не защищено следом в истории (D-UI-52); иначе прежнее последнее сообщение места с вариантами уходит (`retire` с последним содержимым и ссылкой нажатого, если она из его вариантов) и показ идёт новыми (`show`). `update`, давший новое сообщение (`edited: false`), — остальные части новыми, прежнее последнее уходит. Показ новыми, не доставивший ни одного сообщения, место не меняет: следующий показ идёт в прежнее место и, правя его на месте, возвращает варианты. Положение сбивают доставленная заметка беседы, любой сигнал собеседника, кроме нажатия (с первым показом сигнала или его концом; сигнал с дефектом место не трогает), и уведомление (метод места `knock()`; зовёт его доставка уведомлений беседы, D-UI-56); проактивный показ — в место, по инициативе. Мессенджер без правки на `update` шлёт новое — правило в беседе одно. Место (сообщения, последнее сообщение, хэш ключа, положение) хранится в снимке живого экрана необязательными полями; снимок без них — место не последнее, первый показ новым. Последнее сообщение идёт в снимок, только если проходит схему сообщения места (пределы фрагментов, текста, ссылки); иначе место пишется без него — снимок не отвергается целиком, после перезапуска уход прежнего сообщения (`retire`) пропускается. При переходе на другой экран место переходит к новому экрану. *Почему:* одно правило для всех мессенджеров, от сторис не зависит. *Отвергнуто:* правка на месте всегда, пока экран живой (обновление уходит вверх, его не видно); вопрос и подтверждение — всегда новыми (лишние сообщения у мессенджера с правкой).

**D-UI-52. След в истории по ключу.** Представление вправе объявить след (`history`): ключ — адрес экрана или значение из вида. Место с видом экрана со следом правит только вид того же живого экрана с тем же ключом — по положению; смена ключа, уход на другой экран или шаг — прежнее сообщение остаётся в виде «после ухода» (`retire`), показ идёт новым. Листание «Ещё» вариантов того же вида — тот же ключ, на месте. Ключ в снимке — SHA-256 (hex): он может быть данными собеседника. Ядро о ключе не знает. *Почему:* шаг урока или страница должны остаться в беседе, а повтор того же шага — не плодить копии. *Отвергнуто:* правка прежнего сообщения ключа, даже если оно не последнее (правка уходит вверх беседы, беседе пришлось бы помнить сообщения ключа отдельно от места).

**D-UI-53. Путь переходов и «Назад».** Беседа помнит путь — снимки экземпляров (адрес и состояние) экранов, с которых ушла переходом на другой экран; переход на тот же экран путь не растит, на экран из пути — обрезает до него; вход приложения, «В начало», выход сторис и невосстановленный экран путь сбрасывают; предел — 16 элементов, элемент — до 8192 знаков JSON (длиннее — в путь не кладётся, путь прежний). Путь меняется только после успеха: переход растит его, когда экземпляр цели открыт (до показа — «Назад» в первом показе), «Назад» снимает элемент, когда `restore` ответил; бросок порта путь не трогает. «Назад» (сигнал `back` или вариант) поднимает верхний элемент через `ScreenRuntime.restore`: тот же адрес и состояние, свежие данные; не восстановился — заметка и вход «в начало». Вариант «Назад» есть, когда путь не пуст; представление вправе скрыть или переставить его. Экран о пути не знает. Путь — необязательное поле снимка, состояние в нём — данные собеседника, только в снимке. *Почему:* снимок экземпляра ядра уже даёт адрес и состояние — ядро не правится. *Отвергнуто:* путь как история браузера (каждый переход — элемент: листание списка растит путь, циклы); помощник пути в ядре — сравнить не с чем до второго канала.

**D-UI-54. Исходы беседы и ответ на нажатие.** Таблица исходов действия и локального действия (гайд «Пакет канала», §4) дополнена: показ вида, вопроса поля и подтверждения идёт в живое место (D-UI-51), заметки — новыми сообщениями. Выход сторис — вход «в начало» с текстом выхода (подпись и описание выхода) перед видом, одним показом. Реакции на нажатие, после которых экран не меняется («Такого варианта нет.», «Экран уже закрыт.», «Действие сейчас недоступно.» — без активного черновика), у мессенджера с ответом на нажатие уходят текстом ответа, без сообщения и без сдвига положения; иначе — заметкой. На каждое нажатие — ровно один ответ, последней операцией сигнала; при дефекте беседы — без текста. *Почему:* реакция не засоряет беседу и не сбивает положение. *Отвергнуто:* заметка всегда (каждое старое нажатие — сообщение и потеря правки на месте); и заметка, и текст ответа (дублирование).

**D-UI-55. Поиск уведомления по `id`.** `UiIds.findNotification(id)` — пара к `findScreen`: уведомление набора по `id` либо `undefined`; чужой `id` и `id` экрана — не бросок. *Почему:* канал получает `DeliveredNotification` с `id` узла и должен отличить чужой `id` от отсутствующего представления.

**D-UI-56. Уведомления беседы.** Узел бесед доставляет уведомления (`NotificationDelivery`): собеседника получателя даёт порт `peers` (личный чат одной личности в приложении мессенджера): он обязан быть обратным к `people`, пакет этого не сверяет — порту доверяют; собеседник проходит ту же проверку длины, что у сигнала. **D-UI-59. Сообщество: манифесты и исполнитель.** Исполнитель `Communities` — один на приложение мессенджера, как узел бесед; спека — приложение, тот же `ChatCommunitySpec`, что у графа (D-UI-60), порт мессенджера, бэкенд вызова UC, контекст сервера и четыре порта перевода: `people` (личность транспорта → uuid) и `members` (обратно), `keys` (handle группы → ключ домена сообщества) и `handles` (обратно). Домен видит только свои ключи; handle группы и личность транспорта до него не доходят. Вызывающий UC — `SystemCaller` от узла (`module` — имя набора UI, как у `RecipientList`; `name` — `id` узла сигнала или реакции), без человека: человек ничего у домена не просил, политика UC — явная: `allowAll` — только при `callers: ['system']` (с `user` в `callers` UC вызовет любой человек с чужим `userId`), иначе своя проверка системного вызывающего; сборку это не ужесточает. Query UC реакции — граница доступа: вызывается без субъекта, сам проверяет текущее состояние и не отдаёт целью поля своего входа. Сборка бросает (имена приложения и манифеста, без значений; префикс броска и модуль-владелец UC — у `CommunityManifest`, `DefIndex` один): манифест не прошёл `CommunityManifest` (тот же текст); пределы `limit` — не целые ≥ 1 (`0`, `NaN`, дробь выключили бы отсев); UC сигнала не command, UC реакции не query; у UC нет `system` в `callers` (MAN-11); сигнал или операция не объявлены в `capabilities.community` мессенджера (исполнительная пара к CH-03); реакции есть, а порта `messenger.community` нет; операция `inviteLink` — «не реализовано» (DEBT-UI-25). Сигнал (`receive`, данные `CommunitySignal { id, kind, community, member? }`): пределы (поля — строки, не строка — отказ той же причиной; `id` ≤ `MAX_SIGNAL_ID`, handle 1…`MAX_PEER_LENGTH`, `member` ≤ `MAX_PEER_LENGTH`) → манифесты этого вида (нет — ничего) → отсев по ключу (вид, handle, участник, `id`: один апдейт мессенджера бывает у нескольких участников), ключ принимается до исполнения (`MAX_COMMUNITY_SIGNALS` = 1024) → очередь на handle → `keys` (нет ключа — незнакомое сообщество, UC не вызывается) → `people(member)`, только если вход хоть одного манифеста вида берёт `person` (нет uuid — незнакомый: манифест с `person` без `strangers` не вызывается, с `strangers: true` — вход без поля человека; манифест без `person` исполняется и для незнакомого — личность ему не нужна, группа известна по `keys`; данных мессенджера о незнакомом нет нигде) → вход по `input`, на все манифесты вида — один след запроса канала. Пустая строка из порта перевода — как `undefined`. Личность — только из `member` через `people`; uuid в сигнале нет. Сигнал никогда не исполняет операцию сообщества. Реакция (`start`): одна подписка `EventSubscriber` (`dmg-core/app`, D-98 `dmg-core`) на событие, сколько бы реакций на него ни было; повторный `start` без остановки — бросок. Вход query UC — поля payload по `input`; цель — только строки выхода (объект или элементы массива, не больше `MAX_TARGETS` = 256), строковые непустые поля `targets`; строка не по форме — `warn`, операции нет. Нет handle или личности — `warn`. Отсев — ключ SHA-256 от `JSON.stringify([id узла, id события, ключ, uuid])`, проверка до операции, приём после успешной (`MAX_REACTED` = 1024): повтор после недоставки или броска исполнится; операции одного сообщества идут в очереди на ключ — повторы одного события не гонятся. Порт сообщества — напрямую, без стража лимитов: текста у операций нет. Входы не бросают (ERR-01), обработчик события тотален: иначе подписчик платформы запишет текст броска; бросок порта перевода или порта сообщества — дефект, исполнитель его ловит. Лог (`CommunityLog`, источник `chat-ui`): имя мессенджера, вид сигнала (только из `COMMUNITY_SIGNALS`, иначе без поля) или `id` узла реакции, событие и его id, причина, код отказа, операция, имя ошибки; ни handle, ни личности, ни uuid, ни ключа, ни id сигнала, ни payload, ни текста броска (ERR-07). Отсев — в памяти (DEBT-UI-24). Ядро не правилось: `SystemCaller`, `Trace`, `DefIndex`, `UcDispatch`, `ServerContext` и `EventSubscriber` уже публичны — это ответ на вопрос «что потребуют сигналы сообщества»; DEBT-UI-11 закрыт. Зона `chat-ui/src` проверки импортов пускает `dmg-core/app`. *Почему:* операции над группой по подделанному сигналу невозможны — путь к операции лежит через домен (событие → query UC), а цель берётся только из выхода UC; домен нейтрален к мессенджеру, второй мессенджер не требует поля в домене. *Отвергнуто:* сигналы через `UiSession.on` и `ChannelNode` ядра (подписка на сессию личности, вызывающий — человек); handle группы в домене; человек вызывающим — «система за человеком» или сам человек (политика видела бы субъектом того, кто ни при чём); голый `bus.subscribe` вместо `EventSubscriber` (вторая копия страховки платформы); цели из payload события или сигнала.

**D-UI-60. Граф сообщества и CH-03.** Манифесты сообщества приложения — один объект `ChatCommunitySpec` (`signals`, `reactions`) в `ChatAppSpec.community`; тот же объект получит исполнитель сообщества, две копии не разойдутся. Сигнал `ChatSignalSpec` — вид сигнала мессенджера → command UC, `input` — поле входа UC → `community` (ключ домена сообщества) или `person` (uuid), `strangers` — вызывать и для незнакомого; реакция `ChatReactionSpec` — событие домена → query UC (`input` — поле входа UC → поле payload) → операция мессенджера, цель — поля выхода UC `targets.community` и `targets.person`. Операция `inviteLink` объявляется (тип, возможности, граф), исполнение — позже. `CommunityManifest` проверяет манифест при сборке, одна проверка для поставщика и исполнителя: имя повторено среди сигналов или среди реакций приложения или не сегмент `GraphId`, UC или событие вне модулей приложения (`DefIndex` по `dependsOn`), пустые `input` или поле `targets` — бросок с именами приложения, манифеста и Def, без подписей и описаний; поставщик бросает тем же текстом. Под приложением поставщик ставит узлы `chatSignal` (`<app>/signal-<имя>`, свойства `{ signal }`) и `chatReaction` (`<app>/reaction-<имя>`, свойства `{ operation }`) и рёбра ядра: `invokes` от сигнала к UC, `notifiedBy` от реакции к событию и `reads` к UC (концы — `DomainIds`). Тип UC поставщик не проверяет: реакцию на command UC ловит UI-10 строкой отчёта, бросок спрятал бы её. CH-03 — сигнал или реакция прямо под приложением UI только если мессенджер приложения (свойства `chatMessenger` под ним, схема `MessengerCapabilitiesSchema`) принимает сигнал или исполняет операцию; приложение с сигналом или реакцией без `chatMessenger` — тоже строка; свойства не по схеме — молча (строку о возможностях даёт CH-01). *Почему:* граф ядра уже предписывает узлам канала рёбра `invokes` и `notifiedBy`, а UI-10 проверяет любой узел с `notifiedBy`; бросок на «вне приложения» обязателен — UI-22 видит только рёбра поставщика `dmg-ui`, ребро `dmg-ui-chat` к сироте молчало бы. *Отвергнуто:* `signals` и `reactions` прямо в `ChatAppSpec` (две формы для графа и исполнителя); свои виды рёбер сообщества (UI-10 не охранял бы реакцию); проверка типа UC броском поставщика.

## Telegram

**D-UI-61. Пакет Telegram: узкий порт Bot API и мессенджер.** `TelegramMessenger` (`dmg-ui/tg-bot`) исполняет `MessengerPort` поверх порта `BotApi`: по методу на операцию Bot API (`sendMessage`, `editMessageText`, `editMessageReplyMarkup`, `answerCallbackQuery`; позже `setMyCommands` — D-UI-64, `banChatMember`, `unbanChatMember`, `approveChatJoinRequest` — D-UI-65), параметры — JSON Bot API как есть (snake_case, подмножество полей), ответ — `BotApiResult`. Отказ Bot API — значение `{ ok: false, error_code, description }`, бросок порта — сбой транспорта; ответ и `result` пакет сверяет схемой, транспорту не верит. Реализацию порта (на библиотеке или на сети) и подачу апдейтов даёт проект: пакет не импортирует библиотеку и не ходит в сеть. Методы мессенджера не бросают: недоставка — `Delivery`. Текст (`TelegramText`) — видимый текст (`PlainText`), одиночный суррогат заменён на U+FFFD (длина в UTF-16 та же), и `entities` со смещениями и длинами в единицах UTF-16: `bold`, `italic`, `strikethrough`, `code`, `pre`, ссылка — `text_link`, цитата — один `blockquote` на непрерывную серию фрагментов. Строчные стили и ссылка ставятся на каждый фрагмент отдельно, поэтому две сущности либо не пересекаются, либо одна внутри другой. Правило вложенности Bot API целиком: сущности не пересекаются частично, в `code` и `pre` ничего не вкладывается, цитаты не вкладываются; ссылка на фрагменте с кодом снимает `code` и `pre` — на одном диапазоне Telegram показывает код без ссылки (проверено на живом клиенте); строчный стиль со строчным кодом даёт обе сущности — не сверено. Строчный код в цитате отбрасывается: сочетание не сверено, доставка важнее стиля. Адрес ссылки — только `http`, `https` и из `tg` лишь `tg://resolve` и `tg://user` (профиль), иначе текст без ссылки: `tg://login`, `tg://proxy`, `tg://join` под чужой подписью — фишинг. Пустой или из одних пробелов текст — заглушка `TELEGRAM_TEXTS.empty`: Bot API требует 1–4096 знаков, а беседа пропускает в порт пустой текст с вариантами. Клавиатура (`TelegramKeyboard`) — по кнопке в строке, `text` — подпись, `callback_data` — ссылка беседы; ссылка вне 1–64 байт UTF-8 — `rejected` без вызова API (страж меряет ссылку в знаках, ссылки беседы — `[a-z0-9]`, проверка байтов — страховка). Собеседник — каноническое десятичное целое > 0, безопасное для JS; `chat_id` уходит числом. Иначе `rejected` без вызова API: неверный ответ `peers` не отправит экран в группу или в публичный канал (строку `chat_id` Bot API понял бы как имя канала). `show` и `notify` — `sendMessage` с выключенным предпросмотром ссылок, `reply_markup` — только при вариантах, handle — `String(message_id)`. `update` — `editMessageText` того же сообщения, без вариантов — явная пустая клавиатура; «message is not modified» (подстрока без учёта регистра у 400) — тоже правка на месте; иной 400 или handle не число — откат новым сообщением (`edited: false`, прежнее уводит беседа); 403, 429, 5xx и бросок — недоставка без отката. `retire` без нажатого или с нажатым вне вариантов — снятие клавиатуры (`editMessageReplyMarkup`); с нажатым — один `editMessageReplyMarkup` с отключённой кнопкой (D-UI-67), строки «Вы выбрали» нет, текст не правится; handle не число — `rejected`; «not modified» — `ok`. Каждый вызов порта из мессенджера, кроме ответа на нажатие, несёт `operation` (`show`, `update`, `retire`, `notify`) в записи лога; у `answerCallbackQuery` его нет. `answer` — `answerCallbackQuery` без `show_alert`, `peer` не нужен. Отказы (`BotApiFailure`): 403 — `blocked`; 429 и ≥ 500 — `unavailable`, без повтора по `retry_after`; прочие — `rejected`; бросок порта и ответ не по схеме — `unavailable` и `error`. Часы — необязательное поле `now?: () => number` (мс, по умолчанию `Date.now`) в `TelegramMessengerSpec`: от них считается срок бана при исключении (D-UI-65), тест без таймеров. Отказ Bot API может нести `parameters.migrate_to_chat_id` (группа стала супергруппой, D-UI-65). Лог (`TelegramLog`, источник `tg-bot`): имя мессенджера, операция, метод Bot API, `error_code`, описание сервера (`description`, до 200 знаков: текст Telegram без данных собеседника, без него отказ 400 не разобрать) и имя ошибки; ни id чата, ни `message_id`, ни id нажатия, ни текста, подписей, `callback_data` и текста броска. Возможности `TELEGRAM_CAPABILITIES`: текст и текст с вариантами — 4096 UTF-16, вариантов 100, подпись 64 UTF-16, ссылка 64, ответ на нажатие 200 UTF-16, правка есть, писать первым — после первого входящего, сигналы сообщества `joined`, `left`, `added`, `removed`, `requested` и операции `exclude`, `approve` (`invite` не объявлена, D-UI-65). Допущения, не подтверждённые документацией Bot API: дословный текст «message is not modified» (не распознан — откат, видимый дубль, а не потеря), число кнопок и длина подписи, код внутри цитаты, снятие клавиатуры пустой `inline_keyboard` в правке, обрезка пробелов сервером и смещения сущностей; единица длины текста не названа — взята `utf16`, самая строгая мера для символов вне BMP. *Почему:* в типе порта виден весь узкий набор обращений пакета, подставной порт типизирован, проекту остаётся адаптер в несколько строк (отказ библиотеки → значение); сущности вместо разметки снимают экранирование строк собеседника. *Отвергнуто:* `parse_mode` и MarkdownV2 — экранирование каждой строки и отказ Bot API на любой ошибке экранирования; порт одним общим методом «вызвать метод с параметрами» — пакет теряет типы, подставной порт разбирает имена методов строками; порт в форме библиотеки — пакет привязан к одной библиотеке, её типы просачиваются внутрь; повтор по `retry_after` внутри вызова — держал бы очередь собеседника на время ожидания.

**D-UI-62. Апдейт Telegram → сигнал беседы.** `TelegramUpdates` (`dmg-ui/tg-bot`) принимает апдейт Bot API как есть (`receive(update: unknown)`, подачу и `allowed_updates` даёт проект) и отдаёт сигнал беседы узлу бесед; перевод — `TelegramSignals`, чистый: сигнал, отказ с причиной или «ничего». Апдейт сверяется схемой valibot (`looseObject`, только нужные поля по типу), типам транспорта пакет не верит. Диалог — только личный чат: `chat.type === 'private'`, целое `chat.id` > 0 и `from.id === chat.id`; сообщение вне личного чата, `edited_message`, `channel_post` и группа сигналом беседы не становятся; апдейты участников (`my_chat_member`, `chat_member`, `chat_join_request`) — сигналы сообщества, D-UI-65. Поля сигнала — строки: `id` — `update_id` (отсев повтора беседой), `peer` — `chat.id`, `sender` — `from.id`. Личность — только `from` апдейта через порт проекта `people`: uuid даёт проект, владельца беседы сверяет узел бесед; в следе сигнала id Telegram нет вовсе (`Trace.fromRequest` с именем канала), в лог операций человек идёт uuid-ом вызывающего, `visitorId` не нужен — гостей у беседы нет. Личность держится на подлинности апдейта: проект подаёт в `receive` только апдейты от Telegram — getUpdates или вебхук с секретным токеном; пакет подлинность не проверяет. Текст, начинающийся сущностью `bot_command` со смещением 0: `/cancel` — `cancel`, `/back` — `back` (раньше таблицы); прочая команда, в том числе `/start`, — вход по таблице точек входа проекта (D-UI-64), имя в нижнем регистре, параметр `/start <параметр>` выбирает вход точки `link` и в сигнал не идёт; имени нет в таблице — вход-заглушка, «Такого входа нет.» скажет беседа; `@бот` после имени отбрасывается; прочий текст — `text`. Вложения: фото (самый крупный размер по площади) — `image`, документ — `file`, аудио и голос — `audio`, видео, анимация (раньше документа, который Bot API ставит рядом) и кружок — `video`; `handle` — `file_id`; стикер, место, контакт — ничего. Нажатие — `press{ ref: data, press: id }`. На каждое нажатие — ровно один ответ: нажатие диалога отвечает беседа, отвергнутое (чат не личный, чужой человек, инлайн-режим без `message`, без `data`, не по схеме при читаемом строковом `id`) — приём апдейтов через мессенджер, без текста: тексты беседы даёт узел бесед. Отказ — `warn` с причиной и видом апдейта (`update`: `message` или `callback_query`; у апдейта не по схеме без читаемого id нажатия вид не определить — поля нет), без данных; у нажатия сначала ответ, затем запись. Узел бесед не бросает по контракту (ERR-01); если всё же бросил — `error` с видом сигнала и именем ошибки, без страховочного ответа на нажатие; `receive` не бросает. *Почему:* `from.id === chat.id` в личном чате отсекает подмену собеседника, а целое положительное `chat.id` не пускает экран в группу или канал; ответ на отвергнутое нажатие снимает «часики» у клиента и не даёт подсказок постороннему. Пример `examples/tg-bot` (D-UI-68) подаёт апдейты только через `getUpdates`: подлинность держат токен и TLS к Telegram; вебхук с секретом — дело проекта. *Отвергнуто:* диалог в группе — экран и уведомления одного человека видели бы все участники; регистрация незнакомого отправителя в пакете — данные Telegram (имя) ушли бы в пакет, регистрацию делает проект до `receive`; вход по имени команды — открывал бы любой вход приложения без точки (заменён таблицей, D-UI-64).

**D-UI-63. Подставной порт Bot API и построитель апдейтов.** `MemoryBotApi` (`dmg-ui/tg-bot/testing`) — одна реализация `BotApi` в памяти с журналом вызовов `BotApiCall` (метод и параметры как есть). `message_id` растёт в каждом чате; правка неизвестного сообщения или сообщения другого чата — 400 «message to edit not found», правка тем же текстом, сущностями и клавиатурой — 400 «message is not modified», правка без `reply_markup` снимает клавиатуру — как Bot API. `failNext` задаёт отказ, `throwNext` — бросок следующего вызова: вызов есть в журнале, чат не меняется. `failOn(метод, отказ)` бьёт по следующему вызову только этого метода (в отказе — и `migrate_to_chat_id`), `holdOn(метод)` держит такой вызов до вызова возвращённого `release` (вызов уже в журнале): очередь сообщества без таймеров. Операции группы (`banChatMember`, `unbanChatMember`, `approveChatJoinRequest`) и `setMyCommands` — запись в журнал и `ok`, модели членства нет. `chat(chatId)` — сообщения чата глазами собеседника (`BotChatLine`: текст, сущности, клавиатура, число правок). `TestUpdates` — построитель апдейтов: `update_id` общий и растёт с 1, `message_id` — в каждом чате отдельно, id нажатия уникален, текст с `/` в начале — команда с сущностью `bot_command`; апдейты группы — `groupText(чат, человек, текст)`, `joined`, `left` (чат, человек, кто действовал), `botAdded`, `botRemoved` (чат, кто действовал), `joinRequest(чат, человек)`. Тесты `tg-bot` задают отказы Bot API через него, а не своими заглушками. Вход импортирует пакет только по имени `dmg-ui/tg-bot`. *Почему:* как у подставного мессенджера (D-UI-40) — один подставной порт с поведением Bot API ловит код, который полагается на успех правки; проекту он служит в тестах адаптера и сборки. *Отвергнуто:* заглушки порта в каждом тесте — расходятся с Bot API и между собой.

**D-UI-64. Точки входа Telegram, меню команд и граф TG.** Точка входа — запись `ChatEntryPointSpec` (`entry`, `via`, `key`); проект пишет один массив и отдаёт его двум читателям: `ChatAppSpec.entryPoints` (граф) и `TelegramUpdatesSpec.entryPoints` (приём). Слова пакета — `TELEGRAM_VIA`: `command` (ключ — имя команды `[a-z0-9_]{1,32}`), `menu` (то же; человек выбирает команду в меню бота, апдейт её от набранной не отличает — точка нужна, чтобы `TelegramMenu` опубликовал команду), `link` (параметр глубокой ссылки `[A-Za-z0-9_-]{1,64}`, `t.me/<бот>?start=<key>`). `TelegramEntryTable` ищет вход по команде (`command` и `menu` — одно пространство) и по параметру ссылки (своё); повтор ключа — выигрывает первая запись, точка с неизвестным способом пропускается. Разбор команды (`TelegramSignals`, экземпляр со спекой `{ entryPoints, bot }`): имя — в нижний регистр, параметр — как есть; `cancel` и `back` — раньше таблицы; `/start <параметр>` — вход точки `link`, нет такой или параметр не по формату — как `/start`; прочее — вход точки `command`/`menu`, нет в таблице — заглушка `UNKNOWN_ENTRY`, беседа отвечает «Такого входа нет.». Параметр в сигнал не идёт (поле `param` не заполняется) и не влияет на личность: `sender` — всегда `from.id`. `TelegramMenu.publish()` — один `setMyCommands` с командами точек `menu` в порядке таблицы без повторов, описание — название входа (`label` Def приложения), область — `all_private_chats`, `language_code` не задаётся; точек `menu` нет — вызова нет (список владельца не затирается); не бросает (ERR-01): отказ — недоставка и `warn`, бросок порта — `unavailable` и `error`; точка `menu` на вход, которого нет в Def, — бросок сборки. `setChatMenuButton` не вызывается. Вызов `publish()` при старте — дело проекта. `TelegramGraphProvider` (`dmg-ui-tg`) без своих видов и вклада: приложение Telegram — ещё одно `ChatAppSpec` в `ChatGraphProvider`; правила TG-01…TG-06 читают только узлы `chatEntryPoint`, `chatEntry`, `chatMessenger` и работают в области приложений UI с мессенджером `telegram` (виды — `CHAT_NODE_KINDS`, `CHAT_EDGE_KINDS`, экспорт `dmg-ui/chat-ui`). *Почему:* одна таблица на граф и приём — расхождения «граф знает точку, приём нет» нет; параметр ссылки недоверен (его присылает кто угодно), поэтому он выбирает только вход из таблицы; регистр команд Bot API не оговаривает, определение — строчные. *Отвергнуто:* вход по имени входа — любой вход открывался бы без точки; отдельный узел точки Telegram — вид `chatEntryPoint` уже есть, повторная регистрация вида — `duplicate-kind`; пустой список команд при отсутствии точек `menu` — затёр бы меню владельца.

**D-UI-65. Сообщество Telegram: апдейты группы, эхо бота, `exclude` и `approve`.** `TelegramUpdates` переводит апдейты группы в один `CommunitySignal` на апдейт и отдаёт его `communities.receive` спеки (`communities?` необязательно: нет — апдейты группы «ничего» без записи; `bot` — id бота, безопасное целое > 0, иначе бросок сборки; `my_chat_member` с `new_chat_member.user.id` не равным `bot` — сигнала нет и `error` «id бота не совпадает» без id). Группа — `chat.type` `group` или `supergroup` с безопасным `chat.id` < 0, иначе отказ `chat` (небезопасное целое — `schema`); поля сигнала — строки: `id` — `update_id`, `community` — `chat.id` со знаком, `member` — id человека. `chat_member`: был вне группы, стал в ней — `joined`, наоборот — `left`, `member` — `new_chat_member.user`; в группе — `member`, `administrator`, `creator` и `restricted` с `is_member: true`, `restricted` без `is_member` — апдейт не по схеме; прочее (повышение, ограничение) — ничего. `my_chat_member` в группе: бота добавили — `added`, убрали — `removed`, `member` — `from.id` (кто); в личном чате (блокировка бота) и в канале — ничего без записи. `chat_join_request` группы — `requested`, `member` — `from.id`. Эхо: `chat_member` с `from.id` = `bot` (собственные ban, unban, approve) — ничего без записи, иначе исключение вызвало бы сигнал `left` и петлю; опора — вывод «`from` — бот при действиях самого бота», в документации Bot API прямо не сказан (проверка — на живом боте до выкатки). Сообщение и команда в группе — по-прежнему ничего. Служебные сообщения о вступлении не читаются: `chat_member` — единственный источник `joined` и `left`, а он приходит, только если бот администратор группы и `chat_member` есть в `allowed_updates`; `my_chat_member` — всегда. `TELEGRAM_ALLOWED_UPDATES` — `message`, `callback_query`, `my_chat_member`, `chat_member`, `chat_join_request`: проект подаёт их в `getUpdates` или вебхук. `communities.receive` не бросает по контракту; брошенное — `error` с видом сигнала и именем ошибки, `receive` не бросает. Отсев повторов и очередь — в `Communities` (`chat-ui`). `TelegramMessenger.community` (`TelegramCommunity`) — на том же порту; в `Communities` идёт мимо стража. `exclude` — `banChatMember` с `until_date` = сейчас + 300 с (перед ban срок проверяется: безопасное целое > 1 600 000 000, иначе часы неверны — `rejected` и `error` без вызова API) и `unbanChatMember` с `only_if_banned: true`, как у нынешнего бота: срок — страховка, если unban не прошёл, бан снимется сам; ban отказал — unban не вызывается; ban прошёл, unban отказал — недоставка и `warn`, повтор события исполнит оба вызова заново (ключ отсева принимается только после успеха), ban повторно безвреден. В супергруппе бан удаляет сообщения исключённого (так делает Telegram); человек вернуться может. `approve` — `approveChatJoinRequest`; отклонить заявку нельзя (DEBT-UI-28). `invite` не объявлена в возможностях (CH-03 запретит такую реакцию), метод порта — отказ `rejected` без вызова и `error` без данных. Handle группы — каноническое целое < 0, участник — > 0, безопасные для JS; иначе `rejected` без вызова API, личный `peer` в группу не превращается. Отказы — как у мессенджера (403 — `blocked`, 429 и ≥ 500 — `unavailable`, прочее — `rejected`; бросок — `unavailable`). Отказ с `parameters.migrate_to_chat_id` (группа стала супергруппой, у неё новый id) — `rejected` и `warn` «группа перенесена в супергруппу» без id; перепривязки нет (DEBT-UI-27). Лог без данных (ERR-07): ни id группы, участника и апдейта; в `meta` — мессенджер, операция (`exclude`, `approve`, `invite`), метод, код, описание сервера, причина, вид апдейта и сигнала, имя ошибки; успех, эхо и апдейт без порта сообщества не пишутся. Подлинность апдейта — по-прежнему дело проекта (D-UI-62). *Почему:* сигнал сообщества — факт группы, а не диалог: `from.id` группы не принимается за собеседника; страховочный срок бана оставляет в худшем случае пять минут бана, а не вечность; перенос группы не усложняет пакет, пока группы школы нет в работе. *Отвергнуто:* `new_chat_members` — два источника одного вступления дали бы два сигнала; бан без срока — сбой unban оставил бы человека в бане навсегда; вызов проекту `migrated(старый, новый)` — новая форма спеки приёма, а перепривязка ключа домена всё равно на проекте.

**D-UI-66. Акцент варианта и момент времени — нейтральные поля общей части.** `MessageOption.accent?` (`primary` | `positive` | `danger`) — важность варианта, не цвет; `TextFragment.moment?` (`{ at, show }`, `at` — секунды Unix, целое не меньше 0, безопасное; `show` — `date` | `time` | `dateTime` | `relative`) — момент, который человек видит в своём часовом поясе. `TextFragment.text` у момента — запасной текст, всегда обязателен: его покажут мессенджеры без момента, старый клиент и `PlainText` (автор считает его в часовом поясе человека). Акцент ставит представление, переписав `kit.options`: у `ViewOption` он есть у `action` и `local`, беседа переносит его в `MessageOption` одним методом `ConversationReplies.option`, сама «важность» не угадывает. Момент строит `TextBuilder.moment(text, at, show)`: неверный `at` или `show` — бросок построителя; момент не склеивается с соседями. Прочие мессенджеры показывают подпись и запасной текст без акцента и момента (деградация, строка `ChatLine` та же). Страж лимита: целый фрагмент сохраняет момент, оборванный (и тот, к которому дописано `…`) теряет — остаётся запасной текст. Отпечаток экрана (D-UI-46) включает `accent` и `moment`, дописывая их в конец записи только когда они есть, — отпечатки экранов без них не меняются. Снимок беседы (`PlaceMessageSchema`): поля необязательные, допустимые значения задаёт схема, старые снимки читаются; без поля схемы после перезапуска `retire` потерял бы акцент и момент. Слов мессенджера в общей части нет: имя `style` занято `TextStyle`, поэтому акцент — `accent`.

**D-UI-67. Возможности Telegram: отключённая кнопка, цвет кнопки, дата и время.** Ушедший экран: `retire` с нажатым, найденным среди вариантов, — один `editMessageReplyMarkup` с клавиатурой из одной отключённой кнопки `{ text: <подпись нажатого>, disabled: {} }` (подпись через `toWellFormed`); текст не правится, строки «Вы выбрали» нет, предел 4096 откатом не служит. Без нажатого или вне вариантов — прежнее снятие клавиатуры. Отказы: 400 — `rejected` (и `warn`), 403 — `blocked`, 429 и 5xx — `unavailable`, «not modified» — `ok`; отката на строку выбора нет. Цвет: `accent` варианта → `style` кнопки (`primary` → `primary`, `positive` → `success`, `danger` → `danger`; таблица `ACCENT_STYLES`), без акцента поля нет. Момент: `TextFragment.moment` → сущность `date_time` на всю длину фрагмента, `unix_time` — `at`, `date_time_format` — `date` → `d`, `time` → `t`, `dateTime` → `dt`, `relative` → `r` (`MOMENT_FORMATS`); смещения — UTF-16; запасной текст остаётся в `text`. Сочетания: момент с `bold`, `italic`, `strike` — обе сущности; с ссылкой — остаётся `text_link`; с `code` и `codeBlock` — момент снимается (при `quote` с `code` он снимается тоже, хотя код в цитате отброшен, — допущение, в чек-лист); с отвергнутой ссылкой (схема не из `http`, `https`, `tg://resolve`, `tg://user`) — ссылки нет, `date_time` остаётся; в цитате — обе (допущение). Порт: кнопка — нажимаемая (`callback_data`, `style?`) либо отключённая (`DisabledButton`, `disabled` — пустой объект); `MessageEntity` дополнен `date_time`. `MemoryBotApi`: отпечаток «не изменилось» учитывает `disabled`, `style`, `unix_time` и формат, журнал хранит поля как отправлены; нажатия по отключённой кнопке нет — у неё нет `callback_data`. Состав Bot API (выписка на 2026-11-17, версия 10.4): `style` — 9.4, `disabled` — 10.3, `date_time` — 9.5. Допущения, не подтверждённые страницей Bot API, — в чек-лист проверки на тестовом боте: (1) отключённой кнопке не нужны `callback_data` и другие поля; (2) вид кнопки в клиентах без 10.3; (3) `style` с `disabled` не ставим; (4) лимит подписи как у обычной кнопки, 64 UTF-16; (5) клиент без `date_time` показывает `text`; (6) вложение `date_time` в `text_link`, `code`, `pre`, `blockquote`; (7) `unix_time` — целое не меньше 0, безопасное; (8) число кнопок — прежние 100. Перекрытие на учебном примере: `exampleTelegramViews` (`dmg-ui/tg-bot/testing`) = `exampleDialogViews.over([TaskListTelegramView, TaskCardTelegramView])` — «Выполнить выбранные» и «Выполнить» с акцентом `positive`, у открытой задачи в карточке момент `EXAMPLE_MOMENT` с постоянным запасным текстом (данных дат в примере нет, ядро не трогаем); остальные экраны и уведомления общие. Приложение Telegram в графе примера — сцена теста `telegramScene` (`views?` по умолчанию `exampleDialogViews`), а не третье приложение `ExampleDialogArch`: `chat-ui/testing` не зависит от `tg-bot`. `ExampleTelegramPreview` показывает экран примера через `TelegramMessenger` на `MemoryBotApi`; снимки — JSON запроса. Превью — не запрос беседы: оно перехватывает `ViewMessage` на пути сборщика показа и берёт только последнее сообщение, поэтому в нём нет шапки заместителя, раскладки «Ещё» и стража `MessageFit`, ссылки вариантов — `1..n`; сверка с живым запросом — в чек-листе, публичный показ «вид → `Message`» — DEBT-UI-29. Акцент варианта читает один метод `ScreenComposer.accent` (экспортирован из `dmg-ui/chat-ui`): беседа, отпечаток и превью. Прочие возможности Bot API: значок кнопки `icon_custom_emoji_id`, эфемерные сообщения, `sendMessageDraft`, `force_reply`, `sendWidget` и Mini Apps, опросы, стили `underline`/`spoiler`/`expandable_blockquote`, Communities, цвет и дата в уведомлениях — позже; «богатые» сообщения (`sendRichMessage`), виды сообщений (фото, аудио, голос, видео, документ) — следующий трек tg-rich; реакции, темы, чек-листы, suggested posts, message effects, guest mode, managed bots, подарки и stories, сущности `ton_address` и `bank_card_number` — не нужны (нет сценария школы). *Почему:* отключённая кнопка оставляет на месте ушедшего экрана сам текст и выбор человека без правки текста и без предела 4096; цвет и момент задают нейтральные поля общей части (D-UI-66), Telegram лишь переводит их в свои поля. *Отвергнуто:* откат на строку выбора, если кнопка не принята, — `disabled` часть Bot API 10.3, а прежний путь уходит.

**D-UI-68. Запускаемый пример `examples/tg-bot` и `grammy`.** Каталог `examples/tg-bot/` — пример потребителя `dmg-ui/tg-bot` на живом Telegram: `ExampleBot` (сборка узла бесед, приёма апдейтов, меню и уведомлений на порте `BotApi`), `GrammyBotApi` (порт на `api.raw` библиотеки; отказ Telegram — значение с полями только из ответа, иной сбой — бросок с фиксированным текстом без причины), `GrammyPolling` (`getMe`, `getUpdates` через `Bot.start` с `TELEGRAM_ALLOWED_UPDATES`, один общий обработчик), `TracingBotApi` (трасса вызовов), `ExampleProbe` (проба Bot API), входы `main.ts` и `probe.ts`, `ExampleEnv`, `ExamplePeople`. Учебная сторис ядра — без новых экранов. `grammy` — зависимость разработки корня репо с точной версией, не `peerDependencies` и не `dependencies`; импортируется только из `grammy-bot-api.ts` и `grammy-polling.ts` (их тестов и файлов типов; адаптеры по относительному пути берут только `main.ts`, `probe.ts` и тесты), это проверяет `ExampleZoneScanner` (и словарь `ChannelWordScanner`, и белый список `CoreImportScanner` для пакетов); адаптер и опрос живут в примере, не в пакетах (D-UI-61: реализацию порта даёт проект). Апдейты — только `getUpdates`: порт не открывается, подлинность держат токен и TLS (D-UI-62), `Bot.start` снимает вебхук бота, поэтому токен тестового бота отдельный. Сборка `ExampleBot` не знает ни сети, ни библиотеки и проверяется на `MemoryBotApi`; тест адаптера и опроса идёт на loopback `127.0.0.1` (проверяется тело запроса на проводе, отказы, сбой транспорта без токена), внешней сети нет. Хранилище бесед — `MemoryConversationStore`: после перезапуска беседы забыты, хранилище на диске — дело проекта. Токен только из окружения (`.env` в `.gitignore`, читает один `main.ts`, ARC-09), в репо его нет (`BotTokenScanner`); id людей и тексты в консоль и журнал не идут (ERR-07). Трасса вызовов — по флагу `EXAMPLE_TG_TRACE`, в файл (тексты и id людей), `.trace/` и `*.jsonl` в `.gitignore`; файл трассы доступен только владельцу (0600). Исключение из TST-07: пример берёт учебный домен из тестовых входов (`dmg-core/testing/example`, `dmg-ui/testing`, `dmg-ui/chat-ui/testing`, `dmg-ui/tg-bot/testing`) — учебный домен живёт только там, а правило относится к прикладному слою проекта. Проба — отдельный вход `bun run example:tg:probe <chat_id>`: через настоящие `TelegramMessenger` и `LimitedMessenger` шлёт 13 проб (`PROBE_CASES`, группа Е), которых учебные экраны не показывают. Ручная проверка — чек-лист в `examples/tg-bot/README.md` (запуск, группы 0, А–Г, Е, раздел «Что пример не проверяет»); пункт получает «пройден» или «не пройден», подтверждённое допущение D-UI-67 записывается в него, неподтверждённое — правка пакета с тестом. *Почему:* допущения о Bot API (отключённая кнопка, цвет, дата, пределы) документация не подтверждает; один запускаемый путь с реальной библиотекой дешевле, чем отложить их до первого проекта, а сборка и опрос разведены, чтобы дефект транспорта не прятался за подставным портом. *Отвергнуто:* отдельный `package.json` примера (два лок-файла, лишняя установка перед `check`); вебхук (нужны публичный адрес и секрет); перехватчик `api.config.use` вместо loopback (тело запроса на проводе не проверяется); хранилище бесед на диске (граница примера); сообщество и группа в примере (учебный домен их не знает).
