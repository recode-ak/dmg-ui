# Каталог правил

**Назначение:** проверяемые правила графа UI. Правило графа — тип `GraphRule` (`dmg-core/graph`): получает собранный граф и возвращает строки нарушений. В отчёте `arch:check` строка выходит как `<ID>: <текст>`. Правило меняется только через [decisions.md](../decisions.md).

Префиксы: `UI` — правила ядра (`UiGraphProvider`, вход `dmg-ui/graph`), `PG` — правила учебного страничного канала (`PageGraphProvider`, вход `dmg-ui/web-ui`), `CH` — правила общей части мессенджеров (`ChatGraphProvider`, вход `dmg-ui/chat-ui`), `TG` — правила Telegram (`TelegramGraphProvider`, вход `dmg-ui/tg-bot`). У каждого пакета канала свой префикс, и принадлежит он одному поставщику; он не совпадает с префиксами `dmg-core` и с `UI` (ARC-13, см. [D-UI-13](../decisions.md), [D-UI-57](../decisions.md)). Список префиксов репо держит проверка `RuleCatalog` (`RULE_PREFIXES`): новый префикс добавляется туда тем же коммитом, что и первое правило. Как собрать правила своего канала — `node_modules/dmg-core/docs/guides/graph-extension.md`.

Правила читают только граф: схемы `params`, `state`, `input` и данные выходов лежат в свойствах узлов как JSON Schema. Исключения — UI-20: примеры проверяются схемами valibot, поэтому правило получает набор UI в конструктор; CH-01: виды примеров и реестры представлений приложений правило получает в конструктор (собраны заранее, [D-UI-58](../decisions.md)), возможности мессенджера читает из графа.

В текстах нарушений `<id>` — `id` узла графа (`<набор>/<модуль>/<имя>` у экрана, сторис и уведомления, `<экран>/<действие>` у действия, имя приложения UI у приложения).

## Сторис, переходы, достижимость

| ID | Правило | Срабатывает, если | Текст нарушения |
|---|---|---|---|
| UI-01 | Вызывающие сторис допущены к каждому UC её экранов | в `callers` сторис есть вызывающий, которого нет в `callers` UC (`reads` экрана или `uc` его действия) | `сторис <id>: вызывающий «<caller>» не допущен к UC <uc> экрана <экран>` |
| UI-02 | Экран входит хотя бы в одну сторис | у экрана нет ни одного ребра `includes` от сторис | `экран <id> не входит ни в одну сторис` |
| UI-03 | У экрана и цели перехода есть общая сторис | действие ведёт (`leadsTo`) на экран, у которого с экраном-источником нет общей сторис; экран-вход приложения UI из правила исключён | `действие <id> ведёт на экран <цель>, с которым у экрана нет общей сторис` |
| UI-04 | Каждый выход экрана связан с исходом | у сторис, включающей экран, ни один исход не ссылается на выход экрана | `выход <имя> экрана <экран> не связан с исходом сторис <сторис>` |
| UI-05 | Переход и вход приложения ведут на экран его сторис | переход действия или вход приложения (`entry`) указывает на экран вне сторис приложения | `приложение <app>: экран <экран> ведёт на <цель>, которого нет в его сторис` и `приложение <app>: вход ведёт на <цель>, которого нет в его сторис` |
| UI-06 | У экрана и уведомления приложения есть представление в канале | нет ребра `presents` от приложения или узла под ним ни к самому узлу, ни к набору UI целиком | `приложение <app>: у экрана <id> нет представления в канале` (у уведомления — `у уведомления`) |
| UI-07 | Каждый экран приложения достижим от входов | экран не достигается от целей `entry` и ссылок `links` уведомлений приложения по переходам действий | `приложение <app>: экран <id> недостижим от входов` |

## Вызовы UC

| ID | Правило | Срабатывает, если | Текст нарушения |
|---|---|---|---|
| UI-08 | Загрузка экрана и уведомление читают только query UC | ребро `reads` ведёт к command UC | `экран <id> читает command UC <uc>` (у уведомления — `уведомление`) |
| UI-09 | Действие вызывает только command UC | ребро `invokes` действия ведёт к query UC | `действие <id> вызывает query UC <uc>: чтение — в загрузке экрана` |
| UI-10 | Узел, привязанный к событию, не вызывает command UC | у узла есть ребро `refreshedBy` или `notifiedBy` и ребро `reads` или `invokes` к command UC | `<id> привязан к событию и вызывает command UC <uc>` |
| UI-11 | UC для человека вызывается экраном | у UC `visible: true` нет ни одного входящего ребра `reads` или `invokes` | `UC <id> предназначен человеку (visible), но ни один экран его не вызывает` |
| UI-12 | Экран, действие и уведомление вызывают только UC для человека | цель `reads` или `invokes` — UC с `visible: false` | `<id> вызывает UC <uc>, не предназначенный человеку (visible: false)` |

## Форма манифестов

| ID | Правило | Срабатывает, если | Текст нарушения |
|---|---|---|---|
| UI-13 | Тексты заполнены | `label` или `description` узла `dmg-ui`, исхода, выхода, локального действия, подтверждения или входа — пустая строка или начинается с `TODO` | `<id>: пустой или не заполненный (TODO) <label\|description> у <узла\|исхода <имя>\|выхода <имя>\|локального действия <имя>\|подтверждения\|входа <имя>>` |
| UI-14 | У каждого поля схем UI есть `description` | поле без `description` в `params`, `state`, `input` действия, `input` локального действия или данных выхода; данные загрузки не проверяются: они выводятся из UC | `<id>: поле <путь> схемы <params\|state\|input\|local.<имя>.input\|exit.<имя>.data> без description` |
| UI-15 | Перехватываемая ошибка объявлена у UC экрана | код из `catches` экрана не объявлен (`failsWith`) ни у одного UC экрана | `экран <id> перехватывает <ошибка>, которой нет у его UC` |
| UI-16 | Основное действие экрана объявлено | `primary` не совпадает ни с одним именем из `actions` | `экран <id>: основное действие <имя> не объявлено` |
| UI-17 | Запись `refresh` согласована с экраном и событием | запись пуста (нет `params`, `subject`, `any`); ключ `params` — не параметр экрана; поле, на которое указывает значение `params` или `subject`, не входит в payload события | `экран <id>: запись refresh события <событие>: запись без params, subject и any` · `… ключ <имя> не параметр экрана` · `… поля <поле> нет в payload события <событие>` |
| UI-18 | Получатели уведомления заданы и согласованы с событием | список полей получателей пуст; поле (из `payload` — `fields`, из `query` — значения `input`) не входит в payload события; для `from: 'query'` UC получателей не query или у него нет `system` в `callers` | `уведомление <id>: список получателей пуст` · `… поля <поле> нет в payload события <событие>` · `… UC получателей <uc> — не query` · `… в callers UC получателей <uc> нет system` |
| UI-19 | `params` и `state` строгие, `input` — объект | схема `params` или `state` экрана без `additionalProperties: false`; схема `input` действия — не объект | `экран <id>: схема <params\|state> не строгая (strictObject)` · `действие <id>: схема input не объект` |
| UI-20 | Примеры проходят схемы своего экрана или уведомления | пример экрана не проходит `params`, `data` или `state`; пример уведомления — `data` | `<id>: пример <имя> не по схеме <params\|data\|state>: <сообщение valibot>` |
| UI-21 | Имена действий и локальных действий не пересекаются | одно имя есть и в `actions`, и в `locals` экрана | `экран <id>: имя <имя> и у действия, и у локального действия` |
| UI-22 | Ссылки узлов `dmg-ui` — только на Def набора UI и домена | ребро поставщика `dmg-ui` ведёт во внешний конец под `dmg-ui/orphan/` или `dmg-core/orphan/` (Def вне набора UI или домена); повтор одного сообщения не выводится | `<from> ссылается на <вид Def> «<имя>» вне набора UI и домена` |
| UI-23 | Форма сторис: `start` и выходы исходов принадлежат её экранам | `start` не входит в экраны сторис; исход ссылается на выход экрана вне сторис | `сторис <id>: start <экран> не входит в её экраны` · `сторис <id>: исход <имя> ссылается на выход экрана вне сторис` |

## Правила страничного канала

Правила страничного канала (`dmg-ui/web-ui`, `PageGraphProvider`). Читают рёбра `entry`, `opens`, узлы `pageRoute` и `screen`; из свойств узла `screen` — только `params`. Образец для правил канала — [гайд по пакету канала](../guides/channel-package.md).

| ID | Правило | Срабатывает, если | Текст нарушения |
|---|---|---|---|
| PG-01 | Маршрут ведёт на вход, который объявило приложение UI | у узла `pageRoute` нет ребра `opens` | `маршрут <id>: вход <имя входа> не объявлен приложением`; если свойства узла не по схеме — `маршрут <id>: свойства узла не по схеме` |
| PG-02 | У каждого входа приложения есть маршрут | экран, на который ведёт ребро `entry` приложения, не открыт ни одним маршрутом под приложением (`opens`) | `вход приложения <app>: экран <экран> не открыт ни одним маршрутом` |
| PG-03 | Шаблон пути маршрута — по синтаксису | нет `/` в начале, пустой сегмент, неизменяемый сегмент вне `[a-z0-9-]+`, имя параметра не по форме, повтор параметра | `маршрут <id>: <причина>` (причина — из `PagePath.read`: `шаблон пути «<path>» не начинается с /`, `сегмент «<сегмент>» шаблона пути «<path>» не по форме: [a-z0-9-]+ или :имя`, `параметр <имя> повторён в шаблоне пути «<path>»`) |
| PG-04 | Маршруты приложения не совпадают на одном URL | у двух маршрутов одного приложения шаблоны пересекаются: одна длина, в каждой позиции равные неизменяемые сегменты либо параметр (в том числе равные пути) | `приложение <app>: маршруты <id1> и <id2> совпадают на одном URL: <path1> и <path2>` — на каждую пару |
| PG-05 | Параметр пути объявлен экраном входа | имя параметра пути не входит в параметры экрана входа маршрута (остальные параметры экрана идут строкой запроса) | `маршрут <id>: параметр пути <имя> не объявлен экраном входа <экран>` |
| PG-06 | Маршрут не пересекается с общим путём экрана | шаблон маршрута совпадает с общим путём `/<модуль>/<экран>` какого-либо экрана набора | `маршрут <id>: шаблон <path> совпадает с общим путём экрана <экран> (<общий путь>)` — на каждый экран |
| PG-07 | Экран набора выражается в URL | имя модуля или экрана вне `[A-Za-z][A-Za-z0-9]*`; имя параметра не по форме; вид параметра не строка, целое или булево (массив, объект, объединение, `null`, константа, дробное) | `имя <имя> не годится для общего пути экрана <экран>: буква, затем буквы и цифры` · `имя параметра <имя> экрана <экран> не выражается в URL` · `параметр <имя> экрана <экран> не выражается в URL: нужна строка, целое или булево` |

## Правила общей части мессенджеров

Правила общей части мессенджеров (`dmg-ui/chat-ui`, `ChatGraphProvider`). Возможности мессенджера приложения читаются из свойств узла `chatMessenger` под приложением (схема `MessengerCapabilitiesSchema`), цели показа — из рёбер `presents`, подписи ссылок уведомления — из `label` экранов-целей рёбер `links`; CH-02 читает только узлы `chatEntry`, `chatEntryPoint` и рёбра `chatOpens`, свойств не трогает. CH-03 читает узлы `chatSignal`, `chatReaction` и `chatMessenger` прямо под приложением ([D-UI-60](../decisions.md)). Примеры собирает `ChatExamples.collect` до сборки графа ([D-UI-58](../decisions.md)). В текстах `<app>` — `id` приложения UI, `<n>` и `<m>` — номера сообщения показа и варианта с 1, `<лимит>` — `text` или `textWithOptions`, `<длина>`, `<предел>`, `<единица>` — из возможностей мессенджера; у CH-03 `<id>` — `id` узла сигнала или реакции, `<вид>` и `<операция>` — из его свойств, `<name>` — имя мессенджера из возможностей.

| ID | Правило | Срабатывает, если | Текст нарушения |
|---|---|---|---|
| CH-01 | Пример экрана и уведомления укладывается в лимиты мессенджера своего приложения | показ примера экрана (с «Назад», сборщиком показа), подогнанный стражем лимитов без лимита числа вариантов, обрезал бы текст сообщения (последнее с вариантами — по `textWithOptions`, остальные — по `text`) или подпись варианта (`options.label`); текст уведомления длиннее `text` (без ссылок) или `textWithOptions` (со ссылками), подпись экрана-цели ссылки длиннее `options.label`, ссылок уведомления больше `options.max` (беседа их не раскладывает — лишние отбросит страж); представление бросило или вывело показ не по правилам сборщика | `приложение <app>: экран <id>, пример <имя>: сообщение <n> длиннее лимита <лимит> (<длина> из <предел> <единица>)`; `…: сообщение <n>, вариант <m>: подпись длиннее лимита (…)`; `приложение <app>: уведомление <id>, пример <имя>: текст длиннее лимита <лимит> (…)`; `…: ссылка на <id экрана>: подпись длиннее лимита (…)`; `…: ссылок больше лимита (<n> из <max>)`; `…, пример <имя>: представление не собрало показ`; свойства `chatMessenger` не по схеме — `приложение <app>: возможности мессенджера не по схеме` |
| CH-02 | У каждого входа беседы приложения есть точка входа | у узла `chatEntry` под приложением UI нет входящего ребра `chatOpens` от узла `chatEntryPoint` под тем же приложением | `вход <имя> приложения <app>: нет точки входа` (имя входа — из `id` узла `chatEntry`) |
| CH-03 | Сигнал или реакция сообщества — только в приложении мессенджера, который их умеет | у узла `chatSignal` прямо под приложением UI вид сигнала (`signal`) не входит в `community.signals` возможностей мессенджера приложения (свойства узла `chatMessenger` под тем же приложением); у узла `chatReaction` операция (`operation`) не входит в `community.operations`; у приложения с сигналом или реакцией нет узла `chatMessenger` | `приложение <app>: сигнал <id> (<вид>) — мессенджер <name> его не принимает`; `приложение <app>: реакция <id> (<операция>) — мессенджер <name> её не исполняет`; нет мессенджера — `приложение <app>: сигнал <id> — у приложения нет мессенджера` (у реакции — `реакция <id>`) |

## Правила Telegram

Правила пакета Telegram (`dmg-ui/tg-bot`, `TelegramGraphProvider`, [D-UI-64](../decisions.md)). Область — приложения UI, у которых прямо под узлом лежит `chatMessenger` с именем `telegram`; приложения других мессенджеров правила не видят. Правила читают узлы `chatEntryPoint` (`entry`, `via`, `key`), `chatEntry` (название входа — `label` узла) и `chatMessenger`; `check` не бросает. В текстах `<app>` — `id` приложения UI, `<id>` — `id` узла точки (`<app>/point-<вход>-<n>`).

| ID | Правило | Срабатывает, если | Текст нарушения |
|---|---|---|---|
| TG-01 | Способ точки входа известен Telegram | `via` не `command`, `menu`, `link` | `точка <id>: способ «<via>» неизвестен Telegram (command, menu, link)` |
| TG-02 | Ключ точки — по правилам Bot API | у `command` и `menu` ключ не `[a-z0-9_]{1,32}`; у `link` не `[A-Za-z0-9_-]{1,64}` | `точка <id>: ключ «<key>» не по правилам Bot API (<формат>)` |
| TG-03 | Ключ ведёт на один вход | в приложении один и тот же ключ задан дважды (`command` и `menu` — одно пространство, `link` — своё) | `приложение <app>: <команда\|ссылка> «<key>» объявлена дважды (<id1>, <id2>)` |
| TG-04 | Команда не занимает имя беседы | ключ `command` или `menu` — `cancel` или `back` | `точка <id>: команда «<key>» занята беседой (cancel, back)` |
| TG-05 | Новичок попадает в бота | у приложения есть вход и нет точки `command` или `menu` с ключом `start` (кнопка «Запустить» в пустом чате шлёт `/start`) | `приложение <app>: нет точки входа для /start` |
| TG-06 | Меню укладывается в Bot API | точек `menu` больше 100 или название входа (описание команды) вне 1–256 знаков UTF-16 | `приложение <app>: в меню <n> команд из 100`; `точка <id>: описание команды «<key>» (название входа <entry>) вне 1–256 знаков` |

## Ограничения правил

Что правило не проверяет сознательно. Это не долг, а граница правила.

- **Кто что пропускает:** PG-04, PG-05 и PG-06 пропускают маршрут с невалидным шаблоном (его называет PG-03); PG-05 — маршрут без ребра `opens` (его называет PG-01) и экран входа с замечаниями PG-07 о параметрах; PG-06 — экран с именем модуля или экрана не по форме (его называет PG-07). PG-04 сверяет маршруты внутри одного приложения.
- **PG-05…PG-07 читают только `params` узла `screen` и не видят `transform`:** JSON Schema его от входного типа не отличает. Круг «адрес → URL → адрес» на примерах — бросок сборки `PageUrls`, правила нет (DEBT-UI-34). Экраном правила читают только узел `screen` с `id` ровно из трёх сегментов (`<набор>/<модуль>/<экран>`); иной узел вида `screen` пропускается молча. PG-07 работает по всем экранам набора, в том числе нужным только другим каналам: сборка клиента бросит на любом.
- **UI-14 не обходит `anyOf` и `oneOf`.** Обход идёт по `properties` и `items`. Поля внутри `nullable`, объединений и вариантов схемы без `description` правило не заметит.
- **UI-12 смотрит только узлы ядра** (экран, действие, уведомление). Узлы каналов вправе вызывать служебные UC (`visible: false`), например читать данные для сигнала канала. Узлы канала ядра (`ChannelNode` в `UiServerSpec.nodes`, подписка `UiSession.on`) в граф не попадают: их `uses` и `listens` правила не видят. У мессенджеров сигналы и реакции — узлы поставщика `chatSignal` и `chatReaction` (CH-03, D-UI-60); прочему каналу узлы в граф ставит только его поставщик — тогда по их рёбрам действуют UI-10 и UI-11 (D-UI-30).
- **UI-10 дублирует UI-08 для узлов ядра.** Правило нужно для узлов каналов: узел, привязанный к событию, не вызывает command UC ни по `reads`, ни по `invokes`.
- **UI-11 считает вызовом любое ребро `reads` или `invokes`** к UC, в том числе от узла канала, хотя текст говорит об экране.
- **UI-15 пропускает все внешние концы: базовые ошибки ядра и ошибки вне домена.** Они не узлы графа и есть у любого UC, поэтому экран без UC тоже вправе их перехватить. Ошибку вне домена ловит UI-22.
- **UI-18 для `from: 'query'` не сверяет ключи `input` со схемой входа UC и `fields` с выходом UC.** Проверяются только поля payload события, тип UC (query) и `system` в его `callers`.
- **UI-03 допускает переход между экранами общей сторис и переход от экрана-входа.** Меню ведёт на экраны разных сторис, общей сторис с ними у него нет. Переход на экран без общей сторис не из входа — нарушение; выход за пределы приложения — UI-05.
- **UI-20 строит `UiIds` внутри `check`.** К этому моменту граф уже собран, повтор `id` поймал бы поставщик (`GraphError` → ARC-13 «граф не собран»), поэтому правило не бросает.
- **CH-01 не меряет раскладку вариантов экрана.** Число вариантов показа экрана сверх `options.max` раскладывает беседа — страницами с «Ещё» или номерами в тексте вопроса; подпись «Ещё» и номера в тексте правило не видит.
- **CH-01 не меряет ссылки вариантов.** Варианты меряются по подписи, ссылки — заглушки: длину ссылок держит таблица ссылок беседы.
- **CH-01 меряет один контекст рендера** — тот, в котором собраны примеры (по умолчанию без заместителя и без «только чтение»). Шапка заместителя удлиняет первое сообщение и правилом не меряется.
- **CH-01 видит текст уведомления строкой.** Представление уведомления возвращает строку, разметки и стилей у текста нет — мера идёт по `TextBuilder.of(text)`, как у беседы.
- **CH-01 меряет только примеры по схеме.** Пример не по схеме `ChatExamples.collect` пропускает: нарушение даёт UI-20.
- **CH-01 берёт цели только из рёбер `presents` прямо от узла приложения.** UI-06 принимает `presents` и от узла под приложением, и на набор; такие рёбра CH-01 не видит. Цель `presents` без представления в реестре приложения CH-01 не меряет и молчит: свои рёбра поставщик строит из того же реестра.
- **CH-01 не меряет заметку перед видом.** Текст, который беседа ставит первым абзацем перед показом экрана (`lead`, например текст выхода сторис перед видом входа), в показ сборщика не входит и правилом не меряется.
- **Дефект кода экрана при превью — бросок сборки, а не строка CH-01.** Код экрана примера, бросивший в `ScreenPreview`, отклоняет `ChatExamples.collect`: падает сборка `ArchApp` с графом, отчёт не появляется. Строку «представление не собрало показ» даёт только представление беседы.
- **Охват CH-01 и CH-02 разный.** CH-01 смотрит приложения спеки поставщика (узел `chatMessenger` и реестр из спеки), CH-02 — все узлы приложений UI графа, в том числе без `chatMessenger`.
- **CH-02 видит только `chatEntry` прямо под узлом приложения UI.** Узел `chatEntry` в корне графа или под другим узлом правило не проверяет и строки о нём не даёт.
- **CH-02 не проверяет `via` и `key` точки входа.** Значения — слова пакета мессенджера: есть ли такой способ у мессенджера, верен ли ключ (команда, ссылка, кнопка) — дело правил пакета мессенджера. Точку на вход, которого нет у приложения, правило не видит: такую точку не принимает конструктор `ChatGraphProvider` (бросок сборки).
- **CH-03 не видит порта сообщества.** Правило сверяет узлы со списками возможностей мессенджера; есть ли у мессенджера порт `community`, проверяет сборка исполнителя `Communities` (D-UI-59), а не граф.
- **`arch:check` зелёный там, где старт исполнителя сообщества упадёт.** Сборка `Communities` бросает на реакцию с `inviteLink` (DEBT-UI-25), на UC сигнала или реакции без `system` в `callers`, на UC сигнала не command, на пределы `limit` не по правилу и на реакции без порта сообщества; граф этого не видит, правила для этого нет — ловит тест сборки приложения мессенджера.
- **CH-03 молчит при свойствах не по схеме.** Возможности `chatMessenger` не по схеме — строку даёт CH-01 («возможности мессенджера не по схеме»); у узла `chatSignal` или `chatReaction` не по схеме строки о нём нет: свои узлы поставщик ставит по схеме вида, другой граф сборщик не соберёт.
- **CH-03 видит только узлы прямо под узлом приложения UI.** Узел `chatSignal` или `chatReaction` в корне графа или под другим узлом правило не проверяет; узел другого поставщика прямо под приложением — проверяет (реестр видов общий).
- **Поля `input` и `targets` манифестов сообщества не сверяются со схемами** входа и выхода UC и с payload события — как у UI-18 (DEBT-UI-4). Сборка (`CommunityManifest`) проверяет только, что они не пусты; реакцию на command UC ловит UI-10, тип UC сигнала граф не проверяет — это делает сборка исполнителя.
- **Возможности, не годные беседе** (`options.max < 3`, `options.ref < 16`), ловит сборка `Conversations` при старте, а не граф: отдельного правила нет.
- **TG-правила видят только узлы прямо под узлом приложения UI и только приложения с `chatMessenger` `telegram`.** Приложение без узла мессенджера в графе, приложения других мессенджеров и узлы точек в корне графа правила не проверяют; точка с неверными свойствами пропускается молча.
- **TG-02 не знает о регистре входящих команд.** Bot API его не оговаривает; пакет приводит имя входящей команды к нижнему регистру, ключ `command` и `menu` обязан быть строчным.
- **TG-03 называет узлы в порядке `id`, не таблицы.** Граф хранит узлы отсортированными, порядок записей таблицы правилу недоступен.
- **TG-06 меряет в UTF-16.** Единица длины описания команды в Bot API не названа — берётся строгая; повтор ключа `menu` считается точкой (его ловит TG-03), `TelegramMenu` публикует команду один раз.
- **Схема, не переводимая в JSON Schema** (например `v.date()`), роняет сборку графа исключением, а не нарушением правила: это ошибка программиста.

## Проверки репо

Правила разработчика пакета `dmg-ui`, потребителю они не видны. Лежат в `checks/`, выполняются в `bun test` и называют нарушение файлом и строкой.

| Проверка | Что проверяет |
|---|---|
| `PackageDirections` | направления между пакетами-каталогами `packages/*` (таблица: `core` — без соседей, `chat-ui` → `core`, `tg-bot` → `core`, `chat-ui`, `web-ui` → `core`; пакет вне таблицы — нарушение); относительный импорт не выходит из каталога пакета; соседа импортируют по имени входа из `exports`, а не по пути; внутри каталога входа его собственное имя не импортируют |
| `CoreImportScanner` | импорты по зонам: ядро (`src/`, без `graph/` и `server/`) — только `valibot` и `dmg-core`, без `node:`, `bun:`, встроенных модулей и тестовых входов; граф — плюс `dmg-core/graph`; сервер — плюс `dmg-core/app` и `dmg-core/graph`, без графа ядра; учебный пример — только `valibot`, `dmg-core`, `dmg-ui` и контракты `dmg-core/testing/example`. Пакеты каналов: `chat-ui/src` — публичные входы ядра без тестовых, относительные только внутри `packages/chat-ui/src`; `chat-ui/testing` — плюс `dmg-core/arch`, `dmg-core/testing`, `dmg-core/testing/example`, `dmg-ui/testing` и `dmg-ui/chat-ui`; `tg-bot/src` — как `chat-ui/src` плюс `dmg-ui/chat-ui`, внешних библиотек (в том числе `grammy`) нет. `tg-bot/testing` — как `chat-ui/testing` плюс `dmg-ui/chat-ui/testing` и `dmg-ui/tg-bot`. `web-ui/src` — как `chat-ui/src` без `dmg-core/app`: клиент не знает сервер и граф, но видит представления `view/`; представления `web-ui/src/view/` — только `valibot`, `dmg-core`, `dmg-ui`, относительные только внутри `view/` (ни клиента, ни провода, ни сервера, ни графа); провод не знает ни клиента, ни сервера, сервер не знает клиент и граф, граф не знает сервер, провод и клиент — реестр представлений берёт из `view/` ([D-UI-70](../decisions.md)); кодек адреса `web-ui/src/url/` (маршрут `PageRouteDef` и `PageUrls`) — только `valibot`, `dmg-core`, `dmg-ui`, относительные только внутри `url/`; его видят клиент, граф и корень канала ([D-UI-76](../decisions.md)); `web-ui/testing` — плюс `dmg-core/arch`, `dmg-core/testing`, `dmg-core/testing/example`, `dmg-ui/testing`, `dmg-ui/testing/fixtures` и `dmg-ui/web-ui`. Привязки примера к каналам друг друга не знают. Приёмочный каталог `acceptance/` не ограничен, но в `packages/` заходит только по именам входов из `exports` (`dmg-ui/packages/…` — нарушение). Страж раскладки `CoreImportScanner.scanLayout`: каждый `.ts` пакетов `chat-ui`, `tg-bot` и `web-ui` лежит в `src/` или `testing/`, иначе — нарушение «добавь зону» |
| `ChannelWordScanner` | в `packages/core/src` нет слов канала: сообщение, кнопка, страница, URL, `href`, `http`, мессенджеры, бот, чат; текст режется на слова, сравнение по целым словам (русские — по основе). Список расширяется решением в [decisions.md](../decisions.md). Для `packages/chat-ui` — второй список: названия мессенджеров и их библиотек (`telegram`, `tg`, `whatsapp`, `slack`, `discord`, `viber`, `grammy`, `telegraf`, `baileys`, `twilio`), `webhook`, поля API (`keyboard`, `markup`, `mrkdwn`; русские основы — `телеграм`, `ватсап`, `вотсап`, `слак`, `клавиатур`); общие слова (сообщение, кнопка, чат, бот) в `chat-ui` разрешены. Для `packages/web-ui` (весь каталог, с тестами) — третий список: названия фреймворков (`svelte`, `sveltekit`, `sveltejs`, `react`, `reactjs`, `preact`, `vue`, `vuejs`, `nuxt`, `nextjs`, `solidjs`, `angular`, `lit`, `jsx`, `htmx`, `alpine`, `jquery`, `qwik`) и мессенджеров (`telegram`, `tg`, `whatsapp`, `slack`, `discord`, `viber`; русские основы — `телеграм`, `ватсап`, `вотсап`, `слак`, `дискорд`, `вайбер`); русских основ фреймворков нет, «реактивность» разрешена; `solid-js` через дефис не ловится (части — «solid» и «js»), общие слова канала (страница, URL) тоже ([D-UI-70](../decisions.md)). `packages/tg-bot` сканером не проверяется |
| `NetworkGlobalScanner` | в `packages/tg-bot/src` (кроме `.test.ts`) нет глобалов сети и среды `fetch`, `WebSocket`, `XMLHttpRequest`, `EventSource`, `Bun`, `process`: сеть и библиотеку даёт проект через порт Bot API, импорт закрывает `CoreImportScanner`, а глобал импортом не ловится; нарушение — отдельный идентификатор или доступ через `globalThis`, `window`, `self`, член объекта и часть имени — нет; комментарии и строки тоже проверяются ([D-UI-61](../decisions.md)) |
| `BrowserGlobalScanner` | глобалы браузера (`WebSocket`, `XMLHttpRequest`, `EventSource`, `localStorage`, `navigator`, `window.<член>`, `document.createElement`, `history.pushState`, `location.href`, `globalThis.window`, `self.document`, обращение по ключу `window['document']`, деструктуризация из `window`, `globalThis`, `self` и подобные) в `packages/**` и `examples/**` (кроме `.test.ts`) только в клиенте `packages/web-ui/src/client/` и в `examples/web/`; глобалы среды `Bun` и `process` (в том числе `globalThis.process`, `globalThis['Bun']`) — нигде в `packages/web-ui/src/` (кроме `.test.ts`): сервер говорит с соединением через порт, клиент выполняется в браузере; голые `window`, `document`, `history`, `location` ловятся только по форме использования; не ловятся члены `document` вне списка, алиасы (`const w = window`) и вычисляемые ключи; комментарий с `window.x` вне клиента — нарушение; `fetch` не ловится (в `tg-bot` его закрывает `NetworkGlobalScanner`) |
| `ExampleZoneScanner` | библиотека Telegram (`grammy`, её подпути, `@grammyjs/*`) импортируется только в `examples/tg-bot/src/grammy-bot-api.ts`, `grammy-polling.ts`, их тестах и файлах типов `*.types.ts`; адаптеры по относительному пути берут только `main.ts`, `probe.ts` и тесты; файлы `examples/*` не выходят за каталог своего примера ни относительным, ни абсолютным путём; динамический `import(переменная)` не ловится ([DEBT-UI-5](../../debt.md)) |
| `BotTokenScanner` | в текстовых файлах репо (`.ts`, `.md`, `.json`, `.sh`, `.example`, `.snap`) нет токена бота по форме BotFather (8–10 цифр, двоеточие, 35 знаков), текст нарушения токена не содержит; `.gitignore` исключает `.env`; токен другой формы или разорванный не ловится |

Вспомогательные проверки: `ModuleSpecifiers` (поиск спецификаторов импорта регулярным выражением; ограничение — [DEBT-UI-5](../../debt.md)), `RuleCatalog` (правила в коде и в этом каталоге совпадают, каждое `D-UI-N` определено в решениях, «Последний выданный ID» в реестре долга равен максимуму), `DocsLinkChecker` (относительные ссылки документов ведут на существующие файлы и заголовки), `TrackReferenceScanner` (в коде и документах нет ссылок на локальную историю разработки).
