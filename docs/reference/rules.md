# Каталог правил

**Назначение:** проверяемые правила графа UI, слоёв фронта и имён файлов UI. Правило графа — тип `GraphRule` (`dmg-core/graph`): получает собранный граф и возвращает строки нарушений. Правило слоя фронта (UI-28…UI-34) — ID слоя или доступа, который объявляет `UiGraphProvider.layers()`: импорты файлов проверяет `arch:check` `dmg-core`, граф правило не читает. В отчёте `arch:check` строка выходит как `<ID>: <текст>`. Правило имён файлов (`NM`) графа не читает: его проверяет класс `UiFileNames` в тесте потребителя (`bun test`), а не `arch:check`. UI-06 и CH-01 граф не читают — раздел [«Проверки единицы»](#проверки-единицы). Правило меняется только через [decisions.md](../decisions.md).

**Серия:** `UI-<n>`, `PG-<n>`, `CH-<n>`, `TG-<n>`, `NM-<n>`

Префиксы: `UI` — правила ядра, слоёв фронта (`UiGraphProvider`, вход `dmg-ui/graph`) и полноты реестров (`UiCompleteness`), `PG` — правила страничного канала `web-ui` (`PageGraphProvider`, вход `dmg-ui/web-ui`), `CH` — правила общей части мессенджеров (`ChatGraphProvider`, вход `dmg-ui/chat-ui`) и лимиты примеров (`ExampleLimits`, вход `dmg-ui/chat-ui/testing`), `TG` — правила Telegram (`TelegramGraphProvider`, вход `dmg-ui/tg-bot`), `NM` — имена и раскладка файлов UI (проверка `UiFileNames`, вход `dmg-ui/testing`; тест, не правило графа, [D-UI-112](../decisions.md)). У каждого пакета канала свой префикс, и принадлежит он одному поставщику; он не совпадает с префиксами `dmg-core` и с `UI` (ARC-13, см. [D-UI-13](../decisions.md), [D-UI-57](../decisions.md)). Список префиксов репо держит проверка `RuleCatalog` (`RULE_PREFIXES`): новый префикс добавляется туда тем же коммитом, что и первое правило. Как собрать правила своего канала — `node_modules/dmg-core/docs/guides/graph-extension.md`.

Правила читают только граф: схемы `params`, `state`, `input` и данные выходов лежат в свойствах узлов как JSON Schema. Исключения — UI-20 и UI-38: примеры проверяются схемами valibot, а схемы данных экрана в свойствах узла нет, поэтому правило получает набор UI в конструктор.

В текстах нарушений `<id>` — `id` узла графа (`<набор>/<модуль>/<имя>` у экрана, сторис и уведомления, `<экран>/<действие>` у действия, имя приложения UI у приложения).

## Сторис, переходы, достижимость

| ID | Правило | Срабатывает, если | Текст нарушения |
|---|---|---|---|
| UI-01 | Вызывающие сторис допущены к каждому UC её экранов | в `callers` сторис есть вызывающий, которого нет в `callers` UC (`reads` экрана или `uc` его действия) | `сторис <id>: вызывающий «<caller>» не допущен к UC <uc> экрана <экран>` |
| UI-02 | Экран входит хотя бы в одну сторис | у экрана нет ни одного ребра `includes` от сторис | `экран <id> не входит ни в одну сторис` |
| UI-03 | У экрана и цели перехода есть общая сторис или цель — старт связанной сторис | действие ведёт (`leadsTo`) на экран, у которого с экраном-источником нет общей сторис и который не `start` сторис из связей (`leads`) сторис экрана-источника; экран-вход приложения UI не исключение ([D-UI-96](../decisions.md)) | `действие <id> ведёт на экран <цель>, с которым у экрана нет общей сторис и который не старт сторис из связей сторис` |
| UI-04 | Каждый выход экрана связан с исходом | у сторис, включающей экран, ни один исход не ссылается на выход экрана | `выход <имя> экрана <экран> не связан с исходом сторис <сторис>` |
| UI-05 | Переход, вход приложения и цель исхода ведут на экран его сторис | переход действия, вход приложения (`entry`) или цель-адрес исхода сторис приложения (свойство `after`, ребро `redirects`) указывает на экран вне сторис приложения; переход не нарушение, если ветка отрезана: цель — `start` сторис из связей сторис приложения с экраном-источником, которой в приложении нет (ребро `omits`) | `приложение <app>: экран <экран> ведёт на <цель>, которого нет в его сторис и не заявлен в связях сторис`, `приложение <app>: вход ведёт на <цель>, которого нет в его сторис` и `приложение <app>: сторис <id> направляет исход <имя> на <экран>, которого нет в его сторис` |
| UI-07 | Каждый экран приложения достижим от входов | экран не достигается от целей `entry` и ссылок `links` уведомлений приложения по переходам действий и целям-адресам исходов (`redirects`) сторис приложения с достигнутым экраном | `приложение <app>: экран <id> недостижим от входов` |
| UI-24 | Связь сторис подтверждена переходом | у сторис есть ребро `leads` к сторис, на стартовый экран которой не ведёт (`leadsTo`) ни одно действие экранов сторис-источника | `сторис <id>: связь с <сторис> не подтверждена переходом на её стартовый экран <экран>` |
| UI-25 | Выход экрана ведёт к одной цели во всех сторис приложения | выход экрана лежит в исходах нескольких сторис приложения, и цели этих исходов (свойство `after`: `back`, `home` или адрес) различаются ([D-UI-96](../decisions.md)) | `приложение <app>: выход <имя> экрана <экран> привязан к исходам сторис <а>, <б> с разными целями` |
| UI-35 | Сторис включает только экраны своего модуля | ребро `includes` от сторис ведёт к экрану другого UI-модуля ([D-UI-119](../decisions.md)) | `сторис <id>: экран <экран> из модуля <m> — сторис включает только экраны своего модуля` |
| UI-36 | Цель исхода и ссылка уведомления в чужой модуль — только `start` его сторис | цель-адрес исхода (свойство `after`, ребро `redirects`) или ссылка уведомления (`links`) ведёт на экран другого UI-модуля, который не `start` ни одной сторис этого модуля; переход действия держат UI-03 и UI-35 | `сторис <id> направляет исход <имя> на <экран> модуля <m>: в чужой модуль — только start его сторис` · `уведомление <id>: ссылка на <экран> модуля <m> — в чужой модуль только start его сторис` |
| UI-37 | Во вспомогательный модуль ведут не меньше двух модулей | модуль вспомогательный (тот же признак, что `section`): в каждую его сторис ведёт `leads` не корневой сторис — другого модуля или своего, а модулей-источников (другие модули не корневых сторис, ведущих в него) меньше двух; переходы из корневых сторис набора (меню — сторис, в которую не ведёт ни одна `leads` набора) не учитываются ни для вида модуля, ни в подсчёте | `модуль <id>: вспомогательный, в него ведёт только <источник> — сторис у единственного пользователя` · `модуль <id>: вспомогательный, в него не ведёт ни один модуль` |

| UI-18 | Получатели уведомления заданы и согласованы с событием | список полей получателей пуст; поле (из `payload` — `fields`, из `query` — значения `input`) не входит в payload события; для `from: 'query'` UC получателей не query или у него нет `system` в `callers` | `уведомление <id>: список получателей пуст` · `… поля <поле> нет в payload события <событие>` · `… UC получателей <uc> — не query` · `… в callers UC получателей <uc> нет system` |
| UI-19 | `params` и `state` строгие, `input` — объект | схема `params` или `state` экрана без `additionalProperties: false`; схема `input` действия — не объект | `экран <id>: схема <params\|state> не строгая (strictObject)` · `действие <id>: схема input не объект` |
| UI-20 | Примеры проходят схемы своего экрана или уведомления | пример экрана не проходит `params`, `data` или `state`; пример уведомления — `data` | `<id>: пример <имя> не по схеме <params\|data\|state>: <сообщение valibot>` |
| UI-21 | Имена действий и локальных действий не пересекаются | одно имя есть и в `actions`, и в `locals` экрана | `экран <id>: имя <имя> и у действия, и у локального действия` |

| UI-23 | Форма сторис: `start` и выходы исходов принадлежат её экранам | `start` не входит в экраны сторис; исход ссылается на выход экрана вне сторис | `сторис <id>: start <экран> не входит в её экраны` · `сторис <id>: исход <имя> ссылается на выход экрана вне сторис` |
| UI-38 | Форма действия строки | у действия с `row`: путь `list` не ведёт к полю данных экрана (через `properties`, необязательные родители допустимы) или ведёт не к массиву; элемент списка не объект (в том числе `anyOf`); у элемента нет поля `key` или оно не строка, число или булево; поле `label` не строка; у `input` не ровно одно поле; действие строки — основное (`primary`); на одном списке экрана больше одного действия строки. Схема данных нормализуется только у экранов с действием строки ([D-UI-129](../decisions.md)) | `действие <id>: пути <list> нет в данных экрана` · `действие <id>: путь <list> ведёт не к массиву` · `действие <id>: элемент списка <list> не объект` · `действие <id>: у элемента списка <list> нет поля ключа <key>` · `действие <id>: поле ключа <key> элемента списка <list> не строка, число или булево` · `действие <id>: поле подписи <label> элемента списка <list> не строка` · `действие <id>: действие строки не может быть основным` · `действие <id>: у входа действия строки полей <n>, нужно одно` · `экран <id>: на списке <list> несколько действий строки (<имена>), допустимо одно` |

## Слои фронта

Правила слоёв проверяет `arch:check` `dmg-core` по слоям, которые объявляет `UiGraphProvider.layers()` ([D-UI-117](../decisions.md)): каналы проекта (имя и база) — параметр поставщика, каталоги слоёв — `ArchApp.layers` проекта. Текст нарушения — от проверяющего слоёв `dmg-core`: `<файл>` — путь от `ArchApp.project`, `<слой>[ <модуль>]` — слой цели и её модуль. Формы «… импортирует файл вне слоёв» и «… мимо <вход>.ts» даёт любой слой-импортёр, в таблице они показаны у одного правила для примера.

## Правила страничного канала

Правила страничного канала (`dmg-ui/web-ui`, `PageGraphProvider`). Читают рёбра `entry`, `opens`, узлы `pageRoute` и `screen`; из свойств узла `screen` — только `params`. Образец для правил канала — [гайд по пакету канала](../guides/channel-package.md); страничные правила и их место в канале — [Web-канал](../guides/web-channel-checks.md#11-граф-и-правила-pg-01pg-07), раздел 11.

| ID | Правило | Срабатывает, если | Текст нарушения |
|---|---|---|---|
| PG-01 | Маршрут ведёт на вход, который объявило приложение UI | у узла `pageRoute` нет ребра `opens` | `маршрут <id>: вход <имя входа> не объявлен приложением`; если свойства узла не по схеме — `маршрут <id>: свойства узла не по схеме` |
| PG-02 | У каждого входа приложения есть маршрут | экран, на который ведёт ребро `entry` приложения, не открыт ни одним маршрутом под приложением (`opens`) | `вход приложения <app>: экран <экран> не открыт ни одним маршрутом` |
| PG-03 | Шаблон пути маршрута — по синтаксису | нет `/` в начале, пустой сегмент, неизменяемый сегмент вне `[a-z0-9-]+`, имя параметра не по форме, повтор параметра | `маршрут <id>: <причина>` (причина — из `PagePath.read`: `шаблон пути «<path>» не начинается с /`, `сегмент «<сегмент>» шаблона пути «<path>» не по форме: [a-z0-9-]+ или :имя`, `параметр <имя> повторён в шаблоне пути «<path>»`) |
| PG-04 | Маршруты приложения не совпадают на одном URL | у двух маршрутов одного приложения шаблоны пересекаются: одна длина, в каждой позиции равные неизменяемые сегменты либо параметр (в том числе равные пути) | `приложение <app>: маршруты <id1> и <id2> совпадают на одном URL: <path1> и <path2>` — на каждую пару |
| PG-05 | Параметр пути объявлен экраном входа | имя параметра пути не входит в параметры экрана входа маршрута (остальные параметры экрана идут строкой запроса) | `маршрут <id>: параметр пути <имя> не объявлен экраном входа <экран>` |
| PG-06 | Маршрут не пересекается с общим путём экрана | шаблон маршрута совпадает с общим путём `/<модуль>/<экран>` какого-либо экрана набора | `маршрут <id>: шаблон <path> совпадает с общим путём экрана <экран> (<общий путь>)` — на каждый экран |
| PG-07 | Экран набора выражается в URL | имя модуля или экрана вне `[A-Za-z][A-Za-z0-9]*`; имя параметра не по форме; вид параметра не строка, целое или булево (массив, объект, объединение, `null`, константа, дробное) | `имя <имя> не годится для общего пути экрана <экран>: буква, затем буквы и цифры` · `имя параметра <имя> экрана <экран> не выражается в URL` · `параметр <имя> экрана <экран> не выражается в URL: нужна строка, целое или булево` |

## Ограничения правил

Что правило не проверяет сознательно. Это не долг, а граница правила.

- **Кто что пропускает:** PG-04, PG-05 и PG-06 пропускают маршрут с невалидным шаблоном (его называет PG-03); PG-05 — маршрут без ребра `opens` (его называет PG-01) и экран входа с замечаниями PG-07 о параметрах; PG-06 — экран с именем модуля или экрана не по форме (его называет PG-07). PG-04 сверяет маршруты внутри одного приложения.
- **PG-05…PG-07 читают только `params` узла `screen` и не видят `transform`:** JSON Schema его от входного типа не отличает. Круг «адрес → URL → адрес» на примерах — бросок сборки `PageUrls`, правила нет (DEBT-UI-34). Экраном правила читают только узел `screen` с `id` ровно из трёх сегментов (`<набор>/<модуль>/<экран>`); иной узел вида `screen` пропускается молча. PG-07 работает по всем экранам набора, в том числе нужным только другим каналам: сборка клиента бросит на любом.
- **UI-14 не обходит `anyOf` и `oneOf`.** Обход идёт по `properties` и `items`. Поля внутри `nullable`, объединений и вариантов схемы без `description` правило не заметит.
- **UI-26 не смотрит значения примеров экрана и уведомления и `hint`.** Значения примеров в граф не попадают, подсказка у чувствительного поля допустима. Обход идёт по `properties` и `items`, как у UI-14: `anyOf` и `oneOf` не разбираются, `examples` в узле обёртки (`optional`, `nullable`) правило не видит.
- **UI-27 смотрит только верхний уровень `input`.** `params`, `state` и `data` выходов вне правила: человек их не вводит. `anyOf`, `oneOf` и `$ref` не разбираются. `v.date()` до правил не доходит: бросок `toJsonSchema` при сборке графа — ARC-13 «граф не собран».
- **UI-12 смотрит только узлы ядра** (экран, действие, уведомление). Узлы каналов вправе вызывать служебные UC (`visible: false`), например читать данные для сигнала канала. Узлы канала ядра (`ChannelNode` в `UiServerSpec.nodes`, подписка `UiSession.on`) в граф не попадают: их `uses` и `listens` правила не видят. У мессенджеров сигналы и реакции — узлы поставщика `chatSignal` и `chatReaction` (CH-03, D-UI-60); прочему каналу узлы в граф ставит только его поставщик — тогда по их рёбрам действуют UI-10 и UI-11 (D-UI-30).
- **UI-10 дублирует UI-08 для узлов ядра.** Правило нужно для узлов каналов: узел, привязанный к событию, не вызывает command UC ни по `reads`, ни по `invokes`.
- **UI-11 считает вызовом любое ребро `reads` или `invokes`** к UC, в том числе от узла канала, хотя текст говорит об экране.
- **UI-15 пропускает все внешние концы: базовые ошибки ядра и ошибки вне домена.** Они не узлы графа и есть у любого UC, поэтому экран без UC тоже вправе их перехватить. Ошибку вне домена ловит UI-22.
- **UI-18 для `from: 'query'` не сверяет ключи `input` со схемой входа UC и `fields` с выходом UC.** Проверяются только поля payload события, тип UC (query) и `system` в его `callers`.
- **UI-03 допускает переход между экранами общей сторис и переход на старт сторис из связей сторис экрана.** Экран-вход исключением не служит ([D-UI-96](../decisions.md)): меню — обычная сторис, переходы в чужие сторис объявлены её связями (`leads`). Переход на экран без общей сторис и не на старт связанной сторис — нарушение; выход за пределы приложения — UI-05. Между модулями — вместе с UI-35: общей сторис с экраном чужого модуля нет, поэтому переход в чужой модуль — только на старт сторис из связей.
- **UI-35 и UI-36 пропускают цели вне набора** — их называет UI-22. Вход приложения (`entry`) UI-36 не ограничивает: адрес снаружи вправе открыть любой экран приложения ([D-UI-119](../decisions.md)).
- **UI-37 не считает связи из корневых сторис набора** (меню, [D-UI-96](../decisions.md)): модуль, открытый только из меню, — раздел. Вход из своей сторис модуль разделом не делает: модуль, в одну сторис которого ведёт один другой модуль, а в остальные — его же сторис, — вспомогательный с одним источником, нарушение. Модуль без сторис и модуль, сторис которого ведут только друг в друга, — вспомогательные без источников, нарушение (второй недостижим — UI-07). Свой модуль в источники не идёт, связи на сторис вне набора не в счёт; неподтверждённую переходом связь правило считает как есть — её называет UI-24.
- **UI-05 и UI-24 смотрят только прямые связи.** Отрезанная ветка — сторис из `leads` сторис приложения, включающей экран-источник; связь связи (дальняя) переход не оправдывает. UI-24 не требует перехода из каждого экрана источника: хватает одного действия любого экрана сторис на `start` цели; цель связи вне графа UI-24 пропускает — её называет UI-22.
- **UI-07 считает цель-адрес исхода достигнутой, когда достигнут любой экран сторис,** а не именно экран выхода исхода: исходы в графе ссылаются на выходы, но замыкание идёт по экранам.
- **UI-25 сравнивает цели как JSON свойства `after`.** Адреса с одинаковыми параметрами в другом порядке ключей — разные цели. Правило смотрит только сторис приложения (сторис набора вне приложения не в счёт) и только выходы, лежащие в исходах; выход без исхода называет UI-04. При расхождении исполнитель (`ExitTargets`) берёт цель первой по порядку сторис приложения.
- **UI-22 о правиле сторис видит только отсутствие узла.** Узел доменного правила ставит поставщик домена, только если правило в `rules` хотя бы одного UC; проверяет ли этот UC экран сторис, правило не сверяет. Правило с ошибкой вне домена даёт строку «ссылается на domainRule … вне набора UI и домена».
- **UI-20 строит `UiIds` внутри `check`.** К этому моменту граф уже собран, повтор `id` поймал бы поставщик (`GraphError` → ARC-13 «граф не собран»), поэтому правило не бросает.
- **CH-01 не меряет раскладку вариантов экрана.** Число вариантов показа экрана сверх `options.max` раскладывает беседа — страницами с «Ещё» или номерами в тексте вопроса; подпись «Ещё» и номера в тексте правило не видит.
- **CH-01 не меряет ссылки вариантов.** Варианты меряются по подписи, ссылки — заглушки: длину ссылок держит таблица ссылок беседы.
- **CH-01 меряет один контекст рендера** — тот, в котором собраны примеры (по умолчанию без заместителя и без «только чтение»). Шапка заместителя удлиняет первое сообщение и правилом не меряется.
- **CH-01 видит текст уведомления строкой.** Представление уведомления возвращает строку, разметки и стилей у текста нет — мера идёт по `TextBuilder.of(text)`, как у беседы.
- **CH-01 меряет только примеры по схеме.** Пример не по схеме `ChatExamples.collect` пропускает: нарушение даёт UI-20.
- **CH-01 меряет модули сборки целиком.** Экраны и уведомления модуля сборки приложения меряются и вне сторис приложения: реестр модуля полон по модулю (UI-06). Модуль вне сборки CH-01 не видит.
- **CH-01 не меряет заметку перед видом.** Текст, который беседа ставит первым абзацем перед показом экрана (`lead`, например текст выхода сторис перед видом входа), в показ сборщика не входит и правилом не меряется.
- **Дефект кода экрана при превью — бросок `ChatExamples.collect`, а не строка CH-01.** Код экрана примера, бросивший в `ScreenPreview`, отклоняет сбор примеров: падает тест единицы. Строку «представление не собрало показ» даёт только представление беседы.
- **Охват CH-01 и CH-02 разный.** CH-01 меряет сборку, которую передал тест, на переданных возможностях; CH-02 — узлы `chatEntry` всех приложений UI графа, в том числе без `chatMessenger`.
- **CH-02 видит только `chatEntry` прямо под узлом приложения UI.** Узел `chatEntry` в корне графа или под другим узлом правило не проверяет и строки о нём не даёт.
- **CH-02 не проверяет `via` и `key` точки входа.** Значения — слова пакета мессенджера: есть ли такой способ у мессенджера, верен ли ключ (команда, ссылка, кнопка) — дело правил пакета мессенджера. Точку на вход, которого нет у приложения, правило не видит: такую точку не принимает конструктор `ChatGraphProvider` (бросок сборки).
- **CH-03 не видит порта сообщества.** Правило сверяет узлы со списками возможностей мессенджера; есть ли у мессенджера порт `community`, проверяет сборка исполнителя `Communities` (D-UI-59), а не граф.
- **`arch:check` зелёный там, где старт исполнителя сообщества упадёт.** Сборка `Communities` бросает на реакцию с `inviteLink` (DEBT-UI-25), на UC сигнала или реакции без `system` в `callers`, на UC сигнала не command, на пределы `limit` не по правилу и на реакции без порта сообщества; граф этого не видит, правила для этого нет — ловит тест сборки приложения мессенджера.
- **CH-03 молчит при свойствах не по схеме.** Свои узлы `chatMessenger` поставщик ставит только по схеме: возможности не по схеме — бросок конструктора `ChatGraphProvider` (D-UI-57); узел не по схеме в чужом графе правило пропускает молча. У узла `chatSignal` или `chatReaction` не по схеме строки о нём нет: свои узлы поставщик ставит по схеме вида, другой граф сборщик не соберёт.
- **CH-03 видит только узлы прямо под узлом приложения UI.** Узел `chatSignal` или `chatReaction` в корне графа или под другим узлом правило не проверяет; узел другого поставщика прямо под приложением — проверяет (реестр видов общий).
- **Поля `input` и `targets` манифестов сообщества не сверяются со схемами** входа и выхода UC и с payload события — как у UI-18 (DEBT-UI-4). Сборка (`CommunityManifest`) проверяет только, что они не пусты; реакцию на command UC ловит UI-10, тип UC сигнала граф не проверяет — это делает сборка исполнителя.
- **Возможности, не годные беседе** (`options.max < 3`, `options.ref < 16`), ловит сборка `Conversations` при старте, а не граф: отдельного правила нет.
- **TG-правила видят только узлы прямо под узлом приложения UI и только приложения с `chatMessenger` `telegram`.** Приложение без узла мессенджера в графе, приложения других мессенджеров и узлы точек в корне графа правила не проверяют; точка с неверными свойствами пропускается молча.
- **TG-02 не знает о регистре входящих команд.** Bot API его не оговаривает; пакет приводит имя входящей команды к нижнему регистру, ключ `command` и `menu` обязан быть строчным.
- **TG-03 называет узлы в порядке `id`, не таблицы.** Граф хранит узлы отсортированными, порядок записей таблицы правилу недоступен.
- **TG-06 меряет в UTF-16.** Единица длины описания команды в Bot API не названа — берётся строгая; повтор ключа `menu` считается точкой (его ловит TG-03), `TelegramMenu` публикует команду один раз.
- **NM-01 берёт вид из текста регулярным выражением, без парсера.** Объявлением не считаются: псевдоним базы (`const D = ScreenDef; D.define(...)`), `export default class`, перенос строки или пробел перед `.define` (`ScreenDef\n  .define(`), реэкспорт `export { X }` и `export { X } from '…'`. Наоборот, текст объявления внутри строки или шаблона (`` `export const X = ScreenDef.define(` ``) считается объявлением: комментарии снимаются, строки — нет. Аннотация типа у `const` (`export const X: T = ScreenDef.define(`) не мешает. У видов канала без базы (`.view`, `.views`, `.routes`, `.placements`, `.wire`, `.graph`, `.arch`) вид — только по суффиксу, имя ищется среди экспортов `const`, `let`, `class`, `function`.
- **NM-01 не проверяет `.rule.ts` и `name` манифеста.** `.rule.ts` — внутренность пакета, ID правил сверяет `RuleCatalog`; `name:` регулярное выражение путает со вложенными объектами.
- **NM-01 не видит файлов вне зон конфигурации** и не проверяет вид тестов, `*.fixture.ts` и `*.test-kit.ts`; `*.browser.test.ts` вне проверки теста рядом.
- **NM-01 выводит место экрана только из относительных импортов `.story`.** Псевдоним пути (`from '@app/ui/…'`) и реэкспорт (импорт через `index.ts` модуля или папки) не разрешаются: у такого экрана, как и у экрана, который не открывает ни одна сторис, место не проверяется; импорт экрана из сторис другого модуля в счёт не идёт. Место уведомления внутри модуля не проверяется. Корень зоны кода и канала модуля (вход, реестр, `public.ts`) по составу не проверяется — только виды в нём.
- **Схема, не переводимая в JSON Schema** (например `v.date()`), роняет сборку графа исключением, а не нарушением правила: это ошибка программиста.
