# Виды генератора — гайд

**Назначение:** как получить заготовки UI-модуля, сторис, экрана и уведомления командой `dmg-core gen`: подключение поставщика `dmg-ui`, четыре вида и их аргументы, что каждый создаёт и правит, когда вид отказывает, что остаётся руками, как проверить форму и как написать тест своего вида.

> Источник — виды пакета `packages/gen` и их тесты ([D-UI-123](../decisions.md)); имена, суффиксы и места файлов — [naming.md](../reference/naming.md). Платформа расширения — `node_modules/dmg-core/docs/guides/provider-extension.md` (D-113 `dmg-core`).

---

## 1. Когда применять

Нужен пустой UI-модуль, сторис, экран или уведомление в проекте, где фронт разложен по трём деревьям ([Слои фронта](../concepts/frontend-layers.md)). Вид создаёт файлы всех деревьев по месту из `layers`, дописывает списки модуля и реестры по маркерам и печатает, что осталось руками. Заполнение заглушек — работа автора: вид не знает ни данных экрана, ни событий домена.

Файлы, которых вид не создаёт (набор UI, приложение UI, оболочка раннера, представления каналов без шаблона), пишутся по [naming.md](../reference/naming.md) и [Сторис, экран, уведомление](./story-screen-notification.md#10-добавить-вид-в-учебный-проект).

## 2. Подключение

В `.dmg/config.json` проекта — поставщик и места слоёв:

```json
{
  "providers": ["dmg-ui"],
  "layers": {
    "ui": { "dir": "platform/ui/src", "package": "@acme/ui" },
    "fe-app": { "dir": "frontend/app/src" },
    "fe-logic": { "dir": "frontend/{m}/logic/src", "package": "@acme/fe-{m}" },
    "fe-chat": { "dir": "frontend/{m}/chat/src", "package": "@acme/fe-{m}-chat" },
    "fe-web": { "dir": "frontend/{m}/web/src", "package": "@acme/fe-{m}-web" }
  }
}
```

- `providers: ["dmg-ui"]` — `dmg-core` находит вход `dmg-ui/dmg-core` (D-113 `dmg-core`) и берёт из него виды; тот же список доставляет роль `dmg-ui-author` (`dmg-core sync`).
- `layers` — места слоёв: `dir` с `{m}` (имя модуля) и, по желанию, `package` с `{m}`. Те же каталоги проект отдаёт проверке слоёв в `ArchApp.layers`.
- Нужные слои:

| Слой | Роль | Нужен |
|---|---|---|
| `ui` | описание: Def модуля, сторис, экранов, уведомлений; `index.ts` с маркером `// gen:exports` | всем видам |
| `fe-logic` | код модуля и реестр кода | всем видам |
| `fe-<канал>` | представления канала; `fe-app` и `fe-logic` каналами не считаются | `ui-module` — хотя бы один; остальным — по желанию |
| `package` у слоя | имя пакета единицы выноса | `ui-module` пишет `package.json` для `fe-logic` и каналов с шаблоном, если `package` задан; у `ui` — только имя для импорта описания, `package.json` не пишется |

- Если у слоёв кода или каналов есть `package`, версию `dmg-ui` для пакетов единиц вид читает из `package.json` корня проекта (`dependencies`, затем `devDependencies`) — строка переносится в пакеты как есть.
- Каналы с шаблонами — `chat` (`ChatViews`, `ScreenPresenter`, `NotificationPresenter` из `dmg-ui/chat-ui`) и `web` (`PageViews`, `PagePresenter`, `PageNotePresenter` из `dmg-ui/web-ui`). Новый канал с шаблоном — строка таблицы технологий в коде пакета ([D-UI-123](../decisions.md)).

## 3. Виды

Команда — `bunx dmg-core gen <вид> <аргументы>`: без `--write` — dry-run (печатает файлы и правки, ничего не пишет), с `--write` — записывает. Все имена — kebab-case (`a-z`, `0-9`, дефисы).

| Вид | Аргументы | Что делает |
|---|---|---|
| `ui-module` | `<модуль> [<раннер>…]` | пустой UI-модуль целиком: описание, код, реестры каналов, пакеты единиц; `<раннер>` — каталог раннера от корня проекта |
| `story` | `<модуль> <сторис> <экран>` | сторис с экраном `start` |
| `screen` | `<модуль> <папка> <экран>` | экран; `<папка>` — сторис модуля или `shared` |
| `notification` | `<модуль> <папка> <уведомление>` | уведомление; `<папка>` — сторис модуля или `shared` |

Порядок работы над модулем: `ui-module` → `story` (экран `start` вместе с ней) → `screen` и `notification` по надобности. Имена сторис и экранов в примерах ниже — учебные.

```
bunx dmg-core gen ui-module courses runners/bot
bunx dmg-core gen story courses browse course-list --write
bunx dmg-core gen screen courses browse course-card --write
bunx dmg-core gen notification courses shared course-opened --write
```

### 3.1. `ui-module`

Файлы по деревьям (канал — каждый слой `fe-<канал>` с шаблоном):

- описание: `<ui>/<m>/<m>.ui-module.ts` — `UiModuleDef` со списками `screens`, `stories`, `notifications` и маркерами `// gen:imports`, `// gen:screens`, `// gen:stories`, `// gen:notifications`;
- код: `<logic>/index.ts` и `<logic>/<m>-codes.ts` — реестр `<m>Codes` (`CodeLoaders.of`) с маркерами `// gen:imports`, `// gen:codes`;
- канал: `<канал>/index.ts` и `<канал>/<m>-<канал>.views.ts` — реестр `<m><Канал>Views` с маркерами `// gen:imports`, `// gen:views`;
- пакеты единиц (если у слоя есть `package`): `package.json` и `tsconfig.json` в каталоге каждого пакета — кода и каналов с шаблоном.

Правки: строка экспорта `Def` модуля в `<ui>/index.ts` (маркер `// gen:exports`). Зависимости: если указан раннер — каждый пакет единицы дописывается в `package.json` раннера как `workspace:*`.

Заметки (печатаются всегда): подключить `Def` модуля в `modules` набора UI; подключить реестры к сборкам оболочки (`AppCodeLoaders`, реестры представлений канала); канал без шаблона — реестр не создан; каталоги пакетов вне `workspaces` корня — «Добавь … в workspaces»; затем `bun install`; раннер не указан — объяви пакеты в `package.json` оболочки.

### 3.2. `story`

Сторис не собирается без экрана, поэтому вид создаёт и экран `start` в той же папке — аргумент `<экран>` обязателен.

Файлы: `<ui>/<m>/<сторис>/<сторис>.story.ts` и всё, что создаёт `screen` для `<сторис>/<экран>`. Правки: списки `stories` и `screens` модуля, импорты и реэкспорт, реестр кода, реестры представлений каналов. Сам экран в файл сторис шаблон уже вписал (`start`, `screens`, исход `done` на выход `done` экрана; `callers: ['user']`, маркер `// gen:screens` для следующих экранов).

Заметка: подключить сторис к `stories` приложения UI (`*.ui-app.ts`) или к `leads` другой сторис; поправить `callers`, если сторис для гостя или системы.

### 3.3. `screen`

Файлы (по одному пути `<папка>/<экран>` в трёх деревьях): описание `<экран>.screen.ts`, код `<экран>.scode.ts`, представление `<экран>.view.ts` в каждом канале с шаблоном. Правки: список `screens` и импорты модуля, реэкспорт из `<ui>/index.ts`, реестр кода (`CodeLoader.screen`), реестры представлений; для экрана сторис — ещё импорт и элемент `screens` в файле сторис.

Заметки: экран в `shared` — добавь его в `screens` сторис, которые открывают; экран сторис — открой действием `to` (иначе недостижим, UI-07); канал без шаблона — представление не создано.

### 3.4. `notification`

Файлы: `<уведомление>.notification.ts`, `<уведомление>.ncode.ts` и представления каналов с шаблоном — те же деревья, что у экрана. Правки: список `notifications`, импорты, реэкспорт, реестр кода, реестры представлений; файла сторис в правках нет и при `<папка>` = сторис.

Заметка: заполни `event` (событие домена) в файле описания — без него файл не соберётся.

## 4. Отказы

Отказ — `GenError`: ничего не записано, код возврата 1. Порядок проверок у `story`, `screen`, `notification`: число аргументов, kebab-case имён, раскладка слоёв, проверка вида, лишние аргументы. У `ui-module`: модуль задан, kebab-case, каналы в `layers`, имена `app` и `<канал>-kit`, затем пакеты, корень и раннеры; хвост раннеров не ограничен.

| Вид | Причина | Текст |
|---|---|---|
| `ui-module` | модуль не задан | `Для «ui-module» нужен модуль — ui-module <usage>` |
| `story`, `screen`, `notification` | не хватает аргументов | `Для «<вид>» нужны <…> — <вид> <usage>` |
| все | имя не kebab-case | `<вид>: <модуль, сторис, папка, экран, уведомление> «<имя>» — имя в kebab-case (a-z, 0-9, дефисы)` |
| `story`, `screen`, `notification` | лишние аргументы | `<вид>: лишние аргументы — <вид> <usage>` |
| все | нет слоя `ui` или `fe-logic` | текст `dmg-core`: `слой «<слой>» не задан в .dmg/config.json (layers)` |
| `ui-module` | в `layers` нет каналов | `ui-module: в layers нет каналов — нужен слой fe-<канал>` |
| `ui-module` | модуль `app` | каталог совпал бы со слоем `fe-app`, имя зарезервировано |
| `ui-module` | модуль `<канал>-kit` | каталог совпал бы со слоем `<канал>-kit`, имя занято |
| `ui-module` | у слоя `ui` нет `package`, а у слоёв кода или каналов есть | пакеты импортируют описание по имени пакета — задай `layers.ui.package` |
| `ui-module` | раннер указан, а у слоёв модуля нет `package` | подключать нечего |
| `ui-module` | у слоёв есть `package`, а в `package.json` корня нет `dmg-ui` | версия для пакетов единиц берётся оттуда; нет файла — тот же отказ |
| `ui-module` | `package.json` корня — не JSON или не объект | `package.json корня — не JSON` / `не объект JSON` |
| `story` | сторис `shared` | имя папки занято общими экранами и уведомлениями |

Экран и уведомление без отдельных отказов сверх общих: папка `shared` для них — штатное значение.

## 5. Что вид не делает

- **Уведомление без `event`.** Событие домена вид не знает: в описании — комментарий `TODO`, заметка называет путь файла. Пока `event` не заполнен, файл не собирается.
- **Заглушки `load` бросают.** Код экрана и уведомления — класс с `load`, который бросает `Error('TODO: реализовать загрузку')`: тесты и приложение падают на нём, пока код не написан. Подписи и описания — `TODO: …`.
- **`workspaces` не правится.** Если шаблон `workspaces` корня уже покрывает каталог пакета — заметки нет; иначе заметка «Добавь … в workspaces». Корневой `package.json` вид читает, но не пишет; зависимость на раннер пишет ядро по плану.
- **Каналы без шаблона** (не `chat` и не `web`, например `telegram` на базе `chat`) — заметкой: файлов нет, канал на базе держит только перекрытия.
- **Набор UI, приложение UI, оболочка раннера** — руками: вид `set` и вид оболочки пакет не даёт.
- **Достижимость и связи.** `to`, `leads`, подключение сторис к приложению — руками; заметки напоминают, правило — UI-07, UI-24.
- **Каналов в `layers` нет** (для `story`, `screen`, `notification`) — не отказ: описание и код создаются, представлений нет, заметка об этом.

## 6. Форма созданного кода

Тексты шаблонов написаны в форме `biome` примера: перенос строк по ширине, импорты в порядке файла. Отступ вставки в существующий файл — от строки маркера `// gen:*`; нет файла или маркера — отступ формы шаблона, а строка уходит в «Вставь вручную». Не встал импорт — элемент списка того же файла тоже уходит вручную (правки одного файла связаны).

После `--write` прогони `biome check --write` проекта: форма проекта может отличаться от шаблона (ширина строки, порядок импортов).

Проверка имён — `NM-01` ([naming.md §7](../reference/naming.md)): файлы плана проходят её без нарушений при раскладке по `layers`.

## 7. Для автора видов

Свой вид (поставщика, а не проекта) — по `node_modules/dmg-core/docs/guides/provider-extension.md`: класс `GenProviderKind` с синхронным `plan`, вход `dmg-ui/dmg-core` отдаёт `gen: GenProvider` с массивом видов. Правила пакета: вид знает только `dmg-core/gen`, `node:fs` и `node:path`, с ядром и соседями пакетов не связан (`PackageDirections`, `CoreImportScanner`).

Тесты вида — два слоя:

- **План.** `plan(args, { layout })` на временной раскладке: файлы, правки, заметки, отказы `GenError`. Тест проверяет итоговый текст файлов, а не построение (TST-08).
- **Применённый план.** `applyPlan` из `dmg-core/gen` не экспортируется, поэтому тест собирает временный проект и запускает шаги через `DmgCoreCli.gen(…, '--write')` из `dmg-core/cli`: сначала модуль, затем сторис, экраны и уведомление — и проверяет итоговые файлы (без дублей и подсказок «Вставь вручную», имена по `NM-01`, форма `biome`). Образец — `packages/gen/src/ui-module-kind.applied.test.ts`.

Новый вид регистрируется в `packages/gen/src/index.ts`; имя вида не совпадает с видом `dmg-core` или другого поставщика (конфликт имён — отказ `gen`).
