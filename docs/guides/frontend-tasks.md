# Задачи фронта

**Назначение:** что обычно решает фронтенд-разработчик и чем это закрыто в `dmg-ui`: от задачи («пункт меню по роли», «кнопка, которая сейчас нельзя», «подсказка к полю») — к объявлению в коде экрана, к тому, как это видит человек в беседе, в Telegram и на странице, и к тесту, который это подтверждает. Гайд не заменяет описание API: как объявить сторис и экран — [Сторис, экран, уведомление](./story-screen-notification.md), как подключить канал — [Пакет канала](./channel-package.md), [Telegram](./telegram.md), [Web-канал](./web-channel.md).

---

## 1. Для кого и как читать

Гайд для автора экранов и для того, кто сверяет, что умеет пакет, прежде чем писать своё. Все примеры — на одном учебном наборе: домен «задачи и пользователи» учебного приложения `dmg-core` и набор UI поверх него ([packages/core/testing/example](../../packages/core/testing/example/todo/task-list.screen.ts), вход `dmg-ui/testing`). Экраны и сторис набора пишутся один раз, представление экрана — один раз на общей части (D-UI-50), каналы их только показывают: беседа (`dmg-ui/chat-ui`), в ней — Telegram (`dmg-ui/tg-bot`), и страница (`dmg-ui/web-ui`).

Раздел 2 — девять сценариев «что хотим». В каждом: задача; как объявить (блок кода из набора); как это видит человек в беседе, в Telegram и на странице; строка проверки; решения. Раздел 3 — таблица всех известных задач фронта с состоянием. Раздел 4 — чего пакет не делает. Раздел 5 — чеклист автора экрана.

**Как читать «Проверено».** Строка «Проверено:» — ссылка на файл теста и фрагмент имени теста в кавычках (такие строки — под каждым сценарием и в последнем столбце таблицы) — называет тест, который подтверждает утверждение: файл существует, фрагмент (подстрока) в нём есть. Это не пересказ теста, а адрес: открой файл и найди фрагмент. Проверка репо ([checks/guide-tasks.ts](../../checks/guide-tasks.ts)) сверяет каждую такую строку, каждый блок кода и требует строку у каждого сценария и у каждой строки таблицы с состоянием «есть»; мёртвая ссылка или пропавший фрагмент роняют `bun run check`.

**Как читать блоки кода.** Первая строка блока — `// из: путь`: остальные строки взяты из этого файла по порядку, дословно; пропуски строк допустимы. Сочинённого кода в гайде нет: чего нет в файле, того нет и в блоке.

Тексты «в беседе», «в Telegram», «на странице» — те, что показывают тесты и [примеры](../../examples/tg-bot/README.md) ([web](../../examples/web/README.md)); они даны для понимания, а не как контракт: контракт — исходы и вид экрана ядра.

## 2. Сценарии «Что хотим»

### 1. Пункт меню по роли и состоянию

**Задача.** В меню человек видит только свои разделы: администратору — одно, владельцу задачи — другое, исполнителю чужого поручения — третье. Меню — корневая сторис (D-UI-96), а не исключение.

**Как объявить.** Сторис объявляет, кому и когда она положена: `access` — право субъекта по Policy домена, `rules` — доменные правила. Это те же объекты, что исполняют UC: копий правил в UI нет. Ядро их пока только показывает графу и проверкам, а решает, показывать ли дверь (действие-переход в сторис), код экрана-источника тем же правилом (D-UI-94, D-UI-98, DEBT-UI-53).

```ts
// из: packages/core/testing/example/todo/finish-tasks.story.ts
export const FinishTasksStoryDef = StoryDef.define({
  name: 'finishTasks',
  callers: ['user'],
  start: TaskListScreenDef,
  access: TaskPolicy.rules.canManage,
});
```

```ts
// из: packages/core/testing/example/todo/plan-tasks.story.ts
export const PlanTasksStoryDef = StoryDef.define({
  name: 'planTasks',
  rules: [TaskRules.rules.withinOpenLimit],
});
```

Решение о двери — в коде экрана, ответом `Availability` (сценарий 3). «Карточка исполнителя» есть только у того, у кого есть субъект:

```ts
// из: packages/core/testing/example/todo/assigned-tasks.code.ts
openAssignee: ({ data, subject }) =>
  subject === undefined
    ? Availability.hidden()
    : Availability.when(data.tasks.length > 0, 'Поручений нет'),
```

**Беседа.** Вход `menu` даёт «Мои задачи», «Назначенные мне», «Закрыть»; скрытое (`hidden`) в вид не попадает, варианта нет вовсе. Роль читается при каждом показе: стал администратором — следующий показ с новым ответом.

**Telegram.** Те же варианты кнопками под сообщением; меню команд слева от поля ввода строит приложение из входов (D-UI-64).

**Страница.** Те же действия ссылками и кнопками области; роль приходит с соединением, смена роли — новое соединение (D-UI-99).

Проверено: [channels-story.test.ts](../../acceptance/channels-story.test.ts) — «сценарий 6», «вход menu даёт», «смена роли между показами»

Решения: D-UI-94, D-UI-96, D-UI-98.

### 2. Действие по праву над выделенным («Выполнить выбранные»)

**Задача.** В списке человек отмечает задачи; «Выполнить выбранные» доступно, только если он вправе управлять всеми отмеченными (владелец каждой или администратор). Всё — сразу при выделении, без запроса к серверу: правило то же, что у UC, и работает на клиенте.

**Как объявить.** Выбор — состояние экрана и локальное действие `toggle` (UC не зовёт); доступность — ответ кода экрана по Policy домена над выбранными:

```ts
// из: packages/core/testing/example/todo/task-list.screen.ts
completeSelected: {
  label: 'Выполнить выбранные',
  uc: CompleteTasksUcDef,
  confirm: {
    label: 'Выполнить выбранные задачи?',
  },
},
```

```ts
// из: packages/core/testing/example/todo/task-list.code.ts
completeSelected: ({ data, state, subject }) =>
  Availability.given(
    new TaskSelection(data.tasks, state.selected).openTasks(),
    'Отметьте открытые задачи',
    (tasks) =>
      Availability.policy(TaskPolicy.rules.canManageAll, subject, {
        tasks,
      }),
  ),
```

Ответ — только показ: сервер перепроверяет каждый вызов, и «ложное доступно» (код экрана ошибся) заканчивается отказом `ACCESS_DENIED` с текстом, а не выполнением.

**Беседа.** До выбора вариант помечен — «🚫 Выполнить выбранные»; после «Отметить задачу» и выбора задачи — обычный «Выполнить выбранные». Исполнителю-не-владельцу при выбранном поручении варианта нет вовсе: ни обычного, ни помеченного. Нажатие — вопрос «Выполнить выбранные задачи?» с «Да» и «Нет».

**Telegram.** То же сообщением с кнопками: «Отметить задачу», выбор, «Выполнить выбранные», «Да»; задача отмечена `[x]`, после «Да» выполнена, список обновлён.

**Страница.** Форма «Выполнить выбранные» — `available: false` с причиной «Отметьте открытые задачи» до отметки строки галочкой и доступна после; у исполнителя-не-владельца формы нет. Подтверждение — «Подтвердить».

Проверено: [channels-story.test.ts](../../acceptance/channels-story.test.ts) — «сценарий 1», «помечено, после — обычное», «администратор выбрал поручение», «через код экрана»

Решения: D-UI-29, D-UI-79, D-UI-98.

### 3. Скрыто или отключено с причиной

**Задача.** Действие, которое человеку не положено, не показывается. Действие, которое сейчас нельзя, показывается и объясняет почему: «Создать задачу» при пределе открытых задач.

**Как объявить.** Три ответа `Availability` — доступно, скрыто (текста нет), отключено с причиной; в вид попадают два (скрытое из вида исчезает):

```ts
// из: packages/core/src/screen/availability.types.ts
| { readonly kind: 'available' }
| { readonly kind: 'hidden' }
| { readonly kind: 'disabled'; readonly text: string };
```

Причину пишет не экран: доменное правило отвечает текстом своей ошибки, правило вида «нет прав» — скрывает.

```ts
// из: packages/core/testing/example/todo/task-list.code.ts
create: ({ data }) =>
  Availability.rule(TaskRules.rules.withinOpenLimit, {
    ownerTasks: data.owned.map((row) => TaskAr.readonly(row)),
  }),
```

**Беседа.** У владельца трёх открытых задач вместо «Создать задачу» — «🚫 Создать задачу»; свободный текст отвечает причиной «Слишком много открытых задач», задач по-прежнему три. Нажатие помеченного варианта — ответ с причиной, UC не вызывается, подписи прежние. Выполнил одну — «Создать задачу» снова обычная.

**Telegram.** Кнопка «🚫 Создать задачу» обычная (есть `callback_data`, нет `disabled` и `style`); нажатие — ровно один `answerCallbackQuery` с причиной без `show_alert` (тост вверху чата), сообщение и кнопки прежние, причина длиннее 200 единиц UTF-16 обрезается (D-UI-105). Пометка «🚫» заметна и в подписи «🚫 Предыдущая страница» на первой странице списка.

**Страница.** Кнопка серая и стоит на месте, причина — под кнопкой и в подсказке при наведении; Tab достигает её, Enter и пробел ничего не отправляют; форма «Создать» при пределе — `available: false` с причиной, отправка — `unavailable` (D-UI-106). Скрытого на странице просто нет.

Проверено: [channels-story.test.ts](../../acceptance/channels-story.test.ts) — «сценарий 4», «предел открытых», «возврат доступности»; [telegram-disabled.story.test.ts](../../packages/tg-bot/testing/telegram-disabled.story.test.ts) — «нажатие — ровно один answerCallbackQuery», «причина длиннее 200»; [example-web-disabled.browser.test.ts](../../browser/example-web-disabled.browser.test.ts) — «Enter и пробел на кнопке с причиной»

Решения: D-UI-98, D-UI-105, D-UI-106.

### 4. Карточка из другой сторис и возврат; ветка, отрезанная составом

**Задача.** Из «Назначенные мне» человек открывает карточку исполнителя — экран другой сторис — и возвращается тем же путём. В канале, где карточки пользователя нет (например, в боте нет управления чужими учётными записями), ветка отрезана, а остальной экран тот же.

**Как объявить.** Связь сторис — `leads`: действие-переход ведёт на `start` связанной сторис. Состав канала — список сторис приложения UI: нет `viewUser` — нет и действия карточки, код экранов тот же (D-UI-95).

```ts
// из: packages/core/testing/example/todo/follow-assigned.story.ts
export const FollowAssignedStoryDef = StoryDef.define({
  name: 'followAssigned',
  leads: (): readonly AnyStoryDef[] => [ViewUserStoryDef],
});
```

```ts
// из: packages/chat-ui/testing/example/example-trimmed.app.ts
stories: [
  StartWorkStoryDef,
  PlanTasksStoryDef,
  FinishTasksStoryDef,
  FollowAssignedStoryDef,
],
```

**Беседа.** «Назначенные мне» → «Карточка исполнителя»; пока карточка открыта, пришло новое поручение; «Закрыть» возвращает на «Назначенные мне», список перечитан — обе задачи. В урезанном приложении у «Назначенные мне» только «Закрыть», карточки нет.

**Telegram.** Те же варианты кнопками; путь и возврат — как в беседе (D-UI-53).

**Страница.** Действие `openAssignee` есть; карточка открывается в боковой панели, список в основной области не пропадает и перечитывается по событию назначения; «Закрыть» или «Назад» браузера закрывает панель, положение истории прежнее.

Проверено: [channels-story.test.ts](../../acceptance/channels-story.test.ts) — «сценарий 2», «сценарий 3», «возврат с карточки исполнителя: список поручений перечитан», «карточка в side»

Решения: D-UI-94, D-UI-95, D-UI-96.

### 5. «Назад» и структурный переход рядом

**Задача.** «Назад» возвращает туда, откуда пришёл; рядом лежит обычный переход («К моим задачам»), который идёт вглубь, а не назад. Листание не растит путь.

**Как объявить.** «Назад» экран не объявляет: канал добавляет его сам, когда путь не пуст. Структурный переход — обычное действие `to`, уходящая карточка попадает в путь; подпись листания — не «Назад» (так названа автокнопка).

```ts
// из: packages/core/testing/example/users/user-card.screen.ts
tasks: {
  label: 'К моим задачам',
  description: 'Переход к списку своих задач.',
  to: (): readonly AnyScreenDef[] => [TaskListScreenDef],
},
```

**Беседа.** В карточке последний вариант — «Назад». «К моим задачам» открывает «Мои задачи» с «Назад» в конце; три «Назад» подряд ведут в карточку, в «Назначенные мне» и в меню, на «Назначенные мне» без пути кнопки «Назад» нет.

**Telegram.** «Назад» правит то же сообщение, список перечитан, ответ на нажатие один; `/back` делает то же новым сообщением, у прежнего снимаются кнопки; «Дальше» и «Предыдущая страница» путь не растят.

**Страница.** «Назад» — «Назад» браузера: шаг истории при уходе вглубь, замена при листании («Дальше» записей не прибавляет); открытие панели и окна — запись с пометкой `over`, «Назад» закрывает слой и не уходит со страницы (D-UI-97, D-UI-104).

Проверено: [channels-story.test.ts](../../acceptance/channels-story.test.ts) — «сценарий 2», «сценарий 6», «в конце; три», «листание — замена записи истории»; [telegram-back.story.test.ts](../../packages/tg-bot/testing/telegram-back.story.test.ts) — «/back с путём»; [example-web-back.browser.test.ts](../../browser/example-web-back.browser.test.ts) — «запись не добавляется; ещё»

Решения: D-UI-53, D-UI-97, D-UI-104, D-UI-108.

### 6. Окно над списком, закрытие, «Назад»

**Задача.** Из меню в «Мои задачи», из списка — окно с карточкой; несколько действий в окне; закрыл — вернулся в список; «Назад» — в меню.

**Как объявить.** Для беседы объявлять нечего: окна в ней нет, карточка — следующий экран. Для страницы окно — размещение экрана в области `modal`; приложение и умолчание канала («из корня — в панель») не меняются, размещение передаёт сборка вкладки:

```ts
// из: packages/web-ui/testing/example/example-pages.placements.ts
export const exampleWindowPlacements: readonly PagePlacement[] = [
  { screen: TaskCardScreenDef, region: 'modal' },
];
```

**Беседа.** Меню → список → карточка → «К списку»: «Назад» ведёт в меню, и там «Назад» уже нет.

**Telegram.** Как в беседе: один диалог, один путь.

**Страница.** Поверх страницы окно, фон затемнён, фокус внутри; запись истории на открытие окна (`over`), назначение и выполнение внутри окна — замены, а не шаги. «Закрыть» и «К списку» закрывают окно движением назад; «Назад» браузера при открытом окне тоже закрывает его, следующий «Назад» — меню.

Проверено: [channels-story.test.ts](../../acceptance/channels-story.test.ts) — «сценарий 6», «закрытие окна client.close», «при открытом окне закрывает его»; [example-web-back.browser.test.ts](../../browser/example-web-back.browser.test.ts) — «после закрытия окна кнопкой»

Решения: D-UI-78, D-UI-81, D-UI-97.

### 7. Поле: подпись, подсказка, пример, пределы, булево и дата

**Задача.** Каждое поле входа — с подписью, пояснением зачем оно, примером и пределами; число и дата вводятся как число и дата, а не как строка; текст ошибки поля — из схемы.

**Как объявить.** Всё — в схеме входа действия: `v.title` — подпись, `fieldHint` — подсказка, `v.examples` — пример, `v.minValue` и `v.maxValue` — пределы с текстом отказа. Канал узнаёт о поле только из вида экрана (`FieldDescription`, D-UI-100), второго описания нет.

```ts
// из: packages/core/testing/example/todo/task-list.screen.ts
jumpTo: {
  label: 'К части',
  input: v.object({
    part: v.pipe(
      v.number('Введите номер части'),
      v.integer(),
      v.minValue(1, 'Части начинаются с первой'),
      v.maxValue(99, 'Не больше 99'),
      v.title('Часть'),
      v.examples([2]),
      fieldHint('Номер части списка, с первой'),
    ),
  }),
},
```

**Беседа.** Вопрос поля: «Введите: Часть / Номер части списка, с первой / Пример: 2 / Пределы: от 1 до 99, целое». «abc» — замечание схемы «Введите номер части» и тот же вопрос; «0» — «Части начинаются с первой» и тот же вопрос; «2» — часть 2. Булево поле — вопрос с подсказкой и кнопками «Да» и «Нет»; дата — подсказка и пример, «завтра» отвергнуто текстом схемы.

**Telegram.** Те же тексты сообщением; ввод логируется без значения (ERR-07).

**Страница.** Поле числа — `type=number`, `min=1`, `max=99`, `step=1` из пределов схемы, подсказка связана с полем; булево в карточке задачи — чекбокс «Срочно» с подсказкой, дата — поле даты «Когда»; отказ схемы — замечание у поля, форма и введённое остались.

Проверено: [channels-story.test.ts](../../acceptance/channels-story.test.ts) — «сценарий 5», «поле part: вид», «вопрос с подсказкой, примером и пределами»; [telegram-fields.story.test.ts](../../packages/tg-bot/testing/telegram-fields.story.test.ts) — «вопрос: подпись и подсказка»; [example-web-fields.browser.test.ts](../../browser/example-web-fields.browser.test.ts) — «type=number, min=1, max=99, step=1»

Решения: D-UI-47, D-UI-100, D-UI-106.

### 8. Справка по экрану и общая

**Задача.** Человек спрашивает «что здесь можно»: справка называет действия и переходы экрана, у отключённых — причину; общая справка без экрана — с чего можно начать. Скрытого в справке нет.

**Как объявить.** Подсказка — поле `hint` экрана и действий; подсказка двери берётся из сторис-цели (`leads`), поэтому у «Назначенные мне» в меню справка называет подсказку сторис «Поручения». Справку строит ядро (`ScreenHelp`), канал её только показывает (D-UI-107).

```ts
// из: packages/core/testing/example/todo/task-list.screen.ts
hint: 'Отметьте задачи и выполните их разом или откройте одну',
jumpTo: {
  label: 'К части',
  hint: 'Укажите номер части списка, чтобы не листать по одной',
```

**Беседа.** Сигнал `help`: отдельная заметка «Справка: Мои задачи» с подсказкой экрана и пунктами «• …»; у отключённого — «• Предыдущая страница (недоступно: Это первая страница)»; в меню — «• Назначенные мне — Смотрите, что вам поручили, и выполняйте поручения».

**Telegram.** Команда `/help` — ровно одно сообщение без кнопок, прежнее сообщение и его кнопки живы, UC не вызывается; без живого экрана — «Справка: …» с корнями приложения; длинная справка не длиннее 4096 знаков. В меню команд `/help` не публикуется, но работает.

**Страница.** Кнопка «Справка» у заголовка области: достижима Tab, `aria-expanded` — `false`, затем по Enter блок под заголовком с разделами «Что можно сделать» и «Куда можно пойти».

Проверено: [channels-story.test.ts](../../acceptance/channels-story.test.ts) — «сценарий 7», «справка показывает подсказку сторис followAssigned»; [telegram-help.story.test.ts](../../packages/tg-bot/testing/telegram-help.story.test.ts) — «справка — ровно один sendMessage», «длинная справка»; [example-web-help.browser.test.ts](../../browser/example-web-help.browser.test.ts) — «справка области на странице в Chrome»

Решения: D-UI-107.

### 9. Смена человека

**Задача.** Тот же экран после смены роли или человека показывает его возможности, а не прежнего.

**Как решено.** Пакет читает роль при каждом показе (беседа) и при каждом соединении (страница); смену человека на странице решает проект-потребитель, форма по умолчанию — перезагрузка страницы. Правило и ограничения — в [Web-канале](./web-channel.md), раздел 12; решение — D-UI-109.

**Беседа.** Стал администратором — следующий показ с новым ответом.

**Страница.** Новое соединение исполнителя, ставшего администратором, — форма выполнения доступна; вкладки того же адреса, не перезагруженные, остаются прежним человеком до обрыва связи.

Проверено: [channels-story.test.ts](../../acceptance/channels-story.test.ts) — «смена роли: новое соединение исполнителя», «смена роли между показами»

Решения: D-UI-88, D-UI-99, D-UI-109.

## 4. Чего пакет не делает

У каждого пункта — причина и условие, при котором он станет задачей пакета. Пока условие не наступило, пишется в проекте.

- **Экран «за результатом»** (выбор с возвратом значения вызвавшему). Триггер — первый экран выбора, нужный двум вызывающим.
- **Общий черновик мастера на несколько экранов.** Сейчас мастер — шаги одного экрана или поля входа по шагам. Триггер — мастер, которому одного экрана мало.
- **Файл во входе действия.** Вида поля нет: UI-27 отвергает `array` и `object`. Триггер — первая форма с файлом.
- **Кнопка-ссылка.** Ссылка наружу — фрагмент текста; URL-кнопки в виде нет — DEBT-UI-46.
- **«Вперёд» в беседе и Telegram.** Автокнопка «Назад» есть; «Вперёд» — лишняя кнопка при редком удобстве. Триггер — в логе операций частые «Назад» с немедленным возвратом на тот же экран.
- **Вычисление доступа сторис ядром.** Доступность двери решает код экрана-источника; `access` и `rules` объявлены, но ядро их не вычисляет — DEBT-UI-53.
- **Запрос допуска у бэка** (проверка UC без исполнения) и проверка поля на сервере при вводе. Случаи закрывает признак в ответе query UC; триггер — экран, где признак пришлось бы писать под каждую кнопку.
- **Формат даты со временем в поле страницы.** Поле `date` — только день: DEBT-UI-56.
- **Смена человека без перезагрузки страницы.** Клиент не умеет очищать вкладку от следов прежнего человека. Триггер (D-UI-88) — вход и выход без перезагрузки у первого web-приложения потребителя; пока — сценарий 9, D-UI-109.
- **Серверный рендер страницы.** Цель на горизонте, форма контракта его допускает — D-UI-86.

## 5. Чеклист автора экрана

- Право — объект домена (Policy или правило), а не условие в экране; ответ `Availability` берёт его из `subject` и данных, а не пишет копию.
- Действие, которое человеку не положено, — `hidden`; которое сейчас нельзя — `disabled` с причиной для человека; причина — текст ошибки правила, а не строка экрана.
- Подпись листания и переходов — не «Назад»: так называется автокнопка канала.
- Поле входа — с `v.title`, `fieldHint`, `v.examples` и текстом отказа в пределах; описание берёт ядро, свой вид поля канал не придумывает.
- Подсказка двери — в `hint` сторис-цели; у экрана и действий — `hint`, которую покажет справка.
- Экран работает на двух каналах без условий: код один, различие — в составе приложения UI (`stories`) и в размещении областей страницы.
- Новая строка в этом гайде — с `Проверено:` и блоком `// из:`: иначе `bun run check` её не примет.
