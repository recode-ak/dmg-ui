# Сторис, экран, уведомление — гайд

**Назначение:** как автор UI объявляет сторис, экран и уведомление манифестами, пишет код экрана и как всё это исполняется. Пример — учебный набор [platform/ui/todo/finish-tasks/](../../packages/example/src/platform/ui/todo/finish-tasks/task-card.screen.ts) (импортируется из `dmg-ui/example`; привязка к диалоговому каналу — `dmg-ui/chat-ui/testing`). Пакет канала — в [channel-package.md](./channel-package.md). Имена и раскладка файлов — [naming.md](../reference/naming.md).

---

## 1. Когда применять

- Нужно описать, что человек видит и делает, независимо от канала: тот же экран работает в мессенджере, на странице и в консоли.
- Система сообщает человеку сама по доменному событию — это уведомление, а не экран.
- Канал, транспорт и рендер — другой гайд ([channel-package.md](./channel-package.md)). Логика «можно ли» остаётся в UC и агрегате: экран читает query UC и вызывает command UC.

## 2. Модель

| Понятие | Что объявляет | Класс |
|---|---|---|
| набор UI | модули поверх доменного приложения `dmg-core` | `UiSetDef` |
| приложение UI | канал, состав сторис и уведомлений, входы | `UiAppDef` |
| UI-модуль | экраны, сторис, уведомления одной области | `UiModuleDef` |
| сторис | кто (`callers`), зачем (`goal`), старт, экраны, исходы с целью, связи (`leads`), доступ (`access`), правила (`rules`) | `StoryDef` |
| экран | параметры, чтение, данные, состояние, действия, выходы | `ScreenDef` |
| уведомление | событие, получатели, чтение, ссылки | `NotificationDef` |

Принципы: экран читает, действие пишет; экран адресуем; вход действия объявляет схема; состояние — данные по схеме; код экрана не знает, где исполняется; открытых экранов может быть несколько; сторис — описание, а не диспетчер; манифест статичен, код ленив; логика показа (доступность, варианты) — в коде экрана, а не в представлении. Причины — в [decisions.md](../decisions.md) (D-UI-6, D-UI-7, D-UI-10).

## 3. Объявление

1. **Экран** — `ScreenDef.define({...})`: `params` (`v.strictObject`, UI-19), `reads` (query UC), `data`, необязательные `state`, `actions`, `locals`, `primary`, `exits`, `refresh`, `catches`, `examples`. Ссылка на другой экран в `to` — thunk с аннотацией возврата, иначе TS7022 (D-UI-8):
   ```ts
   back: {
     label: 'К списку',
     description: 'Возврат к списку задач.',
     to: (): readonly AnyScreenDef[] => [TaskListScreenDef],
   },
   ```
   Действие `to` — структурный переход: уходящий экран кладётся в путь канала (D-UI-108); автокнопку «Назад» экран не объявляет, и подпись действия — не «Назад».
2. **Действие** — `uc` (command UC) и/или `to`. Без `uc` — переход (меню, листание). Действие вправе не вызывать UC; вызывает не больше одного (D-UI-10). `input` — схема полей (как их писать — ниже, «Поле входа»); `confirm` — подтверждение с текстами. Необязательное `hint` — подсказка человеку (у сторис, экрана, действия и локального действия одно имя), отдельная от `description`, который пишется для программиста.
3. **Локальное действие** (`locals`) меняет только состояние экрана и UC не зовёт. Имена `actions` и `locals` не пересекаются (UI-21).
4. **Выходы** (`exits`) объявляет экран; `data` выхода — схема. Выход экрана получает значение через `TaskListScreenDef.exits.closed.with(...)`.
5. **Перечитывание** — `refresh: [{ event, params, subject }]`: `params` сопоставляет параметр адреса с полем payload, `subject` — поле payload с `uuid` человека, `any: true` — «всем» (D-UI-22). Пустая запись — нарушение UI-17.
6. **Сторис** — `StoryDef.define`: `callers`, `goal` в форме «чтобы …», `start`, `screens`, `outcomes` с `exits: [Экран.exits.имя]` (UI-23). Экран о сторис не знает; один экран живёт в нескольких сторис. Необязательное: `leads` — thunk со сторис, в которые ведёт эта (переход — на `start` цели, связь без перехода — UI-24; отрезанная составом приложения ветка — `AppReach`, D-UI-95); `access` — правило Policy домена, тот же объект, что исполняет UC; `rules` — доменные правила для показа человеку (оба только объявлены, решает код экрана, D-UI-94); `hint` — подсказка человеку. У исхода — `after`: `'back'` (по умолчанию), `'home'` или адрес экрана; выход общего экрана ведёт к одной цели во всех сторис приложения (UI-25, D-UI-96).
   ```ts
   export const FinishTasksStoryDef = StoryDef.define({
     name: 'finishTasks',
     label: 'Выполнение задач',
     description: 'Пользователь отмечает задачи выполненными.',
     callers: ['user'],
     goal: 'чтобы закрыть сделанное',
     start: TaskListScreenDef,
     screens: [TaskListScreenDef, TaskCardScreenDef],
     outcomes: {
       closed: { label: 'Список закрыт', description: '…', exits: [TaskListScreenDef.exits.closed] },
       created: { label: 'Задача создана', description: '…', exits: [TaskListScreenDef.exits.created] },
     },
   });
   ```
7. **Уведомление** — `NotificationDef.define`: `event`, `recipients`, `reads`, `data`, `links`, `examples`. Получатели — `{ from: 'payload', fields: ['assigneeId'] }` или `{ from: 'query', uc, input, fields }`: query UC вызывает система (`SystemCaller` с `kind: 'app'`, `module` — имя набора UI, D-UI-23).
8. **Сборка** — `UiModuleDef.define({ screens, stories, notifications })`, затем `UiSetDef.define({ app: <AppDef домена>, modules })` и `UiAppDef.define({ set, channel, stories, notifications, entries })`. Вход — `entries.start.address: TaskListScreenDef.at({ page: 0 })`.
9. **Адрес.** `Screen.at(params)` даёт `Address`; через границу JSON адрес идёт как `AddressJson` (`AddressCodec.encode/decode`). `id` экрана — `<набор>/<модуль>/<экран>` (`UiIds.screen`). `decode` — внешние данные: отказ приходит значением (`AddressRejection`), не броском (D-UI-9). Параметры, влияющие на чтение (страница, фильтр), — параметры адреса, а не состояние.

**Поле входа** (D-UI-100). Ядро читает схему поля и отдаёт каналу `ActionField`: подпись, вид, обязательность, подсказку, пример, пределы. Пиши поле так:

```ts
title: v.pipe(
  v.string(),
  v.minLength(1),
  v.title('Название задачи'), // подпись для человека; без него — description, затем имя поля
  fieldHint('Коротко: что нужно сделать'), // подсказка (v.metadata), не v.description
  v.examples(['Купить хлеб']), // пример: первый скаляр
  v.description('Название'), // для программиста (UI-14)
),
```

- Вид — по схеме: `v.number` — `number` (`v.integer` даёт предел «целое»), `v.boolean` — `boolean` (варианты «Да» и «Нет»), `picklist`, `enum`, union литералов — `choice`, `v.pipe(v.string(), v.isoDate())` — `date`; всё остальное, включая `v.date()`, откатывается на `string`. Дата — строка ISO.
- Пределы показываются из `v.minValue`, `v.maxValue`, `v.minLength`, `v.maxLength`, `v.length`, `v.nonEmpty`; сообщение схемы пиши по-человечески (`v.number('Введите номер страницы')`): канал показывает его как замечание.
- Число из строки приводит канал через `FieldInput`; не число отвергает схема.
- Подсказка и пределы — только показ: проверяет схема входа и Policy (D-UI-29). У поля с `F.sensitive` пример в `ActionField` не отдаётся, но `examples` и `hint` попадают в граф через JSON Schema входа и там видны: пример у `F.sensitive` пиши вымышленным. Правило графа UI-26 ловит `examples` у `F.sensitive` (D-UI-101). Поле `array` или `object` в `input` действия человек не введёт: правило UI-27.
- Дерево сторис для меню: `StoryTree.of(app)` отдаёт `roots()` (корни: сторис, в которые не ведёт связь другой сторис приложения) с вложенными `children` в порядке `leads`, сторис из нескольких мест — полный узел один раз, дальше `again: true`; в узле — `label`, `description`, `hint`, `goal`, `access` и `rules`. `access` и `rules` — объявленное, не вычисленное: по человеку меню отбирает доступность дверей (D-UI-98). `omitted()` — сторис, отрезанные составом приложения, с «откуда» (D-UI-101). Корни дерева видны в графе — `props.roots` узла приложения.

**Подсказка двери и справка** (D-UI-107). Дверь экрана — действие без `uc`, которое ведёт (кроме своего экрана) на `start` сторис приложения из `leads` сторис с этим экраном (`StoryDoors`). У двери без своей `hint` вид экземпляра (`ActionView.hint`) берёт `hint` сторис-цели, **если цель ровно одна**: две сторис с общим `start` (как «Планирование» и «Выполнение» на `taskList`) — подсказки нет, пиши `hint` у действия. Своя подсказка действия побеждает. Без приложения (`ScreenPreview`, исполнитель без `app`) подстановки нет; граф не меняется — подстановка в виде, не в Def. Справка — `new ScreenHelp(app)`: `of(view)` и `general()` дают `HelpSheet` (данные, текст строит канал): `title` — подпись экрана из Def (у общей — подпись приложения), `hint` — из вида, `items` — действия и локальные (отключённое — с причиной `disabled` из вида), `leads` — доступные двери; общая — корни `StoryTree` без `access`. Текст справки — только `hint`: `description` и `goal` пиши для программиста, `hint` — для человека.

```ts
new ScreenHelp(ExampleDialogUiAppDef).of(menuView);
// { title: 'Начать работу', hint: 'Отсюда начинается работа: выберите раздел',
//   items: [{ name: 'close', label: 'Закрыть' }],
//   leads: [{ name: 'tasks', label: 'Мои задачи' },
//           { name: 'assigned', label: 'Назначенные мне',
//             hint: 'Смотрите, что вам поручили, и выполняйте поручения' }] }
```

## 4. Код экрана и уведомления

`ScreenCode<D, S>` лежит отдельно от манифеста и вызывающего не видит (D-UI-7). Обязательны `load` и `done` у каждого действия — это проверяет `ScreenUnit` лениво, при первом `open` (не при сборке). Остальное необязательно:

- `load({ params, read, context })` — данные через `read(uc, input)`, только UC из `reads`; отказ UC — `err`.
- `actions[name]` — шаги: `command` строит вход UC (без него — вход действия), `done(ctx, output)` возвращает переход, `caught(ctx, error)` — переход по отказу с кодом из `catches`.
- `initialState(data)` — обязателен у экрана со `state`; `locals[name]` — чистая функция `(state, data, input) => state`.
- `availability[name]({ params, data, state, subject, context })` — ответ `Availability` о действии: `Availability.yes()`, `hidden()` (субъекту не положено, текста нет; в вид не попадает), `disabled(text)` (отключено с причиной); помощники `when(условие, текст)`, `policy(правило, субъект, ctx)` (нет субъекта или отказ — скрыто) и `rule(доменноеПравило, ctx)` (отказ — отключено с текстом ошибки). Нет записи — доступно. В виде — два ответа: доступно и отключено с причиной (`ViewAvailability`); булева признака нет (D-UI-98). В беседе и Telegram отключённое — вариант с пометкой `🚫` в подписи, нажатие отвечает причиной (D-UI-105).
- `choices(...)`, `defaults(...)` — варианты и начальные значения полей.

Субъект — доменный объект «кто смотрит» (тот, что получает Policy; не `Caller`) — лежит в `context.subject` у `load`, шагов и функции доступности; тип проекта — второй параметр `ScreenCode<D, S>`. Его кладёт канал в контекст рендера; без человека субъекта нет. Ответ о доступности — только показ: сервер перепроверяет каждый вызов (D-UI-29). Приложение вправе не включать часть связанных сторис: действие-переход в отрезанную сторис исполнитель из вида убирает (`ScreenRuntimeSpec.app`, D-UI-95).

Переход — `Address` (свой экран с теми же параметрами значит «остаться и перечитать») или `exits.имя.with(data)`. Образец: [task-card.scode.ts](../../packages/example/src/frontend/todo/logic/finish-tasks/task-card.scode.ts).

`NotificationCode<D>`: `load({ payload, read })` собирает данные уведомления от имени получателя, `links(data, payload)` возвращает адреса из `links()` манифеста. Образец — [task-assigned.ncode.ts](../../packages/example/src/frontend/todo/logic/shared/task-assigned.ncode.ts).

Код подключает корень сборки реестром `CodeLoaders.of(set, [CodeLoader.screen(def, async () => new (await import('./x.scode')).XScreenCode()), CodeLoader.notification(def, async () => new (await import('./x.ncode')).XNotificationCode())])`; загрузчик возвращает объект кода, а не модуль, и нужен каждому экрану и уведомлению набора (образец — [example-codes.ts](../../packages/example/src/runners/example-codes.ts)).

## 5. Исполнение

`ScreenRuntime.open(address, { context, trace })` даёт `ScreenInstance`; `restore(json, options)` — из снимка `InstanceJson`. Вид — `instance.view()` (`InstanceView`; в типах экрана — `ScreenViewOf<D>`). Подписка на изменения вида — `onChange(listener)`, причина — `ViewChange.cause`: `refreshed`, `acted`, `local`.

`act({ action, input, revision, confirmed, trace })` проверяет по порядку: закрыт → ревизия → имя → «только чтение» (действие с `uc` отключено исполнителем, D-UI-11) → доступность → подтверждение → вход по схеме → `command` → вызов UC → `done`/`caught` → проверка перехода по манифесту. Исходы `ActionOutcome`:

| исход | значение |
|---|---|
| `moved` | открыть адрес `address` |
| `stayed` | остаться: экземпляр перечитан, ревизия выросла |
| `exited` | экран закрыт выходом `exit` (с `data`) |
| `confirm` | нужно подтверждение (тексты из манифеста) |
| `rejected` | вход не по схеме; `issues` с полем и текстом |
| `refused` | отказ UC (`Refusal`: код, главная строка `ErrorText`, `caught`) или дефект кода — `SERVER_INTERNAL` |
| `stale` | ревизия вида устарела |
| `unavailable` | `unknown`, `disabled`, `readOnly`, `closed` |

Действия, перечитывание и локальные действия одного экземпляра идут по очереди; ревизия растёт только при загрузке; сигналы, пока перечитывание ждёт, сливаются в одно (D-UI-19). Состояние не по схеме при `restore` заменяется начальным, адрес не восстановился — отказ каналу (D-UI-21). Отказ UC — исход, а не бросок; перехватываются только коды из `catches` (D-UI-20).

Уведомление исполняет сервер на каждого получателя: данные читаются от его имени, ссылки берутся только из `links()` (D-UI-23). Событие перечитывает экран, но только читает; command UC по событию не исполняется (D-UI-22).

Каталог для документации и снимков: `new ScreenPreview({ set, codes })` даёт `screen(def, 'имя примера', context)` и `notification(def, 'имя')`; они строят вид и данные по `examples`, не зовя `load` и порты.

## 6. Два пути данных

Экран получает данные двумя путями, оба равноправны (D-72 пакета `dmg-core`, `node_modules/dmg-core/docs/decisions.md`). Агрегат и вопросы на клиенте — логика одна, но клиенту нужен код домена той же версии. Готовый ответ UC — один вызов и ровно нужные данные, но UC пишется под экран. Список, поиск, сводка и клиент без кода домена — готовый ответ; вопрос «можно ли» — агрегат. Выбор виден в графе по рёбрам `reads`.

## 7. Чеклист правил

Граф проверяет `bun run arch:check` с поставщиком `UiGraphProvider` (`dmg-ui/graph`). Каталог — [rules.md](../reference/rules.md).

- Сторис: UI-01 (вызывающие допущены к UC экранов), UI-02, UI-03, UI-04, UI-23, UI-24 (связь подтверждена переходом), UI-25 (одна цель у выхода), UI-35 (экраны только своего модуля), UI-36 (цель исхода и ссылка уведомления в чужой модуль — только `start` его сторис).
- Модуль: UI-37 (≥2 пользователя у вспомогательного).
- Экран: UI-08 (`reads` — только query), UI-09 (`uc` — только command), UI-12 (только UC для человека), UI-15, UI-16, UI-17, UI-19, UI-21.
- Тексты и примеры: UI-13 (заполнены, включая необязательную `hint`), UI-14 (`description` у полей), UI-20 (примеры по схемам), UI-26 (нет `examples` у `F.sensitive`), UI-27 (вид поля входа поддержан).
- Уведомление: UI-18 (поля получателей).
- Канал и приложение: UI-05, UI-06 (представление), UI-07, UI-10; общее — UI-11, UI-22.

## 8. Ловушки

- **`toMatchObject` с асимметричным матчером** мутирует проверяемый объект (Bun) — сравнивай поля по одному или через `toEqual`.
- **Код без `done`** обнаружится только при первом `open` экрана: проверь каждый экран тестом открытия.
- **`stayed` при отказе перечитывания.** Команда уже выполнена, а вид покажет `status: 'refused'`: не считай `stayed` «всё прошло».
- **«Назначенные мне» не перечитывается по `completed`:** в payload нет исполнителя, `subject` не из чего взять.
- **Данные уведомления не копируют payload** — читай через `read` от имени получателя.
- **Ловушки канала** — постоянный `requestId`, различимость «нет» и «не твоё», тексты замечаний `InputRejection.issues[].text`, повторный `UiNotifier.start()` — описаны в [channel-package.md](./channel-package.md) (разделы 3, 7, 8).

## 9. Как тестировать

- Состав и связи — `arch:check` и граф (`ExampleDialogArch` из `dmg-ui/chat-ui/testing`, `ExamplePagesArch` из `dmg-ui/web-ui/testing` — образец сборки `ArchApp`); отдельные тесты манифестов не нужны (TST-09).
- Код экрана — тестом через `ScreenRuntime` с `MemoryUiObserver` из `dmg-ui/testing`: открыть, выполнить действие, проверить исход и записи (`kinds()`).
- Примеры — снимками: `ExamplePreview` из `dmg-ui/testing` рендерит пример через представление канала.
- Имена и раскладка файлов набора и канала — тестом с `UiFileNames` из `dmg-ui/testing` (правило `NM-01`): суффикс ↔ вид, имя `<Имя><Вид>`, папка UI-модуля, тест рядом; образец теста — [naming.md §7](../reference/naming.md#7-проверка).
- Браузерный тест нужен, только если без настоящего браузера не проверить: правило и запуск — [Web-канал, раздел 15](./web-channel.md#15-как-тестировать). Какие задачи фронта закрыты экраном и сторис и чем проверены — [Задачи фронта](./frontend-tasks.md).
- Тесты изолированы и короткие (TST-04), проверяют код экрана, а не платформу или схемы (TST-09).
- Набор минимален при полном покрытии поведения (TST-08): тесты затронутого модуля пересматриваются целиком, дубль и тест отменённого поведения удаляются сразу, каждое удаление — строкой «что защищал → где покрыто / почему не нужно».
- Образец сквозного сценария (TST-09: по одному на канал и мессенджер, поверх каналов — [channels-story.test.ts](../../acceptance/channels-story.test.ts): один файл, семь сценариев на двух каналах и общем мире `acceptance/support/`) — [conversation-story.test.ts](../../packages/chat-ui/testing/conversation-story.test.ts): приложение `ExampleApp` из `dmg-core/testing/example`, сервер, беседа мессенджера на двух подставных мессенджерах, два пользователя.

## 10. Добавить вид в учебный проект

Памятка для учебного проекта `packages/example/src` ([D-UI-121](../decisions.md)): куда положить экран, сторис или уведомление и где их зарегистрировать. Обозначения: `UI` — `platform/ui/`, `FE` — `frontend/`, `R` — `runners/`; `<m>` — имя UI-модуля, `<story>` — папка сторис. Образец каждого шага — модуль `profile` (раздел из одной сторис с переходом во вспомогательный модуль `users`).

1. **Описание.**
   - Файл — в `UI/<m>/<story>/`; экран двух сторис — в `UI/<m>/shared/`.
   - Запись — в `UI/<m>/<m>.ui-module.ts`; новый модуль — ещё в `UI/example-ui.set.ts`.
   - Имена Def — в `UI/index.ts` и во вход `packages/example/index.ts`, если их берут тесты других пакетов.
2. **Достижимость (UI-07).**
   - Экран открывается действием-переходом (`to`) с экрана сторис приложения, сторис — связью `leads` (UI-24), а не новым входом приложения.
   - Вход приложения — только для адреса снаружи; тогда к нему нужны точка входа CH-02, маршрут PG-02 и меню Telegram.
3. **Граница модулей.**
   - В чужой модуль ведут только на `start` его сторис: переход действия (UI-03 вместе с UI-35), цель-адрес исхода и ссылка уведомления (UI-36).
   - Модуль, в который ведёт один модуль, — вспомогательный с единственным пользователем: нужен второй пользователь, или сторис переезжает к единственному (UI-37).
   - Связи из меню (корневой сторис набора) не в счёт: модуль, открытый только из меню, — раздел.
4. **Код.**
   - Код экрана — `FE/<m>/logic/<story>/<экран>.scode.ts` (путь зеркалит описание), уведомления — `.ncode.ts`; загрузчик — в `FE/<m>/logic/<m>-codes.ts`, вход оболочки — `FE/<m>/logic/index.ts`.
   - Подмена для тестов — `<M>CodeOverrides` в `<m>-codes.types.ts`; новый модуль — ещё в пересечении `ExampleCodeOverrides` (`R/example-codes.types.ts`).
5. **Представления.**
   - `chat`: `FE/<m>/chat/<story>/<экран>.view.ts` и запись в `FE/<m>/chat/<m>-chat.views.ts`.
   - `web`: `FE/<m>/web/<story>/<экран>.view.ts` и запись в `FE/<m>/web/<m>-web.views.ts`.
   - Telegram — только перекрытие (`FE/<m>/telegram/`), иначе показывает база `chat`.
   - Текстовые страницы — `packages/web-ui/testing/text-views/` (`<m>-pages.views.ts`; место — долг DEBT-UI-42).
   - Вход канала модуля для оболочки — `index.ts`; кирпич для соседних модулей — `public.ts` (образец — `FE/users/chat/public.ts`); кирпич без хозяина — `FE/<канал>-kit/`.
6. **Новый модуль — пять сборок.** Реестр модуля добавляется в каждую:
   - `R/example-codes.ts`;
   - `R/dialog/example-dialog-views.ts`;
   - `R/tg-bot/example-telegram-views.ts`;
   - `R/web/example-web-views.ts`;
   - `packages/web-ui/testing/text-views/example-pages.views.ts`.

   Каждая сборка отбирает реестры фильтром `ModuleRegistries.required(app)` по месту: модуль вне приложения в сборку не попадает (UI-06).
7. **Приложения UI.** Сторис — в `stories` нужных `R/*/*.ui-app.ts`. Сторис, в которую ведёт включённая, но в приложение не вошедшая, отрезана (`omits`): ядро её действие не показывает.
8. **Примеры.** Примеры (`examples`) меряет CH-01 автоматически (`ExampleLimits` в `R/dialog/example-dialog-views.test.ts`); снимок — тестом в `R/<r>/example-*-views.test.ts`, если вид важен.
9. **Проверка — `bun run check`.**
   - `arch:check` проекта — `R/*/example-*.arch.test.ts` (правила графа и слоёв фронта);
   - `NM-01` — `checks/repo-file-names.test.ts`;
   - UI-06 — конструкторы сборок.

   Тесты состава считают свойства набора, а не узлы: упавший тест с числом узлов — дефект теста, а не повод вписать новое число.
