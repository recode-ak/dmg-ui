# Пакет канала — гайд

**Назначение:** что должен дать пакет канала (мессенджер, страница, консоль), как собрать его поверх ядра `dmg-ui`, какие политики выбрать по исходам, как встроиться в граф и где проходит граница безопасности. Образцы — беседа мессенджера, вход `dmg-ui/chat-ui` ([packages/chat-ui/src/conversation/](../../packages/chat-ui/src/conversation/conversation.ts); учебный диалог — фасад над ней для доставки уведомлений и снимка экземпляра), и учебный страничный канал, вход `dmg-ui/web-ui` ([packages/web-ui/src/](../../packages/web-ui/src/server/page-host.ts)). Объявление экранов — [story-screen-notification.md](./story-screen-notification.md).

---

## 1. Когда применять

- Нужно показать сторис, экраны и уведомления набора UI в конкретном канале: бот, веб-страница, терминал, агент.
- Ядро не знает каналов: у него нет `interface Channel` (D-UI-17). Контракт канала — порты, которые зовёт ядро (`CallerSource`, `RecipientCallers`, `NotificationDelivery`, `UiObserver`), и объекты, которые ядро отдаёт (`ScreenRuntime`, `ScreenInstance`, `InstanceView`, исходы).
- Объявление экранов и кода — другой гайд ([story-screen-notification.md](./story-screen-notification.md)).

## 2. Что канал обязан дать

1. **Представления** экранов и уведомлений: вид (`InstanceView`, в типах экрана — `ScreenViewOf<D>`) в разметку канала. Ядро ничего не рисует. У беседы мессенджера — реестр `ChatViews` (раздел 5).
2. **Сбор входа** действия по полям (`ActionView.fields`: подпись, признак необязательности, варианты, начальные значения) и показ подтверждения и отказов.
3. **Личность и её место**: как человек канала становится `Caller` и откуда берётся его место `Place` (язык и пояс) — порт `PersonPlaces.place(uuid, trace)`, источник места (профиль, язык транспорта) — дело проекта. Место — того, кто работает (личность транспорта), а не замещаемого. `RenderContext` из места и признаков `delegate`, `readOnly` собирает `RenderContexts` (D-UI-41).
4. **Хранение** открытых экранов и их состояния (`ScreenInstance.snapshot()` / `ScreenRuntime.restore`); куда вести, если адрес не восстановился. Образец — снимок беседы `ConversationSnapshot` за портом `ConversationStore` (D-UI-45): экран, отпечаток показанного вида, живое место, путь переходов, черновик, таблица ссылок; фасада учебного диалога над беседой нет (D-UI-48).
5. **Точки входа** — команда, маршрут, ссылка — на входы, которые объявило приложение UI; в графе — свой вид узла (раздел 5, п. 2).
6. **След**: на каждый входящий сигнал канал рождает `Trace.fromRequest({ requestId, channel })`.
7. **Политику по исходам** действия (раздел 4) и **доставку уведомлений** (раздел 9).
8. **Граф**: ребро `presents` и, если нужно, свои виды узлов и правила (раздел 5).

## 3. Сборка

Все импорты — из публичных входов: `dmg-ui`, `dmg-ui/server`, `dmg-ui/graph`. Пакет канала лежит в `packages/<имя>/` и видит соседей только по имени входа; канал поверх `chat-ui` (как `tg-bot`) берёт общую модель беседы из `dmg-ui/chat-ui`. Оттуда же ему нужны сообщение, порт мессенджера и возможности; подробности — в гайде «Пакет мессенджера», он появится позже. Помощники тестов ядра для тестов канала — из `dmg-ui/testing/fixtures`.

1. **Код.** `CodeLoaders` (реестр загрузчиков набора) создаёт корень сборки; образец — `exampleCodes()`. Загрузчики другого набора — бросок при сборке.
2. **Сервер.** Один на набор: `new UiServer({ set, dispatch, context, nodes? })`. `dispatch` — бэкенд вызова UC: `new ApiAppDispatch(api)` в одном процессе или `new ModuleApiDispatch([...apis])` для модулей вне процесса; `context` — `{ bus, logger }` приложения; `nodes` — узлы канала (`ChannelNode`: `id`, `uses`, `listens`).
3. **Сессия личности.** `server.session(source)` даёт `UiSession`: она же `UcPort` и `RefreshPort` для исполнителя. `CallerSource`: `subjectId` (субъект для сопоставления событий; у заместителя — замещаемый), `channel` (канал следа), `resolve(trace)` → `Result<Caller>`; порт канал реализует сам. Образец — узел бесед ([conversations.ts](../../packages/chat-ui/src/conversation/conversations.ts)).
4. **Исполнитель.** `new ScreenRuntime({ set, codes, ucs: session, refresh: session, observer })`. Дальше `open(address, { context, trace })`, `restore(json, options)`. Контекст рендера — `new RenderContexts(callers, places).of(uuid, trace)`: место из `PersonPlaces`, признаки — `RenderFlags` вызывающего (`RecipientCallers`); вызывающий не разрешился — `delegate` и `readOnly` `false`. Канал вправе собрать `{ locale, timeZone, delegate, readOnly }` и сам через `RenderFlags.of(caller.value)`. Снимок с ревизией больше `2³¹ − 1` `restore` отвергает отказом `malformed` (D-UI-42).
5. **Уведомления.** `new UiNotifier({ app, codes, dispatch, callers, delivery, observer, context }).start()`; `callers` — `RecipientCallers` (`resolve(uuid, trace)` → `Result<Caller>`), `delivery` — `NotificationDelivery.deliver(notification)`. Запуск один: повторный `start()` без остановки бросает, подписка одна на приложение; `start()` возвращает отписку — храни её.
6. **Наблюдатель.** `UiObserver.record(entry)` синхронный и не бросает; в записи нет входа, данных и payload. Для тестов — `MemoryUiObserver`.

Две части канала (D-UI-16): исполнитель экранов (клиент, `dmg-ui`) и серверная (`dmg-ui/server`). Между ними только JSON (раздел 6). Исполнитель не тянет `dmg-core/app` и `/graph`, поэтому работает в браузере.

```ts
const server = new UiServer({ set: ExampleUiSetDef, dispatch: new ApiAppDispatch(example.api), context });
const session = server.session(identity.source());
const runtime = new ScreenRuntime({ set, codes, ucs: session, refresh: session, observer });
const instance = await runtime.open(address, { context: renderContext, trace: trace.toJSON() });
```

## 4. Политики по исходам

Исход `act` решает канал; ядро только сообщает. Неизвестный исход (новый в ядре) — дефект канала, бросок (ERR-06). Беседа ([conversation-outcomes.ts](../../packages/chat-ui/src/conversation/conversation-outcomes.ts), метод `settle`) показывает тремя способами:

- **в место** — в живое место, на месте или новыми (раздел 5, D-UI-51); текст перед видом — первым абзацем первого сообщения;
- **заметкой** — новое сообщение вне места; доставленная заметка сбивает положение;
- **реакцией** — у мессенджера с ответом на нажатие (`capabilities.pressAnswer`) текстом ответа, без сообщения и без сдвига положения; иначе заметкой (D-UI-54).

| исход | что показывает беседа | как |
|---|---|---|
| `moved` | экран `address` новым экземпляром, прежний закрыт; адрес не декодирован — заметка «Прежний экран не восстановлен…» и вход «в начало» | в место |
| `stayed` | вид заново (ревизия выросла) | в место |
| `exited` | вход «в начало» (по умолчанию `start`), текст выхода (подпись и описание из Def) — перед видом входа, одним показом | в место |
| `confirm` | вопрос «подпись\n\nописание» с «Да» и «Нет»; «Да» повторяет `act` с `confirmed: true`, «Нет» — вид снова | в место (шаг) |
| `rejected` | идёт сбор входа и поле из первого замечания есть — вопрос этого поля с текстом замечания; иначе — вид с текстом замечания | в место (шаг или вид) |
| `refused` | вид с текстом отказа; у `caught` — свой текст представления | в место |
| `stale` | вид (он уже на новых данных) с «Экран обновился.» | в место |
| `unavailable`: `disabled`, `readOnly` | «Действие сейчас недоступно.» | реакцией |
| `unavailable`: `closed` | «Экран уже закрыт.» | реакцией |
| `unavailable`: `unknown` | дефект беседы, бросок; на нажатие — ответ без текста | — |

Локальное действие: `changed` — вид, `rejected` — как выше, `refused` — вид с текстом отказа (экземпляр прежний) — всё в место; `unavailable` — как у действия.

Кроме исходов:

- **Вид в отказе** (загрузка не удалась, `status: 'refused'`) — в место, представление не вызывается: текст отказа (у `caught` — текст представления), варианты «Повторить» (тот же адрес заново, путь прежний), «Назад» (путь не пуст), «В начало» (вход «в начало», путь сброшен).
- **Реакции на нажатие:** неизвестная ссылка — «Такого варианта нет.»; ссылка не живого экрана (действие, локальное, подтверждение, «Ещё», «Назад») — «Экран уже закрыт.»; шаг сбора входа без черновика — «Действие сейчас недоступно.». Устаревшая ссылка локального действия — вид с «Экран обновился.», шаг чужого поля при живом черновике — вопрос заново с «Действие сейчас недоступно.» — в место. На каждое нажатие — ровно один ответ, последней операцией сигнала.
- **Сигналы, не нажатия:** `enter` — вход приложения (неизвестный — заметка «Такого входа нет.»); `text` — текущему полю или основному действию, без живого экрана — вход «в начало»; `cancel` — сброс черновика («Ввод отменён.») и вид; `attachment` — заметка; `back` — раздел 5.

Страничный канал отличается тем, что экранов несколько (три области: `main`, `side` — панель, `modal` — окно): `moved` открывает адрес в области назначения; `exited` в `main` ведёт на вход `start` с заметкой, в прочих областях — очищает область; `confirm` и `rejected` хранятся в области до следующего действия. Живого места, реакций и пути у него нет: всё показывается в области, `unavailable` — заметкой, и `unknown` тоже, а не броском; у `refused` нет отдельного текста для `caught`; адрес исхода, ссылки или «Повторить», который не декодировался, очищает область, а не ведёт на вход ([page-client.ts](../../packages/web-ui/src/client/page-client.ts), метод `settle`); URL страницы, который не разобрался (`route`), ведёт на вход `start` с заметкой «Страница не найдена» (D-UI-76). «Один живой экран» — политика беседы, а не ядра. Ожидаемый итог жеста (раздел 5) снимается по исходу до политики: отказ показывает исходный вид с заметкой, а не итог с заметкой (D-UI-84).

Куда открыть переход, решает канал, а не экран и не приложение UI (D-UI-78): приложение страниц объявляет `PageClientSpec.placements` (`{ screen, region }`), без объявления — умолчание по положению: из `main` в `side`, из `side` и `modal` в `main`, ссылка уведомления — в `side`; тот же экран остаётся на месте. Закрыть `side` или `modal` — `PageClient.close(region)`: область пуста без заметки, подписка снята; `main` закрыть нельзя (тип). Окно — временная область: уход из него переходом закрывает его после открытия назначения. Остальные области при открытом окне клиент не блокирует — блокировку и Esc даёт представление.

Форма (D-UI-79): `PageFormModel(set).of(state)` строит из состояния области формы действий и локальных действий — подписи из Def, варианты и начальные значения из вида, введённое и замечания по полям; чистая функция, не бросает. Отвергнутый вход возвращается состоянием: `issues` и `entered` (форма и введённые значения, данные JSON, в снимок не входит); следующее действие области их снимает. Подтверждение — свойство действия: форма несёт `confirm`, нажатие идёт исходом `confirm` и `confirm(region)`. Представление возвращает намерения методами клиента (`submit`, `submitInput`, `local`, `confirm`, `retry`, `close`, `openLink`, `route`). Жест — `submitInput(region, action, input, revision, expected?)`: готовый вход (значение варианта, а не подпись) и обязательная ревизия вида, по которому нарисована цель; устаревшая — исход `stale`; `expected` — показ до ответа (ниже, D-UI-84). Вложенность экранов ядру не нужна: вкладка — параметр экрана или состояние, независимые части — отдельные экраны в областях (D-UI-80); представление области выбирает представление экрана по `state.view.screen`.

Состояние области страничный канал строит сам, вид экземпляра ядра для этого не расширяется (D-UI-70): `PageViewState` со статусом `empty | loading | ready | refused`, признаками `refreshing` и `stale` и отметками ([page-view-state.types.ts](../../packages/web-ui/src/view/page-view-state.types.ts)). `loading` — от начала открытия до экземпляра: прежний экземпляр снимается в начале открытия, действий по старому экрану нет, а из двух открытий в область побеждает последнее начатое (экземпляр опоздавшего закрывается, исход действия ушедшего экземпляра область не трогает). Отказ открытия оставляет область пустой с заметкой «Экран недоступен», отказ уходит вызывающему. `refreshing` — от сигнала своего порта до `settled()` экземпляра (D-UI-49); сигнал сопоставляется с областью по адресу. Исход `stale` даёт `stale: 'revision'` с заметкой «Данные обновились»; отметку заменяет следующий исход или открытие ([page-regions.ts](../../packages/web-ui/src/client/page-regions.ts)). Без связи (D-UI-74) каждая непустая область получает `stale: 'offline'` (важнее `revision`; у пустой пометки нет) и держит его, пока не перечитана по новому соединению. Действия такой области отключены — исход `unavailable: 'disabled'` без исполнителя; отказ действия, прерванного обрывом, — заметка «Связь прервалась — результат будет виден после переподключения» вместо текста отказа. Переход без связи ждёт соединения: область в `loading` с пометкой, прежний экземпляр снят, вызовов нет.

Подписи действий и выходов канал берёт из Def: `UiIds.findScreen(id)` даёт `AnyScreenDef` с `actions`, `locals` и `exits` (у каждого `label`); `normalize()` для этого не нужен. Уведомление набора по `id` — `UiIds.findNotification(id)` (чужой `id` и `id` экрана дают `undefined`).

## 5. Представление, показ и граф

Образец представлений — беседа мессенджера ([view/](../../packages/chat-ui/src/view/screen-presenter.ts), D-UI-50). Страничный канал отдаёт представлению источник вида и цель показа (D-UI-70): `ViewSource<PageViewState>` (`get()` и `subscribe`, который зовёт слушателя сразу текущим значением; значение неизменяемо) и `PageRegionPresenter<Target>` — `show(source, target)` возвращает отписку, устройство цели пакет не знает ([page-region-presenter.types.ts](../../packages/web-ui/src/view/page-region-presenter.types.ts)). Монтирует приложение: `presenter.show(client.source('main'), target)`. Образец — текстовое представление `PageTextPresenter` ([page-text-presenter.ts](../../packages/web-ui/src/view/page-text-presenter.ts)). Представления страничного канала живут в зоне `src/view/`: не видят клиента, провода, сервера и графа, глобалов браузера и среды у них нет.

**Показ до ответа** (D-UI-84). Жест и «Да» принимают ожидаемый итог — функцию представления `PageExpected = (view) => данные`: `submitInput(region, action, input, revision, expected)`, `confirm(region, expected)`. Итог зависит от входа замыканием (`(view) => ({ ...data, tasks: … taskId … })`), экран его не объявляет, мессенджеры его не видят. Клиент проверяет итог схемой данных экрана и показывает её выход: `client.source(region)` отдаёт состояние с `view.data` итога и `expected: true`, ревизия, адрес, действия и отметки — от области; текст области — «Ждём ответа…» перед видом. Итог снимается по исходу и сразу, как только область перестала быть готовой той же ревизии того же экземпляра: перечитывание, обрыв (`stale: 'offline'`), переход, закрытие, «Назад»; снятый не возвращается. Пока итог показан, действия области недоступны (`unavailable: 'disabled'`, у `PageFormModel` — `available: false`), локальные — доступны; соседняя область не ждёт. Итог не по схеме или бросок функции — показа нет, вызов уходит, в `faults` — фиксированный текст. История, снимок и URL итога не видят: они читают область, а не производный источник.

**Представление экрана** пишется один раз на общей части. Оно получает вид в типах экрана и набор показа `ViewKit` и возвращает одно сообщение или список (`ViewOutput`): текст и варианты-намерения `ViewOption` без ссылок — `action`, `local`, `back`, `retry`, `home`; ссылки ставит беседа.

- `ScreenPresenter.for(def, text, caught?)` — короткая форма: текст тела по виду, варианты по умолчанию, свои тексты отказов по коду из `catches`.
- `ScreenPresenter.of(def, { render, caught?, history? })` — полная: `render(view, kit)` даёт сообщение или список, `history` — след в истории.
- `ViewKit`: `capabilities` мессенджера (уложиться в лимиты — дело представления, `TextTrimmer` и `TextSplitter`; не уложилось — режет страж, D-UI-39), `options` — варианты по умолчанию (доступные действия, затем локальные, подписи из Def, «Назад» последним, если путь не пуст), `message(text, options?)` — одно сообщение.
- Варианты — только у последнего сообщения и только из вариантов по умолчанию, без повторов и пустых подписей; подписи и порядок — представления: «Назад» можно скрыть, переставить, переподписать. Сообщений — от 1 до 32. Нарушение — дефект представления, бросок с id экрана без данных вида.
- Вид в отказе и шапку (заместитель, «только чтение» — первым абзацем первого сообщения) собирает беседа, представление их не видит.
- `NotificationPresenter.for(def, render)` — текст уведомления по его данным.

**Акцент, момент и перекрытие.** Вариант может нести нейтральный `accent` (`primary`, `positive`, `danger`), фрагмент текста — `moment` (секунды Unix и вид показа; `text` фрагмента — запасной, его показывают мессенджеры без даты): представление выставляет их, мессенджер переводит в свои поля или опускает (Telegram: `style` кнопки и сущность `date_time`). Представление под один мессенджер перекрывает общее по `id` через `ChatViews.over`; на учебном примере — `exampleTelegramViews` (`dmg-ui/tg-bot/testing`, D-UI-67), остальные экраны остаются общими.

```ts
import { ChatViews, ScreenPresenter } from 'dmg-ui/chat-ui';
import { ExampleUiSetDef, TaskCardScreenDef } from 'dmg-ui/testing';

const CardView = ScreenPresenter.of(TaskCardScreenDef, {
  render: ({ data }, kit) => [
    kit.message(data?.title ?? TaskCardScreenDef.label, []),
    kit.message('Что дальше?', kit.options.filter((o) => o.kind !== 'back')),
  ],
  history: 'address',
});
const views = ChatViews.of(ExampleUiSetDef, [TaskListView, CardView]);
const own = views.over([OwnCardView]); // реестр приложения своего мессенджера
```

**Реестр** `ChatViews.of(set, presenters)` — представления одного приложения мессенджера по `id`; Def вне набора и два представления одного Def — бросок. `over(presenters)` даёт новый реестр, где представления пакета мессенджера перекрывают общие по `id`; прежний не меняется. Узел бесед обслуживает одно приложение и получает свой реестр (`ConversationsSpec.views`). `presented()` — `id` общих и перекрытых без повторов, для рёбер `presents`.

**На месте или новым** (D-UI-51). Живое место — сообщения последнего показа живого экрана или его шага: вида, вопроса поля, подтверждения, страницы «Ещё». Показ правит место на месте (`update`), если оно последнее в беседе, число сообщений совпало и место не защищено следом; иначе прежнее последнее сообщение места с вариантами уходит (`retire` с последним содержимым и ссылкой нажатого) и показ идёт новыми (`show`). Положение сбивают доставленная заметка и любой сигнал собеседника, кроме нажатия; проактивный показ (перечитывание по событию) — в место, по инициативе. Мессенджер без правки на `update` шлёт новое: ветки в беседе нет. Место хранится в снимке живого экрана.

**След в истории** (D-UI-52). `history: 'address'` или функция вида (шаг урока) — ключ следа. Место с видом экрана со следом правит только вид того же живого экрана с тем же ключом, по положению; смена ключа, уход на другой экран или шаг — прежнее сообщение остаётся в виде «после ухода», показ идёт новым. Листание «Ещё» — тот же ключ. В снимке — SHA-256 ключа: он может быть данными собеседника.

**Путь и «Назад»** (D-UI-53, [conversation-path.ts](../../packages/chat-ui/src/conversation/conversation-path.ts)). Путь — снимки экземпляров ядра (адрес, состояние, ревизия) экранов, с которых беседа ушла на другой экран: исход `moved` или ссылка `open`. Переход на тот же экран (страница списка, «Повторить») путь не растит; на экран из пути — путь обрезан до него, цель открывается заново. Путь меняется только после успеха: переход — когда экземпляр цели открыт, «Назад» — когда `restore` ответил; бросок порта путь не трогает. Путь сбрасывают вход приложения, «В начало», выход сторис и невосстановленный экран. «Назад» — сигнал `back` (его строит мессенджер) или вариант `back` живого экрана: черновик сброшен, верхний элемент поднимает `ScreenRuntime.restore` — тот же адрес и состояние, свежие данные, новый номер экрана (ссылки прежнего показа — «Экран уже закрыт.»); не восстановился — заметка и вход «в начало». Путь пуст — живой экран снова. Сигнал `back` — не нажатие: ответа нет, положение сбито. Экран о пути не знает.

**Граф.** Канал — второй поставщик графа: `implements GraphProvider` (`node_modules/dmg-core/docs/guides/graph-extension.md` — шаги вида Def, видов и правил; здесь только отличия UI).

1. **Ребро `presents`.** Приложение UI `presents` каждый экран и уведомление, у которых в канале есть представление; ставит его пакет канала (`UI_EDGE_KINDS.presents`, `UiIds.app(app)` — откуда, `UiIds.screen/notification` — куда). Без него срабатывает UI-06. Образец — [chat-graph-provider.ts](../../packages/chat-ui/src/graph/chat-graph-provider.ts) (D-UI-57): один поставщик `dmg-ui-chat` на все приложения мессенджеров, рёбра — от `ChatViews.presented()` реестра каждого приложения; под приложением — узел возможностей мессенджера `chatMessenger`, узлы входов беседы `chatEntry` с ребром `chatEnters` к экрану входа и точки входа `chatEntryPoint` (п. 2). Спека обязательно получает `examples` — примеры набора, собранные заранее (`await ChatExamples.collect({ set, codes })`, D-UI-58): `check` правила синхронный, а вид экрана по примеру — `Promise`.
2. **Свой вид узла** — точка входа канала. Достижимость экранов ядро считает от входов (UI-07), поэтому вход должен быть объявлен в `entries` приложения.
   - Страничный канал: `PageRouteDef` — вид Def `pageRoute` (шаблон пути и имя входа приложения), узел под приложением, ребро `opens` к экрану входа. Манифест лежит в `src/url/` ([page-route-def.ts](../../packages/web-ui/src/url/page-route-def.ts)): он нужен и графу, и клиенту. Путь — шаблон: `/`, неизменяемые сегменты `[a-z0-9-]+` и параметры `:имя` экрана входа (D-UI-76).
   - Мессенджер: пакет мессенджера передаёт точки в `ChatAppSpec.entryPoints` — `{ entry, via, key }`, где `entry` — имя входа приложения, а `via` (способ) и `key` (что вводит или нажимает человек) — его слова, `chat-ui` их не трактует. Поставщик `dmg-ui-chat` ставит под приложением узел `chatEntryPoint` (`<app>/point-<вход>-<n>`, `n` — с 1 внутри входа, свойства `{ entry, via, key }`) и ребро `chatOpens` на узел `chatEntry` (имя `opens` занято страничным каналом: виды рёбер общие на граф). Точка на вход, которого нет у приложения, — бросок сборки; вход без точки — CH-02. Проверять значения `via` и `key` — дело правил пакета мессенджера: у Telegram это `command`, `menu`, `link` (`TELEGRAM_VIA`) и правила TG-01…TG-06 поставщика `TelegramGraphProvider` ([D-UI-64](../decisions.md)).

   ```ts
   new ChatGraphProvider({
     apps: [{ app: ExampleDialogAppDef, views, capabilities, entryPoints: [
       { entry: 'start', via: 'message', key: 'start' },
       { entry: 'assigned', via: 'message', key: 'assigned' },
     ] }],
     examples,
   });
   ```
3. **Свои правила — свой префикс** (ARC-13): префикс не из префиксов пакета `dmg-core` и не `UI`. У страничного канала — `PG` (PG-01 — маршрут ведёт на объявленный вход, PG-02 — у входа есть маршрут, PG-03…PG-07 — шаблоны, пересечения и параметры маршрутов и экранов, повторяют проверки сборки `PageUrls` без броска), у общей части мессенджеров — `CH` (CH-01 — пример экрана и уведомления укладывается в лимиты мессенджера своего приложения, CH-02 — у входа беседы есть точка входа, CH-03 — сигнал или реакция сообщества только в приложении мессенджера, который их умеет; [rules.md](../reference/rules.md)). Правило читает граф запросами (`outgoing`, `children`), не ветвится по виду Def; то, чего в графе нет (виды примеров), получает в конструктор. Новый префикс репо — в список `RULE_PREFIXES` проверки `RuleCatalog`.
4. **Вызов UC из узла канала** (сигнал канала, не действие): узел объявляет `uses` и `listens` как `ChannelNode`, а ребро `invokes` ставит канал. Правило UI-10 защищает такие узлы, если у них есть ребро `refreshedBy` или `notifiedBy` к событию: граф ядра узлов канала не строит, и это ребро тоже ставит канал. Такие узлы не вызывают command UC по событию. `ChannelNode` — для прочих каналов; у мессенджеров сигналы и реакции сообщества объявляются манифестами `chat-ui` в `ChatAppSpec.community` (D-UI-60): сигнал `{ name, label, description, signal, uc, input, strangers? }` вызывает command UC (`input` — поле входа → `community` или `person`), реакция `{ name, label, description, event, uc, input, operation, targets }` по событию читает query UC (`input` — поле входа → поле payload) и берёт цель операции из полей выхода `targets`. Поставщик `dmg-ui-chat` ставит под приложением узлы `chatSignal` (`<app>/signal-<имя>`) и `chatReaction` (`<app>/reaction-<имя>`) и рёбра ядра `invokes`, `notifiedBy`, `reads`; манифест проверяет `CommunityManifest` (повтор или плохое имя, UC или событие вне приложения, пустые `input` или `targets` — бросок сборки), реакцию на command UC ловит UI-10, сигнал или операцию, которых мессенджер не умеет, — CH-03. Исполняет манифесты `Communities` (D-UI-59) — один на приложение мессенджера, с тем же объектом `community`: `receive(signal)` принимает сигнал мессенджера `{ id, kind, community, member? }` (handle группы и личность транспорта), `start()` подписывает реакции и возвращает отписку; операции — порт `messenger.community` (`exclude`, `invite`, `approve`; `inviteLink` — бросок сборки, DEBT-UI-25); переводы «мессенджер ↔ домен» — порты `people`/`members` и `keys`/`handles`.

## 6. Граница JSON и провод

Между исполнителем (клиент) и сервером — только JSON; клиент недоверен. Сервер сверяет каждый вызов сам (D-UI-28, D-UI-33).

- **Вызов UC** — простая команда `UcCall`: `{ module, uc, input, requestId }` или `{ …, eventId }`. Ни узла графа, ни следа, ни `Caller`. Сервер сверяет пару `(module, uc)` с объединением объявленного узлами сессии (`UcRoutes`), сам подставляет след и вызывающего. Command UC по `eventId` не исполняется.
- **Сообщения** страничного канала ([page-messages.types.ts](../../packages/web-ui/src/wire/page-messages.types.ts)): клиент → сервер `call`, `watch`, `unwatch`; сервер → клиент `hello`, `result`, `signal`, `watch-refused`, `notification`, `refused`. Схемы строгие: через провод не проходят след вызова и доставки, `caller`, `recipient` и payload события; сигнал несёт обезличенный след.
- **Порядок.** `watch` до `call` загрузки: подписка раньше чтения не пропускает событие между ними. Провод обязан быть упорядоченным в каждую сторону (WebSocket такой; независимые запросы HTTP — нет).
- **Личность — по пропуску соединения** (D-UI-72). До открытия сокета ворота `PageGate` ([page-gate.ts](../../packages/web-ui/src/server/page-gate.ts)) проверяют запрос: `Origin` — точным совпадением с белым списком `origins`, пропуск — cookie с именем `cookie`, ровно одно вхождение, 1–256 символов; отказ (`origin` или `token`) привязка превращает в `403`. Затем `PageHost.connect(token, push)`: асинхронный порт `tokens` → `uuid` → сессия с вызывающим из `callers` (`RecipientCallers`, как у мессенджеров); клиент `uuid` не шлёт; `push` получает строки JSON, готовые к отправке (D-UI-71). Контекст рендера приходит в `hello` один раз и собирается `RenderContexts` из `places` (`PersonPlaces`) по `uuid` токена — место того, кто работает; места по умолчанию нет. Неизвестный токен, сбой `tokens` или `places`, предел соединений — `refused` (сбой порта — ещё и `error` без данных). Отзыв токена открытое соединение не рвёт.
- **Пределы** (константы: `MAX_CLIENT_TEXT`, `MAX_SERVER_TEXT` и `PAGE_CLOSE` в [page-wire.const.ts](../../packages/web-ui/src/wire/page-wire.const.ts), `MAX_ID` в `packages/web-ui/src/wire/page-messages.ts`, `MAX_LENGTH` в `src/server/client-input.ts`): строка клиента 64 Ки символов (65 536, до `JSON.parse`), строка сервера 1 Ми символов, 16 одновременных вызовов и 64 подписки на соединение, 8 соединений на личность, идентификаторы до 256 символов. Мусор и превышение у клиента — `refused`, не бросок (ERR-01); `warn` без данных клиента (ERR-07), на мусор, предел вызовов и каждый вид отказа подписки — раз на соединение (`watch-refused` клиенту — на каждый кадр). Строку сервера длиннее предела `PageOutbox` не отправляет: `result` заменяется отказом `SERVER_INTERNAL` с тем же `id`, уведомление отбрасывается, `warn` — раз на вид; клиент длинную строку не разбирает и рвёт соединение (D-UI-71).
- **Сокет** ([page-sockets.ts](../../packages/web-ui/src/server/page-sockets.ts), [page-socket-end.ts](../../packages/web-ui/src/client/page-socket-end.ts)). Кадр клиента до `hello` — нарушение протокола: закрытие кодом 4400; двоичный кадр — `refused: malformed` на каждый, `warn` — раз на сокет, соединение живо; отказ соединения — закрытие кодом 4403. Порт серверной половины после пуша `hello` разрешает `connect` без дальнейших `await` (`PageServerPort`, `PageHost` так и делает): иначе кадр честного клиента, ответившего на `hello`, мост примет за кадр до связи. Закрытие сокета освобождает доставку, подписки и сессию, в том числе если соединение ещё устанавливалось; новое соединение той же личности начинает с чистого места. Клиентский конец отличает отказ до `hello` от обрыва после; вид отказа — `PageDialFailure`: `refused` (закрытие кодом 4403), `closed` (иное закрытие; отказ ворот `403` сокет браузера видит как `1006` — так же, как недоступный сервер), `malformed` (первый кадр не `hello`), `timeout` (срок `hello` у переподключателя). Кадры после `hello` до первой подписки `onMessage` копятся (до 64, сверх — сокет закрыт и обрыв) и отдаются первому обработчику по порядку; `onBreak` — ровно один раз, опоздавший к обрыву обработчик зовётся сразу (D-UI-74).
- **Привязка к серверу сокетов** — у приложения, не в пакете: в пакете нет глобалов среды, сокет сервера проходит узкий тип `PageServerSocket` без адаптера; образец привязки на `Bun.serve` — [page-socket.test.ts](../../packages/web-ui/src/page-socket.test.ts). Без любого из пунктов ниже привязка небезопасна:
  - методы `PageSockets` передаются лямбдами (`open`, `message`, `close`): сервер сокетов не обязан звать их с `this`. Обработчик `close` обязателен: без него доставка, подписки и сессия закрытого сокета не освобождаются;
  - `data` при `upgrade` — только результат `gate.admit(request.headers)`: пропуск, собранный в обход ворот, обходит и проверку источника;
  - предел кадра (`maxPayloadLength`) — около `3 × MAX_CLIENT_TEXT` байт (до 3 байт UTF-8 на символ): меньше — честный кадр рвёт сокет раньше предела пакета, намного больше — сервер сокетов принимает лишнее до проверки длины;
  - очередь отправки — `closeOnBackpressureLimit: true` и `backpressureLimit` не меньше `3 × MAX_SERVER_TEXT` байт. Мост не смотрит, что вернул `send` сокета: без закрытия по пределу сервер сокетов после переполнения молча выбрасывает кадры (у Bun по умолчанию предел 16 МиБ, а закрытие выключено), и клиент, не читающий сокет, держит память сервера; с закрытием клиент получает обрыв, `result` и `signal` не теряются без следа;
  - предел частоты рукопожатий — у прокси перед сервером: таймеров в пакете нет, а каждое рукопожатие стоит вызова порта `tokens`;
  - заголовки запроса на `upgrade` (`Cookie`, `Origin`) в лог не пишутся.

  Простой мёртвого соединения закрывает сервер сокетов — таймеров в пакете нет.
- **Переподключение** (D-UI-74, [page-reconnector.ts](../../packages/web-ui/src/client/page-reconnector.ts)). `PageReconnector({ sockets, clock, random?, faults? })`: `connect()` — первая попытка сразу, дальше с паузой до `hello`; `follow(end, attach)` — после обрыва попытки с паузой, новый конец отдаётся `attach` раньше любого своего кадра, слежение за прежним концом снято; `close()` — попыток больше нет, текущий конец закрыт. Попытка — новый сокет и ожидание `hello` не дольше 10 с. Пауза перед попыткой `n` — от `d/2` до `d`, `d = min(30 с, 500 мс · 2^(n−1))`; после отказа `4403` — сразу верхняя ступень (неизвестный пропуск или предел соединений в цикле не повторяются); счёт сбрасывает только обрыв соединения, прожившего от `hello` не меньше 30 с (`RECONNECT.stableMs`): сервер, который принимает и сразу рвёт, получает растущую паузу. Бросок и отказ `attach`, бросок фабрики и подписки сокета уходят в `faults` и попыток не останавливают. Свой конец при работающем переподключателе (смена личности) — сначала `follow(next, attach)`, затем `client.attach(next)`: иначе закрытие прежнего конца переподключатель примет за обрыв и подменит конец своим. Новый конец вкладке — `PageClient.attach(end)`: живой прежний закрывается, контекст новых экземпляров — из нового `hello`, отложенные переходы открываются, а каждая область с данными прежнего соединения перечитывается восстановлением из снимка своего экземпляра — подписка, затем чтение, ревизия +1, прежний вид с `refreshing`, пока чтение идёт. Экземпляр, открытый с контекстом прежнего `hello` (конец сменился во время загрузки), помечен «нет связи» и перечитан так же. Сбой восстановления — область пуста с заметкой «Экран недоступен», в `faults` — запись с узлом канала и фиксированным текстом. Без связи порты отказывают вызов сразу и не шлют подписку, команда повторно не уходит никогда. Время — порт `PageClock` (`PageSystemClock` в браузере), разброс — порт `random` (по умолчанию `Math.random`). Образец привязки: `connect()`, затем `new PageClient({ …, end })`, затем `follow(end, (next) => client.attach(next))`.
- **Сигнал перечитывания** — без payload, след обезличен: `correlationId` — `eventId`. Настоящий след сессия помнит по `eventId` (не больше 256 выданных). Экземпляр ставит перечитывание в свою очередь сразу; дождаться его без таймеров канал может через `ScreenInstance.settled()` (D-UI-49).
- **Выход.** `exited.data` провод не пересекает: исполнитель на клиенте; JSON-формы выхода на проводе нет.
- **Адрес в URL** (D-UI-76, [page-urls.ts](../../packages/web-ui/src/url/page-urls.ts)). `PageUrls({ app, routes })` переводит адрес `main` в путь и строку запроса страницы и обратно, браузера не знает. Путь — маршрут (первый объявленный маршрут экрана, который выражает адрес в пределе длины; длинный — следующий маршрут) или общий путь экрана `/<модуль>/<экран>`; маршруты не пересекаются: два шаблона, совпадающие на одном URL (`/:s` и `/assigned`, `/p/:a` и `/p/:b`), — бросок сборки; прочие параметры — `имя=значение` в порядке схемы, без JSON. Виды параметров — строка, целое, булево по JSON Schema параметров; любой экран набора приложения страниц обязан выражаться URL, иначе — бросок сборки. Страж на примерах: каждый пример экрана набора проходит круг «адрес → URL → адрес», иначе бросок сборки с `id` экрана (ловит `v.transform`, которого JSON Schema не видит); экран без примеров страж не проверяет (DEBT-UI-34). Голый путь маршрута — ровно адрес входа (`/`, а не `/?page=0`); есть в URL хоть один объявленный параметр — адрес только из URL. Ключ запроса, которого экран не объявил, пропускается; ключи с `_` в начале — за каналом. Предел — 2048 знаков в обе стороны. Разбор `parse(url)` — `Result` с причиной `tooLong`, `malformed`, `unknownPath` или `invalidParams`; сборка `url(address)` — строка или `undefined` (одиночный суррогат, управляющий знак — разбор его отверг бы, длина), бросок — экран вне набора или значение не того вида. Правила `PG-03…PG-07` повторяют проверки сборки в `arch:check` без броска (D-UI-77).
- **Состав областей в ссылке** (D-UI-78, [page-layout-urls.ts](../../packages/web-ui/src/url/page-layout-urls.ts)). Кроме `main`, в ссылку ложатся области из `PAGE_LINKED_REGIONS` (по умолчанию `side`) ключами `_side`, `_modal`: значение — вложенный URL области, закодированный целиком. Ключи — замкнутый список, чужие метки (`_ga`) пропускаются; вложенный URL разбирается тем же `PageUrls.parse` один раз, резервный ключ внутри — `malformed` у этой области; предел 2048 — на всю строку, не влезшая область пропускается, а не отказывает ссылке. Резервные ключи читает небросающий `PageUrls.pairs`. `PageClient.url()` отдаёт ссылку по текущим областям, `route(url)` открывает `main` и прочитанные области и не трогает те, которых в ссылке нет.
- **История и перезагрузка** (D-UI-81, [page-history.ts](../../packages/web-ui/src/client/page-history.ts), [page-browser-history.ts](../../packages/web-ui/src/client/page-browser-history.ts)). Порт `history` в сборке клиента (`PageHistoryPort`: `current`, `push`, `replace`, `onTraverse`); в браузере — `new PageBrowserHistory(window)`, окно присваивается узкому типу `PageBrowserWindow`. Первая загрузка и перезагрузка — `client.boot()` (не `route`): области по текущей записи истории, без новой записи. Шаг — новая запись — начинают переход по исходу `moved` (вместе с очисткой окна), `exited`, `openLink`, `route` (ссылка внутри страницы) и `close`; любое изменение адресов областей в ходе перехода — одна запись, прочие изменения адресов или состояния переписывают текущую (не ревизия, не пока область грузится). «Назад» и «Вперёд» ставят области по URL записи (главнее) и её снимку: тот же адрес — область не тронута, нет ни в URL, ни в записи — закрыта, окно и панель вне ссылки — из записи; без связи переход отложен. Запись — строка JSON `{"version":1,"regions":…}` со снимком областей; слот длиннее 8192 знаков не пишется, запись длиннее 32 768 не разбирается. Ссылка без своего URL не строится — история не пишется (`PageLayoutUrls.own`): свой URL начинается ровно с одного `/` и состоит из печатных знаков ASCII (табуляцию и перевод строки браузер вырезает). Что переживает перезагрузку и закрытие вкладки — таблица D-UI-83.

Обходы мест, где контракт ядра пока не закрыт:

- **Повтор загрузки и перечитывание без события** — открыть адрес заново (`open`) или восстановить экземпляр из его снимка (`ScreenInstance.snapshot()` → `ScreenRuntime.restore`, подписка раньше чтения — у ядра); своих команд «повторить» и «перечитать» у экземпляра нет.
- **`moved.address`** — внешние данные: `AddressCodec.decode`, отказ — вход приложения, не бросок.
- **`UiSession.watch` с недекодируемым адресом бросает** — ловит канал, подписка отклоняется (`watch-refused`).
- **`on` узла канала** (`UiSession.on(node, def, handler)`) — вне ядра: сверяет только, что узел объявил событие; обработчик получает события всех людей, отсева по `subjectId` нет — фильтрует канал. Мессенджерам он не нужен: сигналы и реакции сообщества — `Communities` (§5 п. 4).

## 7. Безопасность для автора канала

Граница доступа — Policy UC и `callers` (D-UI-29), а не свойства вида.

- **`available`, `confirm`, `readOnly` — не граница.** Клиент вправе прислать любой `call`. `readOnly` отключает действия исполнитель на клиенте; сервер отказывает только по Policy UC.
- **`trace` доставки получателю не показывай:** в нём настоящий `correlationId` инициатора.
- **В текст ошибки доставки данные не клади:** сбой `deliver` попадает в `logger.error` вместе с `message` броска. Бросок кода уведомления и сбой UC получателей пишутся в лог без `message` — только этап и имя ошибки, как у экрана и вызова UC.
- **Ожидаемый итог** (D-UI-84) — код представления, а не внешние данные: в вид идёт только выход схемы данных экрана, сбой итога — в `faults` фиксированным текстом без итога, данных и броска функции; в запись истории, снимок и URL итог не попадает.
- **Строки клиента экранируй при показе:** `OPERATION_NOT_FOUND` отражает `module` и `uc` клиента (до 256 символов).
- **`correlationId` клиента — заявление,** а не доказательство; доверенный только тот, что собрал сервер.
- **Запись `refresh` без `subject`** — оракул: подписчик узнаёт, что событие с такими параметрами случилось у кого-то. Для личных данных задавай `subject`.
- **Различимость отказов.** «Нет» (`TASK_NOT_FOUND`) и «не твоё» (`ACCESS_DENIED`) не показывай по-разному там, где идентификатор угадывается.
- **`InputRejection.issues[].text`** (`FieldIssue.text`) повторяет введённое значение (сообщение схемы): показывай его только автору значения; свои тексты — лучше эха valibot (DEBT-3 `dmg-core`, [debt.md](../../debt.md)).
- **Личность.** `uuid` в сессию попадает только из аутентифицированного транспорта, не из данных запроса. У беседы единственный источник — порт `people(sender)`: отправитель без личности и чужая личность беседу не трогают.
- **Пропуск страничного канала** (D-UI-72) — в cookie, недоступной скрипту страницы (`HttpOnly; SameSite=Strict; Path=/`). Под HTTPS — ещё `Secure` и имя с префиксом `__Host-` (например, `__Host-dmg_page`): без префикса соседний поддомен ставит свою cookie с тем же именем, и ворота получают повтор имени или подсунутый пропуск. Токен — не меньше 128 случайных бит криптостойкого генератора в base64url, не `uuid` и не производное от него. `Origin` обязателен и сверяется точно: без проверки чужая страница открыла бы сокет с cookie человека. Элемент `origins` — в той форме, в какой браузер шлёт `Origin`: `схема://хост[:порт]`, схема и хост в нижнем регистре, без пути и косой черты в конце, порт — только нестандартный (`https://school.example`, `http://localhost:3000`); пустую строку, `'null'` и неканонический элемент `PageGate` отвергает броском при сборке. Токен, cookie и значение `Origin` в лог и след не идут; отказ ворот значений не несёт.
- **Снимок беседы — доверенные данные** хранилища приложения: в нём собранный вход и подписи. Схема (`ConversationSnapshotSchema`) отсекает мусор, а не подделку; снимок от клиента не принимай.
- **URL — внешние данные** (D-UI-76). Разбор не бросает ни на какой строке, длина проверяется первой, регулярные выражения — без вложенных повторов. Сегмент, ключ и значение декодируются один раз, `+` — не пробел, `..` не разрешается молча — поэтому не `URLSearchParams` и не `new URL`. Объект параметров строится только из объявленных имён экрана: `__proto__` и чужие ключи в него не попадают. Экран по пути ищется только в наборе приложения. URL и причина отказа в заметку, лог и `faults` не идут. Свой URL всегда начинается с одного `/` — запись истории не уведёт на чужой хост.
- **Запись истории — внешние данные** (D-UI-81): строка с пределом до разбора, разбор в `try`, схема формы; слоты проверяет `ScreenRuntime.restore`. Запись не даёт прав сверх ссылки: экран из неё читает данные от имени текущей личности вкладки. Состояние экрана браузер хранит на диске (восстановление сессии) — секретов в состояние экрана не клади. Сбой порта истории — в `faults` фиксированным текстом `PAGE_FAULTS.history`: бросок браузера несёт URL с параметрами людей.
- **Текст отвергнутого входа** беседа показывает только в беседе автора значения и в лог не пишет; в групповом разговоре это нарушилось бы — беседа рассчитана на личный.
- **Собеседник и отправитель.** Узел бесед связь `peer` и `sender` не сверяет: первый отправитель в новый `peer` становится владельцем беседы. Адаптер личного чата сверяет их сам — в групповом разговоре без сверки беседу захватил бы первый написавший.
- **Ключ хранилища `peer`** — непрозрачная строка мессенджера без предела длины и набора знаков: в путь файла как есть не кладётся (хеш или экранирование).
- **Сообщество (`Communities`, D-UI-59).**
  - Личность участника — только из транспорта: `people(member)`; uuid в данных сигнала нет и не читается. Незнакомый без `strangers` не вызывает UC, вход которого берёт человека (`person`), с `strangers: true` — вход без поля человека; манифест без `person` (например, `added` от незнакомого админа) исполняется и так, `people` не спрашивается. Имён мессенджера домен не получает. Незнакомое сообщество (`keys` → нет) — без вызова. Пустая строка из порта перевода — тоже «не знаем».
  - Поля сигнала — строки: числа транспорта (у Telegram `chat.id`, `user.id`) пакет мессенджера переводит `String(...)`, иначе сигнал отвергнут по пределу. Отсев — по виду, handle, участнику и `id`: один апдейт на нескольких вступивших — несколько сигналов.
  - Сигнал не исполняет операцию сообщества: он только вызывает объявленный command UC. Путь к операции — событие домена → query UC.
  - Цели реакции — только выход query UC (поля `targets`), не payload события и не сигнал; перевод в мессенджер — `handles` и `members`.
  - Вызывающий — система от узла (`id` узла сигнала или реакции), из данных сигнала не строится; политика UC — явная. `allowAll` — только при `callers: ['system']`: с `user` в `callers` такой UC вызовет любой человек с чужим `userId`. Иначе — своя проверка системного вызывающего.
  - Query UC реакции — граница доступа: вызывается без субъекта, поэтому сам проверяет текущее состояние (повтор устаревшего события не должен исключить вернувшегося) и не отдаёт целью поля своего входа — иначе цель задаёт payload события.
  - Лог без данных: ни handle, ни личности, ни uuid, ни ключа, ни id сигнала, ни payload, ни текста броска.
  - Обработчик события тотален: бросок поймал бы подписчик платформы и записал его текст в лог. Бросок порта перевода или порта сообщества — дефект: исполнитель ловит его и пишет только имя ошибки.

## 8. Идентификаторы запросов

`requestId` каждого входящего сигнала — новый (`crypto.randomUUID()`). Повторный `requestId` платформа считает повтором запроса. С тем же входом клиент получает прежний итог; с другим входом или пока первый запрос исполняется — `REQUEST_CONFLICT` («Запрос уже принят»). Поэтому постоянный `requestId` в тесте даёт отказ. В гостевой сессии отсев повторов ключуется по `channel.visitorId`: без `CallerSource.channel` у гостя его нет. В тестах id задаётся счётчиком (`requestIds: () => 'r-' + (++n)`).

## 9. Доставка уведомлений

- `UiNotifier` отдаёт каналу `DeliveredNotification`: `notification` (`id` узла), `recipient`, `data`, `links` (`AddressJson`), `cause: { event, eventId }`, `trace`.
- **Отсев повтора и предел** — политика канала: ядро только передаёт `cause.eventId`. У беседы отсев — в самой беседе ([conversation-notices.ts](../../packages/chat-ui/src/conversation/conversation-notices.ts)): ключ — SHA-256 от `JSON.stringify([notification, eventId])` (получатель — сама беседа), память в снимке (`notified`), предел 128, вытесняется старейший. Ключ ставится после успешной доставки: недошедшее отсев не ставит, повтор события доходит. У страничного канала отсев — во вкладке ([page-seen-keys.ts](../../packages/web-ui/src/client/page-seen-keys.ts), D-UI-75): тот же ключ без хеша, 256 ключей, срок — час от первого приёма по часам вкладки (`PageClock`), старейший вытесняется; ключ ставится после проверки данных схемой Def уведомления. Входящие вкладки — источник вида `client.inbox()`: запись `{ notification, data, links }` без текста, до 50 записей; текст строит представление уведомления. Отсев и входящие — память вкладки: перезагрузку страницы не переживают.
- **Узел бесед — вход уведомлений** (`Conversations` реализует `NotificationDelivery`): собеседника получателя даёт порт `peers(person)` — личный чат личности в приложении мессенджера, обратный к `people`: пакет сверить это не может, при неверном `peers` уведомление уйдёт не тому, а настоящий владелец чата получит отказ «чужая личность» (`warn`); собеседник — непустая строка до 256 знаков. Беседы у собеседника нет — создаётся с личностью получателя. Уведомление идёт в очереди собеседника и в порт `notify`; беседу не трогает (экран, черновик, путь, номер экрана). Ссылка уведомления — запись `open` в таблице ссылок, подпись — экрана-цели; нажатие открывает экран новым сообщением, путь растёт («Назад» вернёт прежний экран). Дошедшее уведомление сбивает положение места: следующий показ экрана идёт новым сообщением.
- **Недошедшее** (окно мессенджера закрыто, порт отказал) — `warn` без данных и без броска, отсев не ставится, ссылки уведомления из таблицы снимаются; нет собеседника, чужая личность, уведомления нет в наборе — тоже `warn`; дефект представления — `error` с именем ошибки, `deliver` не бросает: наблюдатель ядра пишет `notified` и для недошедшего (DEBT-UI-21). В лог не идут получатель, данные, `eventId`, текст и ссылки (раздел 7).
- Сбой `deliver` у других каналов — бросок: сервер его логирует и идёт к следующему получателю; уведомление не копится. Очередь, push и письмо — дело канала (страничный канал при отсутствии соединений не доставляет и не копит).
- В сообщение клиенту кладут `data`, `links` и `eventId`; `trace` и `recipient` — нет ([page-delivery.ts](../../packages/web-ui/src/server/page-delivery.ts)).

## 10. Чеклист

- ARC-08 — канал импортирует только публичные входы `dmg-ui`, `dmg-core`; UC вызывает через `dispatch` сервера.
- ARC-13 — свой префикс правил; UI-06 — ребро `presents` на каждый экран и уведомление приложения.
- ERR-01, ERR-06, ERR-07 — внешний вход не бросает, неизвестный исход — дефект канала, `warn` без данных клиента.
- Нейтральность: в коде экрана и ядра нет слов канала; в пакете это проверяют тест импортов и сканер слов канала — образец такой проверки для своего канала.
- Личность — из транспорта; `CallerSource.channel` задан; `requestId` новый на сигнал; `RenderContext` строится `RenderContexts` (или из `RenderFlags`).
- Каждый исход `ActionOutcome` и `LocalOutcome` разобран в `switch` с веткой `never`; у беседы так же — сигналы, записи таблицы ссылок и виды `ViewOption`.
- Представление: варианты — только у последнего сообщения и из вариантов по умолчанию; лимиты мессенджера — по `kit.capabilities`.
- Отсев повтора уведомлений и предел памяти (входящие, отсеянные ключи) решены явно. Пределы беседы: таблица ссылок — 256 записей (старейшие вытесняются), отсев повтора сигналов — 128 id, отсев уведомлений — 128 ключей, id сигнала — 256 символов, текст — 64 Ки, собеседник (`peer`) — 1–256 символов (сигнал и уведомление с негодным собеседником не исполняются), бесед в памяти узла — 1000 по умолчанию (давняя нетронутая выгружается), путь переходов — 16 элементов (давний забыт), элемент пути — до 8192 знаков JSON (длиннее — в путь не кладётся, путь прежний), сообщений одного показа и живого места в снимке (`handles`) — 32, последнее сообщение места в снимке — до 1024 фрагментов, текст фрагмента — 64 Ки, ссылка фрагмента — 2048 символов (сверх — место пишется в снимок без сообщения) ([conversation.const.ts](../../packages/chat-ui/src/conversation/conversation.const.ts)). Пределы вкладки страничного канала: входящие — 50 записей, отсев уведомлений — 256 ключей на час (старейшие вытесняются) ([page-client.const.ts](../../packages/web-ui/src/client/page-client.const.ts)).
- Страничный канал: каждый экран набора приложения страниц выражается URL (иначе сборка `PageUrls` бросает); неразборчивый URL ведёт на вход `start` с заметкой, а не бросает и не оставляет `main` пустой (D-UI-76).
- Страничный канал: ожидаемый итог — только `data` и по схеме данных экрана; ревизия жеста — вида области, а не итога (D-UI-84).
- Страничный канал с историей: первая загрузка — `boot()`, ссылки внутри страницы — `route(href)`, `href` — из `PageClient.url()`. Отказ первой загрузки (код экрана мог не загрузиться) ловит привязка, отказ перехода по записи — клиент (в `faults`).

## 11. Как тестировать

- Граф — `reportArchCheck([app], print)` с поставщиками; в тестах пакета — `ArchReport.of(app)` (`dmg-ui/testing/fixtures`: код выхода и `report.rule(id)`). Сцена — `ArchApp` с доменом примера, `UiGraphProvider` и поставщиком канала; сцена с нарушением даёт код 1 и строку `ID: …`, исправленная сцена — код 0 ([page-rules.test.ts](../../packages/web-ui/src/graph/page-rules.test.ts) — образец страничного канала). У мессенджера сцена меняет одно поле `ChatAppSpec`: урезанные возможности — строка `CH-01: приложение <app>: экран …` ([example-limits.rule.test.ts](../../packages/chat-ui/src/graph/rules/example-limits.rule.test.ts)), вход без точки в `entryPoints` — `CH-02: вход <имя> приложения <app>: нет точки входа` ([entry-point.rule.test.ts](../../packages/chat-ui/src/graph/rules/entry-point.rule.test.ts)), реакция или сигнал в `community` приложения на мессенджере без них в возможностях (`MemoryMessenger.windowed`) — `CH-03: приложение <app>: реакция <id> (<операция>) — мессенджер <name> её не исполняет` ([community-capabilities.rule.test.ts](../../packages/chat-ui/src/graph/rules/community-capabilities.rule.test.ts)). Сцена одного правила ставит остальное без нарушений (точку на каждый вход, возможности по профилю), иначе код 1 держится на чужом правиле. Узлы и рёбра, которых поставщик канала сам не ставит (вход не под приложением, ребро от чужого узла, точка входа другого поставщика), сцена получает подставным поставщиком в `providers` того же `ArchApp`: реестр видов общий, и подставной поставщик ставит узлы и рёбра зарегистрированных видов через сборщик графа, а отчёт даёт тот же `ArchReport.of` ([entry-point.rule.test.ts](../../packages/chat-ui/src/graph/rules/entry-point.rule.test.ts)). Граф в обход сборщика (конструктор `Graph`) — не путь сцены: он вне публичного контракта платформы. Пакет мессенджера тестирует свои правила так же, на своём поставщике.
- Сквозные сценарии (TST-09) — по одному на канал и мессенджер: приложение `ExampleApp` из `dmg-core/testing/example`, `UiServer`, `UiNotifier` с доставкой канала, два пользователя. Беседа на обоих подставных мессенджерах (`MemoryMessenger.editing()` и `windowed(clock)`, один реестр представлений и один `exampleCodes()`; текст уведомления проверяется в чате получателя, ожидание — `conversations.settled()` и `bus.delivered()`) — [conversation-story.test.ts](../../packages/chat-ui/testing/conversation-story.test.ts); Telegram — [telegram-story.test.ts](../../packages/tg-bot/testing/telegram-story.test.ts) и [telegram-community.story.test.ts](../../packages/tg-bot/testing/telegram-community.story.test.ts); страничный канал — [page-story.test.ts](../../packages/web-ui/testing/page-story.test.ts). Поверх каналов — [channels-story.test.ts](../../acceptance/channels-story.test.ts) (одна сторис, все каналы).
- Провод — в памяти, строки JSON и журнал сообщений; простой ждёт `PageWire.settled()` без таймеров и без счёта ходов (TST-04): пока не завершится вся работа, включая промисы обработчиков сообщений (D-UI-71).
- Провод на сокете — тест на настоящем сокете среды ([page-socket.test.ts](../../packages/web-ui/src/page-socket.test.ts)): сервер на порту `0`, ожидание — только событиями (подписка на источник области, закрытие на сервере, обрыв, сырые кадры). Что чужое событие экран не перечитало, граница — ответ на свой вызов: кадры одного соединения упорядочены, и сигнал, если бы был отправлен, пришёл бы раньше. Перезапуск сервера — `stop(true)` и новый сервер на том же порту над тем же приложением (прежней сессии нет); вкладка — через `PageReconnector` с `ManualPageClock` и `random: () => 0`: паузу тест сдвигает `clock.advance` на срок из `clock.pending()`, перечитывание ждёт по источнику области. Политику пауз и срока `hello` проверяют подставной сокет и те же часы ([page-reconnector.test.ts](../../packages/web-ui/src/client/page-reconnector.test.ts)), обрыв и `attach` вкладки — подставной конец провода ([page-client.test.ts](../../packages/web-ui/src/client/page-client.test.ts)).
- Текст страницы в тестах — `PageText` (`dmg-ui/web-ui`): подставная цель показа, текстовое представление на трёх областях, `page()` и `region(name)` ([page-text.ts](../../packages/web-ui/src/client/page-text.ts)). Состояния области — по журналу `client.source(region).subscribe(...)`: подписка сразу отдаёт текущее значение, затем каждое новое ([page-client.test.ts](../../packages/web-ui/src/client/page-client.test.ts)). Входящие — так же, по `client.inbox()`; срок отсева — подставными часами `ManualPageClock` (`dmg-ui/web-ui/testing`, `clock.advance(ms)`) без таймеров среды.
- Политики — тестом на каждый исход с `MemoryUiObserver`, у беседы — на обоих подставных мессенджерах (`describe.each`); примеры рендера — `ExamplePreview` и снимки.
- Что видит собеседник — `MemoryMessenger.chat(peer)`: сообщения по порядку появления с последним содержимым, числом правок, уходом и нажатым (`ChatLine`); правка или новое — по журналу `journal`.
- Безопасность — тесты на недоверенный вход: мусор, строка длиннее предела, чужая пара `(module, uc)`, повтор подписки, чужой или пустой `Origin`, негодный пропуск; строка сервера длиннее предела — с обеих сторон.
- Адрес в URL ([page-urls.test.ts](../../packages/web-ui/src/url/page-urls.test.ts)) — круг «адрес → URL → адрес» на каждом примере каждого экрана набора (`def.examples`) и таблица отказов разбора: строка на причину, `not.toThrow()` в каждой; маршрут с параметрами пути и невыразимые схемы — на тестовом приложении в файле теста.
- Показ до ответа (D-UI-84) — без таймеров: UC удержан заглушкой конца провода, итог проверяется сразу после вызова жеста (до `await`), откат — по журналу `client.source(region).subscribe(...)` после отпуска ответа; сцены — успех, отказ, устаревшая ревизия, перечитывание, обрыв, переход, «Назад», два действия подряд.
- История вкладки — подставная `MemoryPageHistory` (`dmg-ui/web-ui/testing`): `back()` и `forward()` ждут клиента без таймеров, `entries()`, `position`, счётчики `pushes` и `replaces` — для сцен «шаг» и «замена»; `reloaded()` — те же записи для новой вкладки и `boot()` (перезагрузка); `fail(error)` — отказ браузера до `fail(undefined)`.
