# Web-канал — гайд

**Назначение:** как подключить страничный канал — вход `dmg-ui/web-ui` — к веб-приложению: что в него входит, контракт представления, провод и привязка сервера к `Bun.serve`, клиент в браузере, адрес в URL, области, история, форма и жест, показ до ответа, граф и правила `PG-NN`, безопасность, решения без реализации, тесты и чеклист проекта. Общее для любого канала (что обязан дать канал, политики по исходам, граница JSON, доставка уведомлений) — в [Пакете канала](./channel-package.md); здесь только страничное. Запускаемый образец — [examples/web](../../examples/web/README.md) ([D-UI-85](../decisions.md)). Объявление экранов — [story-screen-notification.md](./story-screen-notification.md).

## 2. Состав и зоны

Два входа: `dmg-ui/web-ui` (клиент, сервер, провод, представления, кодек URL, поставщик графа; [index.ts](../../packages/web-ui/src/index.ts)) и `dmg-ui/web-ui/testing` (привязка учебного примера: приложение, маршруты, представления, граф; подставные часы `ManualPageClock` и история `MemoryPageHistory`; [index.ts](../../packages/web-ui/testing/index.ts)). Отдельный вход для тестов нужен, чтобы тесты ядра, которым нужен только пример, не грузили канал, сервер и граф (D-UI-69).

Каталоги `packages/web-ui/src/` — зоны с направлениями:

| Каталог | Что внутри | Что видит |
|---|---|---|
| `client/` | `PageClient`, области, переподключатель, конец сокета, история, входящие, текстовая цель `PageText` | `view/`, `wire/`, `url/` и имя канала (`page-channel.const`); сервера и графа нет |
| `server/` | `PageHost`, ворота `PageGate`, мост сокета `PageSockets`, очередь отправки | `wire/` и имя канала, `dmg-ui/server`; клиента и графа нет |
| `wire/` | схемы сообщений, провод в памяти `PageWire`, пределы строки | только себя |
| `view/` | контракт представления, `PageFormModel`, текстовое представление, реестр `PageViews` | только себя: источник состояния и цель показа |
| `url/` | кодек `PageUrls`, маршрут `PageRouteDef`, состав областей в ссылке | только себя; строки на входе и выходе, браузера нет |
| `graph/` | поставщик графа `PageGraphProvider`, правила `PG-NN` | `view/`, `url/`, имя канала, `dmg-ui/graph`; клиента и сервера нет |

Пакет канала видит ядро `dmg-ui` и `dmg-core` и не видит других каналов; импорты проверяют `PackageDirections` и `CoreImportScanner` ([rules.md](../reference/rules.md), D-UI-34). Глобалы браузера разрешены только двум файлам клиента: `PageBrowserSocket` и форме окна `PageBrowserWindow` (`PageBrowserHistory` получает окно аргументом), глобалы среды `Bun` и `process` — нигде в `src/` (проверка `BrowserGlobalScanner`): сервер говорит с соединением через порт, клиент получает среду аргументом.

## 3. Контракт представления

Состояние области страничный канал строит сам, вид экземпляра ядра для этого не расширяется (D-UI-70). `PageViewState` — статус `empty | loading | ready | refused`, признаки `refreshing` и `stale`, отметки и `expected` ([page-view-state.types.ts](../../packages/web-ui/src/view/page-view-state.types.ts)). Состояние — только данные JSON.

- `loading` — от начала открытия до экземпляра: прежний экземпляр снимается в начале открытия, действий по старому экрану нет, а из двух открытий в область побеждает последнее начатое (экземпляр опоздавшего закрывается, исход действия ушедшего экземпляра область не трогает). Отказ открытия оставляет область пустой с заметкой «Экран недоступен», отказ уходит вызывающему.
- `refreshing` — от сигнала своего порта до `settled()` экземпляра (D-UI-49); сигнал сопоставляется с областью по адресу.
- `stale`: исход `stale` даёт `stale: 'revision'` с заметкой «Данные обновились»; отметку заменяет следующий исход или открытие ([page-regions.ts](../../packages/web-ui/src/client/page-regions.ts)). Без связи (D-UI-74) каждая непустая область получает `stale: 'offline'` (важнее `revision`; у пустой пометки нет) и держит его, пока не перечитана по новому соединению. Действия такой области отключены — исход `unavailable: 'disabled'` без исполнителя; отказ действия, прерванного обрывом, — заметка «Связь прервалась — результат будет виден после переподключения» вместо текста отказа. Переход без связи ждёт соединения: область в `loading` с пометкой, прежний экземпляр снят, вызовов нет.
- `expected` — показ ожидаемого итога до ответа (раздел 10).

Представление получает источник вида и цель показа: `ViewSource<PageViewState>` (`get()` и `subscribe`, который зовёт слушателя сразу текущим значением; значение неизменяемо — смена даёт новый объект) и `PageRegionPresenter<Target>` — `show(source, target)` возвращает отписку, устройство цели пакет не знает ([page-region-presenter.types.ts](../../packages/web-ui/src/view/page-region-presenter.types.ts), [view-cell.ts](../../packages/web-ui/src/client/view-cell.ts)). Монтирует приложение: `presenter.show(client.source('main'), target)`. Образец без среды — текстовое представление `PageTextPresenter` с целью `PageTextTarget` (`write(text: string)`) и подставной страницей `PageText` ([page-text-presenter.ts](../../packages/web-ui/src/view/page-text-presenter.ts), [page-text.ts](../../packages/web-ui/src/client/page-text.ts)).

**Раскладка представлений по экранам** (D-UI-80). Единица смены — область; источник области один на жизнь вкладки; представление области одно, подписано на источник и само выбирает представление экрана по `state.view.screen` (в `loading` — по `state.address.screen`). Замена содержимого цели при смене экрана — дело представления: оно владеет целью на время подписки. Реестр `PageViews` хранит представления экранов `PagePresenter` и уведомлений `PageNotePresenter`; форма по умолчанию — `PageFormModel` для любого экрана, своя отрисовка — перекрытие на экран. Представления живут в зоне `view/`: не видят клиента, провода, сервера и графа, глобалов браузера и среды у них нет. Типы представлений для DOM, монтирование и демонтаж, сохранение набранного (черновик живёт в DOM, не в состоянии), фокус и ссылки — за привязкой DOM; образец без фреймворка — [examples/web](../../examples/web/README.md) (D-UI-85).

## 4. Провод и привязка сервера

Общий каркас провода — граница JSON, `UcCall`, порядок «подписка раньше чтения» — в [Пакете канала](./channel-package.md#6-граница-json-и-провод); здесь страничная часть.

### 4.1. Сообщения и порядок

Сообщения ([page-messages.types.ts](../../packages/web-ui/src/wire/page-messages.types.ts)): клиент → сервер `call`, `watch`, `unwatch`; сервер → клиент `hello`, `result`, `signal`, `watch-refused`, `notification`, `refused`. Схемы — `ClientMessage` и `ServerMessage`; строгость схем, порядок «`watch` раньше `call` загрузки», сигнал перечитывания и выход — в каркасе [Пакета канала](./channel-package.md#6-граница-json-и-провод). Провод упорядочен в каждую сторону: WebSocket такой, независимые запросы HTTP — нет, поэтому одно соединение несёт и перечитывание, и уведомления, и вызовы (D-UI-33, D-UI-71, D-UI-89).

### 4.2. Личность: ворота, cookie, `Origin`, место

Личность — по пропуску соединения (D-UI-72). До открытия сокета ворота `PageGate` ([page-gate.ts](../../packages/web-ui/src/server/page-gate.ts)) проверяют запрос: `Origin` — точным совпадением с белым списком `origins`, пропуск — cookie с именем `cookie`, ровно одно вхождение, 1–256 символов; отказ (`origin` или `token`) привязка превращает в `403`. Затем `PageHost.connect(token, push)`: асинхронный порт `tokens` → `uuid` → сессия с вызывающим из `callers` (`RecipientCallers`, как у мессенджеров); клиент `uuid` не шлёт; `push` получает строки JSON, готовые к отправке (D-UI-71). Контекст рендера приходит в `hello` один раз и собирается `RenderContexts` из `places` (`PersonPlaces`) по `uuid` токена — место того, кто работает; места по умолчанию нет. Неизвестный токен, сбой `tokens` или `places`, предел соединений — `refused` (сбой порта — ещё и `error` без данных). Отзыв токена открытое соединение не рвёт.

### 4.3. Пределы

Константы: `MAX_CLIENT_TEXT`, `MAX_SERVER_TEXT` — **публичные**, экспортируются из `dmg-ui/web-ui` ([page-wire.const.ts](../../packages/web-ui/src/wire/page-wire.const.ts)); `WATCH_LIMIT`, `CALL_LIMIT`, `CONNECTION_LIMIT` ([page-server.const.ts](../../packages/web-ui/src/server/page-server.const.ts)); `PAGE_CLOSE` в `page-wire.const.ts`, `MAX_ID` в `wire/page-messages.ts`, `MAX_LENGTH` в `packages/core/src/server/client-input.ts` (ядро).

- Строка клиента — 64 Ки символов (65 536, проверяется до `JSON.parse`), строка сервера — 1 Ми символов; 16 одновременных вызовов и 64 подписки на соединение, 8 соединений на личность, идентификаторы — до 256 символов.
- Мусор и превышение у клиента — `refused`, не бросок (ERR-01); `warn` без данных клиента (ERR-07), на мусор, предел вызовов и каждый вид отказа подписки — раз на соединение (`watch-refused` клиенту — на каждый кадр).
- Строку сервера длиннее предела `PageOutbox` не отправляет: `result` заменяется отказом `SERVER_INTERNAL` с тем же `id`, уведомление отбрасывается, `warn` — раз на вид; клиент длинную строку не разбирает и рвёт соединение (D-UI-71).

### 4.4. Привязка к `Bun.serve`

Привязка к серверу сокетов — у приложения, не в пакете: в пакете нет глобалов среды, сокет сервера проходит узкий тип `PageServerSocket` без адаптера. Образец — [example-web-server.ts](../../examples/web/src/server/example-web-server.ts) (страница, вход, ворота, пульс, остановка) с опциями в [example-web-server.const.ts](../../examples/web/src/server/example-web-server.const.ts) и [page-socket.test.ts](../../packages/web-ui/src/page-socket.test.ts). Без любого из шести условий ниже привязка небезопасна. На раздел 4.4 ссылаются [D-UI-71](../decisions.md) и [D-UI-85](../decisions.md); условия пронумерованы для ссылок из текста.

1. **Методы `PageSockets` — лямбдами** (`open`, `message`, `close`): сервер сокетов не обязан звать их с `this`. Обработчик `close` обязателен: без него доставка, подписки и сессия закрытого сокета не освобождаются.
2. **`data` при `upgrade` — только результат `gate.admit(request.headers)`**: пропуск, собранный в обход ворот, обходит и проверку источника.
3. **Предел кадра `maxPayloadLength`** — около `3 × MAX_CLIENT_TEXT` байт (до 3 байт UTF-8 на символ): меньше — честный кадр рвёт сокет раньше предела пакета, намного больше — сервер сокетов принимает лишнее до проверки длины.
4. **Очередь отправки** — `closeOnBackpressureLimit: true` и `backpressureLimit` не меньше `3 × MAX_SERVER_TEXT` байт. Мост не смотрит, что вернул `send` сокета: без закрытия по пределу сервер сокетов после переполнения молча выбрасывает кадры (у Bun по умолчанию предел 16 МиБ, а закрытие выключено), и клиент, не читающий сокет, держит память сервера; с закрытием клиент получает обрыв, `result` и `signal` не теряются без следа.
5. **Пульс** — `sendPings: true` и `idleTimeout` от 60 до 120 секунд: сервер сам шлёт ping, браузер отвечает без участия клиента, а полуоткрытое соединение (сеть пропала без закрытия TCP) закрывается по сроку молчания и не держит одно из восьми мест личности. Без пульса срока у такого соединения нет; клиентская сторона тихого обрыва — DEBT-UI-33. Таймеров на сервере нет: мёртвое соединение закрывает сервер сокетов по сроку молчания.
6. **Заголовки запроса на `upgrade`** (`Cookie`, `Origin`) в лог не пишутся.

Вне привязки: **предел частоты рукопожатий — у прокси перед сервером**: таймеров на сервере нет, а каждое рукопожатие стоит вызова порта `tokens`.

Сокет ([page-sockets.ts](../../packages/web-ui/src/server/page-sockets.ts), [page-socket-end.ts](../../packages/web-ui/src/client/page-socket-end.ts)). Кадр клиента до `hello` — нарушение протокола: закрытие кодом 4400; двоичный кадр — `refused: malformed` на каждый, `warn` — раз на сокет, соединение живо; отказ соединения — закрытие кодом 4403. Порт серверной половины после пуша `hello` разрешает `connect` без дальнейших `await` (`PageServerPort`, `PageHost` так и делает): иначе кадр честного клиента, ответившего на `hello`, мост примет за кадр до связи. Закрытие сокета освобождает доставку, подписки и сессию, в том числе если соединение ещё устанавливалось; новое соединение той же личности начинает с чистого места. Клиентский конец отличает отказ до `hello` от обрыва после; вид отказа — `PageDialFailure`: `refused` (закрытие кодом 4403), `closed` (иное закрытие; отказ ворот `403` сокет браузера видит как `1006` — так же, как недоступный сервер), `malformed` (первый кадр не `hello`), `timeout` (срок `hello` у переподключателя). Кадры после `hello` до первой подписки `onMessage` копятся (до 64, сверх — сокет закрыт и обрыв) и отдаются первому обработчику по порядку; `onBreak` — ровно один раз, опоздавший к обрыву обработчик зовётся сразу (D-UI-74).

### 4.5. Страница без пропуска

`PageReconnector.connect()` возвращает `Promise<ClientEnd>` и об отказе не сообщает: при отказе (нет cookie, пропуск неизвестен) промис не завершается — переподключатель повторяет попытки с паузой до 30 с, и клиент вечно показывает «Подключение…»; отклонение приходит только после `close()`. Поэтому страницу без годного пропуска не должен получать скрипт клиента: решает сервер приложения — в примере это страница «Кто вы?» без скрипта клиента, вход `POST /_enter/<ключ>` выдаёт пропуск и ведёт на `303` (D-UI-85).

### 4.6. Заголовки страницы

Страница отдаётся с политикой содержимого (`Content-Security-Policy`: `default-src 'none'`, скрипты и стили только свои, `connect-src` — свой источник и сокет, `frame-ancestors 'none'`), `X-Content-Type-Options: nosniff` и `Cache-Control: no-store` ([page-shell.ts](../../examples/web/src/server/page-shell.ts)). `Referrer-Policy` страницы с формой входа — **`same-origin`, не `no-referrer`**: при `no-referrer` браузер шлёт на `POST` формы `Origin: null`, и ворота отвечают `403` (проверяет `page-shell.test.ts`).

### 4.7. Вызов UC и что уйдёт в `dmg-core`

Общий порядок вызова UC (`UcCall`, сверка пары `(module, uc)`, след и вызывающий от сервера) — [Пакет канала](./channel-package.md#6-граница-json-и-провод). Страничное: в `dmg-ui` остаётся знание UI — сверка пары с объявленным узлами сессии (`UcRoutes`), отказ command UC по `eventId`, подписки, сигналы и `hello`. В платформу `dmg-core` вместе с приёмом команды по HTTP уходит остальное: схема простой команды и пределы идентификаторов, сборка следа, вызывающий из личности транспорта, пределы тела и одновременных вызовов, ограниченный набор символов идентификаторов клиента (DEBT-UI-31). Полный перечень — [D-UI-73](../decisions.md).

## 5. Клиент в браузере

Сборка клиента страницы ([example-page.ts](../../examples/web/src/client/example-page.ts) — образец), в таком порядке:

1. `PageReconnector({ sockets, clock, random?, faults? })`: `sockets` создаёт `PageBrowserSocket` поверх сокета браузера, `clock` — `PageSystemClock`.
2. Сразу после создания, до `connect()`: `pagehide` → `reconnector.close()` (попыток больше нет, текущий конец закрыт); `pageshow` с `persisted` — страница из кэша «Назад» получила бы закрытый навсегда сокет, её загружают заново.
3. `await reconnector.connect()` — первая попытка сразу, дальше с паузой до `hello`; `catch` — выход: промис отклоняется только после `close()` (страница уходит).
4. `new PageClient({ app, codes, routes, end, placements, observer, faults, history: new PageBrowserHistory(window) })`.
5. `reconnector.follow(end, (next) => client.attach(next))` — после обрыва новый конец отдаётся вкладке.
6. Монтаж представлений: `presenter.show(client.source(region), target)` на каждую область и показ входящих (`client.inbox()`).
7. `client.boot()` — первая загрузка и перезагрузка: области по текущей записи истории, без новой записи; отказ первой загрузки (код экрана мог не загрузиться) ловит привязка, например в `catch`.

**Переподключение** (D-UI-74, [page-reconnector.ts](../../packages/web-ui/src/client/page-reconnector.ts)). `connect()` — первая попытка сразу; `follow(end, attach)` — после обрыва попытки с паузой, новый конец отдаётся `attach` раньше любого своего кадра, слежение за прежним концом снято; `close()` — попыток больше нет, текущий конец закрыт. Попытка — новый сокет и ожидание `hello` не дольше 10 с. Пауза перед попыткой `n` — от `d/2` до `d`, `d = min(30 с, 500 мс · 2^(n−1))`; после отказа `4403` — сразу верхняя ступень (неизвестный пропуск или предел соединений в цикле не повторяются); счёт сбрасывает только обрыв соединения, прожившего от `hello` не меньше 30 с (`RECONNECT.stableMs`): сервер, который принимает и сразу рвёт, получает растущую паузу. Бросок и отказ `attach`, бросок фабрики и подписки сокета уходят в `faults` и попыток не останавливают. Пауза не ускоряется по сети — DEBT-UI-43. Время — порт `PageClock` (`PageSystemClock` в браузере), разброс — порт `random` (по умолчанию `Math.random`).

**Новый конец вкладке** — `PageClient.attach(end)` (D-UI-74): живой прежний закрывается, контекст новых экземпляров — из нового `hello`, отложенные переходы открываются, а каждая область с данными прежнего соединения перечитывается восстановлением из снимка своего экземпляра — подписка, затем чтение, ревизия +1, прежний вид с `refreshing`, пока чтение идёт. Экземпляр, открытый с контекстом прежнего `hello` (конец сменился во время загрузки), помечен «нет связи» и перечитан так же. Сбой восстановления — область пуста с заметкой «Экран недоступен», в `faults` — запись с узлом канала и фиксированным текстом. Без связи порты отказывают вызов сразу и не шлют подписку, команда повторно не уходит никогда. Обрыв во время вызова UC записан как дефект кода — DEBT-UI-32.

**Входящие и отсев** (D-UI-75). Отсев повтора уведомлений — во вкладке ([page-seen-keys.ts](../../packages/web-ui/src/client/page-seen-keys.ts)): ключ — `[notification, eventId]` без хеша, 256 ключей, срок — час от первого приёма по часам вкладки (`PageClock`), старейший вытесняется; ключ ставится после проверки данных схемой Def уведомления. Входящие — источник вида `client.inbox()` ([page-inbox.ts](../../packages/web-ui/src/client/page-inbox.ts), пределы — [page-client.const.ts](../../packages/web-ui/src/client/page-client.const.ts)): запись `{ notification, data, links }` без текста, до 50 записей; текст строит представление уведомления. Отсев и входящие — память вкладки: перезагрузку страницы не переживают. Сервер при отсутствии соединений уведомление не доставляет и не копит; в сообщение клиенту кладут `data`, `links` и `eventId`, `trace` и `recipient` — нет ([page-delivery.ts](../../packages/web-ui/src/server/page-delivery.ts)).

## 6. Адрес в URL и маршруты

D-UI-76, [page-urls.ts](../../packages/web-ui/src/url/page-urls.ts). `PageUrls({ app, routes })` переводит адрес `main` в путь и строку запроса страницы и обратно, браузера не знает. Путь — маршрут (первый объявленный маршрут экрана, который выражает адрес в пределе длины; длинный — следующий маршрут) или общий путь экрана `/<модуль>/<экран>`. Маршруты — `PageRouteDef`: шаблон пути (`/`, неизменяемые сегменты `[a-z0-9-]+`, параметры `:имя` экрана входа) и имя входа приложения.

- Маршруты не пересекаются: два шаблона, совпадающие на одном URL (`/:s` и `/assigned`, `/p/:a` и `/p/:b`), — бросок сборки. Прочие параметры — `имя=значение` в порядке схемы, без JSON; виды параметров — строка, целое, булево по JSON Schema параметров.
- Любой экран набора приложения страниц обязан выражаться URL, иначе — бросок сборки. Страж на примерах: каждый пример экрана набора проходит круг «адрес → URL → адрес», иначе бросок сборки с `id` экрана (ловит `v.transform`, которого JSON Schema не видит); экран без примеров страж не проверяет (DEBT-UI-34).
- Голый путь маршрута — ровно адрес входа (`/`, а не `/?page=0`); есть в URL хоть один объявленный параметр — адрес только из URL. Ключ запроса, которого экран не объявил, пропускается; ключи с `_` в начале — за каналом.
- Предел — 2048 знаков в обе стороны. Разбор `parse(url)` — `Result` с причиной `tooLong`, `malformed`, `unknownPath` или `invalidParams`; сборка `url(address)` — строка или `undefined` (одиночный суррогат, управляющий знак — разбор его отверг бы, длина), бросок — экран вне набора или значение не того вида.
- URL, который не разобрался (`route`), ведёт на вход `start` с заметкой «Страница не найдена» — клиент не бросает и не оставляет `main` пустой.
- Правила `PG-03…PG-07` повторяют проверки сборки в `arch:check` без броска (D-UI-77).

## 7. Области и окно

Областей три — `main`, `side` (панель), `modal` (окно) (`PageRegionName`). Куда открыть переход, решает канал, а не экран и не приложение UI (D-UI-78): приложение страниц объявляет `PageClientSpec.placements` (`{ screen, region }`, `PagePlacement`), без объявления — умолчание по положению: из `main` в `side`, из `side` и `modal` в `main`, ссылка уведомления — в `side`; тот же экран остаётся на месте ([page-placements.ts](../../packages/web-ui/src/client/page-placements.ts)). Размещение в графе не видно — DEBT-UI-38.

- Закрыть `side` или `modal` — `PageClient.close(region)`: область пуста без заметки, подписка снята; `main` закрыть нельзя (тип). Окно — временная область: уход из него переходом закрывает его после открытия назначения. Остальные области при открытом окне клиент не блокирует — блокировку и Esc даёт представление.
- Исходы: `moved` открывает адрес в области назначения; `exited` в `main` ведёт на вход `start` с заметкой, в прочих областях очищает область; `confirm` и `rejected` хранятся в области до следующего действия. Живого места, реакций и пути, как у беседы, нет: всё показывается в области, `unavailable` — заметкой, и `unknown` тоже, а не броском; у `refused` нет отдельного текста для `caught`; адрес исхода, ссылки или «Повторить», который не декодировался, очищает область, а не ведёт на вход ([page-client.ts](../../packages/web-ui/src/client/page-client.ts), метод `settle`).
- **Состав областей в ссылке** ([page-layout-urls.ts](../../packages/web-ui/src/url/page-layout-urls.ts)): кроме `main`, в ссылку ложатся области из `PAGE_LINKED_REGIONS` (сегодня в ней `side`) ключами `_side`, `_modal`: значение — вложенный URL области, закодированный целиком. Ключи — замкнутый список, чужие метки (`_ga`) пропускаются; вложенный URL разбирается тем же `PageUrls.parse` один раз, резервный ключ внутри — `malformed` у этой области; предел 2048 — на всю строку, не влезшая область пропускается, а не отказывает ссылке. Окно в ссылку не входит. Резервные ключи читает небросающий `PageUrls.pairs`. `PageClient.url()` отдаёт ссылку по текущим областям, `route(url)` открывает `main` и прочитанные области и не трогает те, которых в ссылке нет.
- **Вложенность экранов ядру не нужна** (D-UI-80): вкладка — параметр экрана (смена — `moved` на тот же Def, адрес и URL хранят вкладку); вкладка — состояние экрана и локальное действие (один экземпляр, одна ревизия); части с независимыми данными, правами и перечитыванием — отдельные экраны в областях. Триггер пересмотра — экран, где части живут независимо и три способа не подходят.

## 8. История, «Назад», перезагрузка

D-UI-81, D-UI-97, [page-history.ts](../../packages/web-ui/src/client/page-history.ts), [page-browser-history.ts](../../packages/web-ui/src/client/page-browser-history.ts). Порт `history` в сборке клиента (`PageHistoryPort`: `current`, `push`, `replace`, `back(): Promise<void> | void`, `onTraverse`); в браузере — `new PageBrowserHistory(window)`, окно присваивается узкому типу `PageBrowserWindow`; в тестах — `MemoryPageHistory`.

- Первая загрузка и перезагрузка — `client.boot()` (не `route`): области по текущей записи истории, без новой записи.
- Шаг — новая запись — только смена экрана корневой области (место — `PageHistoryPage.place()`: экран корня без параметров) и открытие панели или окна над тем же местом (запись несёт метку `over`). Листание (другие параметры того же экрана), выбор и любое действие внутри открытого слоя — замена текущей записи (не ревизия, не пока область грузится). Закрытие слоя, положившего запись, — `back()` порта без новой записи, если области под ним не менялись; иначе замена без `over`. Что считать шагом, приложение страниц не объявляет (DEBT-UI-52); `PageBrowserHistory.back()` зовёт `history.back()`, `MemoryPageHistory` ждёт обработчиков.
- «Назад» и «Вперёд» ставят области по URL записи (главнее) и её снимку: тот же адрес — область не тронута, нет ни в URL, ни в записи — закрыта, окно и панель вне ссылки — из записи; без связи переход отложен. Отказ перехода по записи ловит клиент (в `faults`). Помощника пути, как у беседы, в ядре нет (D-UI-82).
- Запись — строка JSON `{"version":1,"regions":…}` со снимком областей и необязательными метками `depth` и `over` (умолчания не пишутся); слот длиннее 8192 знаков не пишется, запись длиннее 32 768 не разбирается ([page-history-record.ts](../../packages/web-ui/src/client/page-history-record.ts)). Ссылка без своего URL не строится — история не пишется (`PageLayoutUrls.own`): свой URL начинается ровно с одного `/` и состоит из печатных знаков ASCII (табуляцию и перевод строки браузер вырезает).
- Сбой порта истории — в `faults` фиксированным текстом `PAGE_FAULTS.history`.
- Два пути восстановления вкладки — `resume(json)` из снимка и переход по записи истории — различаются политикой; у `resume` нет потребителя вне тестов (DEBT-UI-40).

**Что переживает** (D-UI-83; полная таблица — в записи):

| Что | Переход | «Назад» | Перезагрузка | Закрытие вкладки | Перезапуск сервера |
|---|---|---|---|---|---|
| Адреса `main` и панели | новая запись | возвращаются | да, из URL | только через ссылку | вкладка жива, области перечитаны |
| Адрес окна | уход закрывает окно | из записи | из записи | нет: окно не в ссылке | да |
| Состояние экрана (выбор, фильтр) | в записи, с которой ушли | возвращается | да | нет | да (снимок экземпляра) |
| Введённое в отвергнутую форму, замечания, подтверждение | нет | нет | нет | нет | нет |
| Входящие и отсев повторов | да | да | нет — память вкладки | нет | да |

## 9. Форма и жест

D-UI-79. `PageFormModel(set).of(state)` строит из состояния области форму действий и локальных действий ([page-form-model.ts](../../packages/web-ui/src/view/page-form-model.ts)): подписи из Def, варианты и начальные значения из вида, введённое и замечания по полям; чистая функция, не бросает.

- Отвергнутый вход возвращается состоянием: `issues` и `entered` (форма и введённые значения, данные JSON, в снимок не входит); следующее действие области их снимает.
- Подтверждение — свойство действия: форма несёт `confirm`, нажатие идёт исходом `confirm` и `confirm(region)`.
- Представление возвращает намерения методами клиента: `submit`, `submitInput`, `local`, `confirm`, `retry`, `close`, `openLink`, `route`.
- Жест — `submitInput(region, action, input, revision, expected?)`: готовый вход (значение варианта, а не подпись) и обязательная ревизия вида, по которому нарисована цель; устаревшая — исход `stale`; `expected` — показ до ответа (раздел 10, D-UI-84).
- Поле формы (`PageFormField`) несёт `kind`, `hint?`, `example?`, `limits?` из вида; `PageForms` приводит строку формы к виду поля через `FieldInput` (число — числом, варианты побеждают), `PageRenderer` пишет `Часть: ____ — подсказка; Пример: …; Пределы: …` (D-UI-100). Ядро спрашивает подтверждение раньше проверки входа (DEBT-UI-37).

## 10. Показ до ответа

D-UI-84, [page-overlay.ts](../../packages/web-ui/src/client/page-overlay.ts). Жест и «Да» принимают ожидаемый итог — функцию представления `PageExpected = (view) => данные`: `submitInput(region, action, input, revision, expected)`, `confirm(region, expected)`. Итог зависит от входа замыканием (`(view) => ({ ...data, tasks: … taskId … })`), экран его не объявляет, мессенджеры его не видят.

- Клиент проверяет итог схемой данных экрана и показывает её выход: `client.source(region)` отдаёт состояние с `view.data` итога и `expected: true`, ревизия, адрес, действия и отметки — от области; текст области — «Ждём ответа…» перед видом.
- Итог снимается по исходу и сразу, как только область перестала быть готовой той же ревизии того же экземпляра: перечитывание, обрыв (`stale: 'offline'`), переход, закрытие, «Назад»; снятый не возвращается. Итог снимается по исходу до политики исходов: отказ показывает исходный вид с заметкой, а не итог с заметкой.
- Форма несёт `available` (доступно, есть связь, нет ожидаемого итога) и `reason` — текст отключённого из `availability` вида; у скрытого действия формы нет (D-UI-98).
- Пока итог показан, действия области недоступны (`unavailable: 'disabled'`, у `PageFormModel` — `available: false`), локальные — доступны; соседняя область не ждёт. Два действия подряд — DEBT-UI-41.
- Итог не по схеме или бросок функции — показа нет, вызов уходит, в `faults` — фиксированный текст. История, снимок и URL итога не видят: они читают область, а не производный источник.

## 11. Граф и правила `PG-01…PG-07`

Канал — второй поставщик графа ([Пакет канала](./channel-package.md#5-представление-показ-и-граф): общие шаги вида Def, видов и правил). Страничные отличия:

- **Один поставщик на все приложения web** — `PageGraphProvider` (`PageGraphSpec.apps`, имя `dmg-ui-pages`); два набора UI в одном графе не поддержаны (DEBT-UI-12). Ребро `presents` от приложения к экрану и уведомлению ставит поставщик по реестру представлений.
- **Точка входа канала** — `PageRouteDef`, вид Def `pageRoute` (шаблон пути и имя входа приложения): узел под приложением, ребро `opens` к экрану входа. Манифест лежит в `src/url/` ([page-route-def.ts](../../packages/web-ui/src/url/page-route-def.ts)): он нужен и графу, и клиенту.
- **Свои правила — префикс `PG`** (ARC-13): PG-01 — маршрут ведёт на объявленный вход, PG-02 — у входа есть маршрут, PG-03…PG-07 — шаблоны, пересечения и параметры маршрутов и экранов, каждый экран набора выражается URL; повторяют проверки сборки `PageUrls` без броска ([rules.md](../reference/rules.md), [graph/](../../packages/web-ui/src/graph/page-graph-provider.ts), D-UI-77). PG-05…PG-07 не видят `transform` схемы (DEBT-UI-34).
- **Представления на DOM.** Реестр представлений для графа удовлетворяет `PagePresentedViews` структурно (`set`, `presented()`), правки графа не нужно. Образец без фреймворка — чистые модели плюс прямое построение DOM ([examples/web](../../examples/web/README.md), D-UI-85): модель области вычисляется из `PageViewState` и `PageFormModel` и тестируется без браузера на настоящем `PageClient`; тонкий DOM-слой строит тело области заново на каждое состояние, строки людей кладёт только текстом (`textContent`, `value`), ввод полей хранит отдельно. Своя область — `PageRegionPresenter<Target>` с любой целью показа. Образец сборки графа — `ExamplePagesArch` (`dmg-ui/web-ui/testing`).

## 12. Личность и её смена

Субъект («кто смотрит», доменный объект для кода экрана) идёт по проводу (D-UI-99): сервер переводит его `PageHostSpec.subjectToWire` в `hello.context.subject` (JSON), клиент один раз на соединение восстанавливает `PageClientSpec.reviveSubject`; сбой восстановления — запись в `faults` и контекст без субъекта; без перевода поля нет. Смена роли — новое соединение. Личность — на соединение (D-UI-72, раздел 4.2). Смена — новое соединение: форма по умолчанию — перезагрузка страницы после запроса сервера приложения, который ставит cookie пропуска (в примере — `POST /_enter/<ключ>`, `303`). Живая смена в той же вкладке технически собирается из готового (`follow(next, attach)`, затем `PageClient.attach(next)`), но не реализуется: клиент не умеет очистить вкладку от следов прежнего человека (входящие, отсев, состояние экранов, введённое). Следствие, о котором знает потребитель: другие вкладки того же адреса остаются прежним человеком до обрыва, после обрыва переподключаются с новым пропуском и молча становятся другим человеком — `hello` не несёт личности (DEBT-UI-44). Закрыть соединения личности при выходе нечем: индекса сессий по личности нет. Подробно, с вариантами и триггером, — [D-UI-88](../decisions.md).

## 13. Безопасность

Общие пункты — в [Пакете канала](./channel-package.md#7-безопасность-для-автора-канала); страничные:

- **Клиент недоверен.** Сервер сверяет каждый вызов сам; `availability` вида (`ViewAvailability`: доступно или отключено с причиной), `confirm`, `readOnly` — подсказки показа, граница — Policy UC (D-UI-29, D-UI-33).
- **Пропуск** (D-UI-72) — в cookie, недоступной скрипту страницы (`HttpOnly; SameSite=Strict; Path=/`). Под HTTPS — ещё `Secure` и имя с префиксом `__Host-` (например, `__Host-dmg_page`): без префикса соседний поддомен ставит свою cookie с тем же именем, и ворота получают повтор имени или подсунутый пропуск. Токен — не меньше 128 случайных бит криптостойкого генератора в base64url, не `uuid` и не производное от него.
- **`Origin`** обязателен и сверяется точно: без проверки чужая страница открыла бы сокет с cookie человека. Элемент `origins` — в той форме, в какой браузер шлёт `Origin`: `схема://хост[:порт]`, схема и хост в нижнем регистре, без пути и косой черты в конце, порт — только нестандартный (`https://app.example`, `http://localhost:3000`); пустую строку, `'null'` и неканонический элемент `PageGate` отвергает броском при сборке. Токен, cookie и значение `Origin` в лог и след не идут; отказ ворот значений не несёт.
- **URL — внешние данные** (D-UI-76). Разбор не бросает ни на какой строке, длина проверяется первой, регулярные выражения — без вложенных повторов. Сегмент, ключ и значение декодируются один раз, `+` — не пробел, `..` не разрешается молча — поэтому не `URLSearchParams` и не `new URL`. Объект параметров строится только из объявленных имён экрана: `__proto__` и чужие ключи в него не попадают. Экран по пути ищется только в наборе приложения. URL и причина отказа в заметку, лог и `faults` не идут. Свой URL всегда начинается с одного `/` — запись истории не уведёт на чужой хост.
- **Запись истории — внешние данные** (D-UI-81): строка с пределом до разбора, разбор в `try`, схема формы; слоты проверяет `ScreenRuntime.restore`. Запись не даёт прав сверх ссылки: экран из неё читает данные от имени текущей личности вкладки. Состояние экрана браузер хранит на диске (восстановление сессии) — секретов в состояние экрана не клади. Бросок порта истории несёт URL с параметрами людей, поэтому в `faults` уходит фиксированный текст.
- **Снимок вкладки** (`snapshot()`, `resume(json)`) — тоже внешние данные при восстановлении.
- **Ожидаемый итог** (D-UI-84) — код представления, а не внешние данные: в вид идёт только выход схемы данных экрана, сбой итога — в `faults` фиксированным текстом; в запись истории, снимок и URL итог не попадает.
- **Строки людей — только текстом.** Приёмники разметки и исполнения строки (`innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `DOMParser`, `srcdoc`, `eval(`, `new Function`, `javascript:`) запрещает проверка `DomSinkScanner` в клиенте пакета и в примере (D-UI-85): строки кладут `textContent` и `value`.

## 14. Решения без реализации

Записаны решением и обязательствами; кода нет.

- **Серверный рендер** — цель на горизонте, сейчас не реализуется; инварианты, которые новый код канала обязан держать, путь внедрения, место и оценка — [D-UI-86](../decisions.md). Триггер: первый проект с экраном без входа, превью ссылки или замером первой отрисовки.
- **Markdown контента** — строка в данных экрана, блоки строит представление; модель блоков и разбор — отдельный нейтральный подпуть ядра, не `chat-ui` — [D-UI-87](../decisions.md).
- **Смена личности** — новое соединение; живая смена не реализуется — [D-UI-88](../decisions.md).
- **Где исполняется код экрана, WebSocket вместо SSE, что не проверено без фреймворка** — [D-UI-89](../decisions.md). Не проверены и решаются только первым приложением на фреймворке: как привязка реактивности перерисовывает части страницы и сохраняет набранное, жизненный цикл подписки при монтировании и размонтировании, оживление готовой серверной разметки. Контракт правится релизом пакета по замечаниям, пока он не заморожен (D-UI-5).

## 15. Как тестировать

- **Провод в памяти** — `PageWire`: строки JSON и журнал сообщений; простой ждёт `PageWire.settled()` без таймеров и без счёта ходов (TST-04), пока не завершится вся работа, включая промисы обработчиков сообщений (D-UI-71).
- **Провод на сокете** — [page-socket.test.ts](../../packages/web-ui/src/page-socket.test.ts): сервер на порту `0` на настоящем сокете среды, ожидание — только событиями (подписка на источник области, закрытие на сервере, обрыв, сырые кадры). Что чужое событие экран не перечитал, граница — ответ на свой вызов: кадры одного соединения упорядочены, и сигнал, если бы был отправлен, пришёл бы раньше. Перезапуск сервера — `stop(true)` и новый сервер на том же порту над тем же приложением (прежней сессии нет); вкладка — через `PageReconnector` с `ManualPageClock` и `random: () => 0`: паузу тест сдвигает `clock.advance` на срок из `clock.pending()`, перечитывание ждёт по источнику области. Политику пауз и срока `hello` проверяют подставной сокет и те же часы ([page-reconnector.test.ts](../../packages/web-ui/src/client/page-reconnector.test.ts)), обрыв и `attach` вкладки — подставной конец провода ([page-client.test.ts](../../packages/web-ui/src/client/page-client.test.ts)).
- **Текст страницы** — `PageText` (`dmg-ui/web-ui`): подставная цель показа, текстовое представление на трёх областях, `page()` и `region(name)`. Состояния области — по журналу `client.source(region).subscribe(...)`: подписка сразу отдаёт текущее значение, затем каждое новое. Входящие — так же, по `client.inbox()`; срок отсева — подставными часами `ManualPageClock` (`dmg-ui/web-ui/testing`, `clock.advance(ms)`) без таймеров среды.
- **История** — `MemoryPageHistory`: `back()` и `forward()` ждут клиента без таймеров, `entries()`, `position`, счётчики `pushes` и `replaces` — для сцен «шаг» и «замена»; `reloaded()` — те же записи для новой вкладки и `boot()` (перезагрузка); `fail(error)` — отказ браузера до `fail(undefined)`.
- **Адрес в URL** ([page-urls.test.ts](../../packages/web-ui/src/url/page-urls.test.ts)) — круг «адрес → URL → адрес» на каждом примере каждого экрана набора (`def.examples`) и таблица отказов разбора: строка на причину, `not.toThrow()` в каждой.
- **Показ до ответа** — без таймеров: UC удержан заглушкой конца провода, итог проверяется сразу после вызова жеста (до `await`), откат — по журналу `client.source(region).subscribe(...)` после отпуска ответа; сцены — успех, отказ, устаревшая ревизия, перечитывание, обрыв, переход, «Назад», два действия подряд.
- **Граф** — сцена с `PageGraphProvider` и `ArchReport.of(app)` ([page-rules.test.ts](../../packages/web-ui/src/graph/page-rules.test.ts)); общий порядок — в [Пакете канала](./channel-package.md#11-как-тестировать).
- **Сквозные** — [page-story.test.ts](../../packages/web-ui/testing/page-story.test.ts) (сторис на страничном канале: клиент поверх провода в памяти) и приёмочный [channels-story.test.ts](../../acceptance/channels-story.test.ts) (одна сторис, все каналы).
- **Безопасность** — тесты на недоверенный вход: мусор, строка длиннее предела, чужая пара `(module, uc)`, повтор подписки, чужой или пустой `Origin`, негодный пропуск; строка сервера длиннее предела — с обеих сторон.
- **Браузер** — [examples/web](../../examples/web/README.md): сервер на настоящем сокете, сборка клиента `Bun.build` с проверкой запретных входов по метафайлу ([client-bundle.test.ts](../../examples/web/src/server/client-bundle.test.ts)), модели представлений на `PageClient` в памяти и ручной чек-лист для того, что без браузера не проверить (перетаскивание, окно, «Назад» и «Вперёд» в живом браузере, политика содержимого, пульс).

## 16. Чеклист проекта

- Привязка к `Bun.serve` по шести условиям раздела 4.4: лямбды `open`, `message`, `close`; `data` только из `gate.admit`; `maxPayloadLength`; `closeOnBackpressureLimit` и `backpressureLimit`; пульс `sendPings` и `idleTimeout` 60–120 с; заголовки запроса не в лог. Предел частоты рукопожатий — у прокси.
- Предел кадра считается от публичных `MAX_CLIENT_TEXT` и `MAX_SERVER_TEXT`.
- Страница без годного пропуска не получает скрипт клиента (`PageReconnector.connect()` отказа не возвращает) — «Кто вы?» отдаёт сервер приложения.
- `Referrer-Policy` страницы с формой входа — `same-origin`; политика содержимого, `nosniff`, `no-store`.
- Пропуск — cookie `HttpOnly; SameSite=Strict`, под HTTPS `Secure` и `__Host-`; `origins` — в канонической форме.
- Клиент: первая загрузка — `boot()` с `catch`; ссылки внутри страницы — `route(href)`, `href` из `PageClient.url()`; `pagehide` → `close()` переподключателя; `follow(end, attach)`.
- Каждый экран набора приложения страниц выражается URL (PG-07, иначе сборка `PageUrls` бросает); неразборчивый URL ведёт на вход `start`.
- Ожидаемый итог — только `data` и по схеме данных экрана; ревизия жеста — вида области, а не итога.
- Строки людей — только текстом (`textContent`, `value`); приёмников разметки нет.
- Секретов в состоянии экрана и в параметрах адреса нет: историю браузера читает браузер, «Назад» поднимает прежнее состояние.
- Смена человека — перезагрузкой страницы; вкладки того же адреса при обрыве станут другим человеком (DEBT-UI-44).
- Правила `PG-01…PG-07` зелёные в `arch:check` проекта; граф собран одним поставщиком страниц на все приложения web.
