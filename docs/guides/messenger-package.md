# Пакет мессенджера — гайд

**Назначение:** что даёт общая часть мессенджеров `dmg-ui/chat-ui` и что обязан дать пакет конкретного мессенджера (Telegram, WhatsApp, Slack и другие), чтобы экраны и уведомления набора UI заработали в беседе. Общий контракт канала — [channel-package.md](./channel-package.md); здесь только то, что добавляет мессенджер. Решения — [decisions.md](../decisions.md) (`D-UI-N`), образец пакета — `packages/tg-bot`.

---

## 1. Когда применять

- Канал — личная беседа с ботом или приложением мессенджера: сообщения, варианты под сообщением, текстовый ввод.
- Экраны набора UI пишутся один раз на общей части (`ChatViews`, D-UI-50) и показываются на любом мессенджере; различие мессенджеров общая часть видит только через `MessengerCapabilities` и порт.
- Страничный или консольный канал — не мессенджер: их контракт — [channel-package.md](./channel-package.md). Три уровня каналов (ядро, вид канала, реализация) — [Виды каналов](./channel-package.md#виды-каналов): `chat-ui` — вид «беседа», пакет конкретного мессенджера — реализация.
- Какие задачи фронта закрыты и чем — [Задачи фронта](./frontend-tasks.md).
- Библиотеку мессенджера и сеть выбирает проект: пакет получает клиент портом и сам не ходит в сеть.

## 2. Что даёт `chat-ui` и что обязан дать пакет

Общая часть (`dmg-ui/chat-ui`, D-UI-34): сообщение `Message` и построитель `TextBuilder` (D-UI-35), помощники лимита (D-UI-36), порт `MessengerPort` и возможности `MessengerCapabilities` (D-UI-37, 38), страж `LimitedMessenger` (D-UI-39), узел бесед `Conversations` (D-UI-43…54, 56), исполнитель сообщества `Communities` (D-UI-59), поставщик графа `ChatGraphProvider` (D-UI-57, 60).

Пакет мессенджера даёт:

1. **Порт** `MessengerPort`: `show`, `update`, `retire`, `answer`, `notify` и, если есть сообщество, `community` (`CommunityPort`: `exclude`, `invite`, `approve`). Недоставка — значение `Delivery<T>` с причиной `window`, `blocked`, `rejected`, `unavailable`; бросок порта — дефект. Способ выбирает мессенджер: `update` без правки на месте даёт новое сообщение и `edited: false`; `retire` без правки ничего не делает; `answer` без ответа на нажатие — `ok`.
2. **Возможности** `capabilities` — JSON по `MessengerCapabilitiesSchema`: `name`, `kinds`, `edit`, `text`, `textWithOptions`, `options` (`max`, `label`, `ref`), `pressAnswer`, `initiative`, `community`. Лимиты — числа и единица (`TextLimit`: графема, кодовая точка, UTF-16, байт UTF-8); мессенджер без объявленного предела ставит практическое число. Схема нестрогая: свои поля допустимы. Возможности не по схеме — бросок при сборке.
3. **Сигналы**: апдейт мессенджера → `ConversationSignal` (`enter`, `text`, `press`, `attachment`, `cancel`, `back`, `help`, `link`; у каждого `id`, `peer`, `sender`; `open` — только от проекта, пакет его не строит) → `Conversations.receive`. Сигналы сообщества — `CommunitySignal` → `Communities.receive`. Входящие внешние данные: `receive` не бросает.
4. **Порт сообщества** — если мессенджер исполняет операции (`CommunityPort`); без него реакции сообщества не собираются.
5. **Точки входа** — `ChatAppSpec.entryPoints`: `{ entry, via, key }`, где `entry` — вход приложения, а `via` и `key` — слова мессенджера (команда, ссылка, кнопка меню); `chat-ui` их не трактует.
6. **`ChatAppSpec`** — `{ app, capabilities, entryPoints?, community? }` для поставщика графа; представлений спека не принимает (D-UI-118).
7. **Перекрытие представлений** — `ChatViews.over(presenters)`: новый реестр, где представления пакета перекрывают общие по Def; прежний не меняется. Перекрывается реестр UI-модуля (`<m>ChatViews.over`): так пакет показывает то, что умеет только его мессенджер, не меняя экраны модуля.

Порты проекта для узла бесед (`ConversationsSpec`): `people(sender)` — личность транспорта → uuid, единственный источник личности; `peers(person)` — uuid → собеседник; `store` (`ConversationStore`, `load`/`save` по `peer`); `callers`, `places`, `server`, `codes`, `views`, `observer`, `logger`; необязательный `exits` (`ConversationExits`) — приёмник выходов сторис вне набора UI (D-UI-90, раздел 3); необязательный `texts` (`ConversationTextOverrides`) — замена текстов ответа на устаревшую кнопку, `closed` и `unknownRef` (D-UI-92). Остальное — [channel-package.md](./channel-package.md#3-сборка), разделы [3](./channel-package.md#3-сборка) и [5](./channel-package-view.md#5-представление-показ-и-граф).

## 3. Беседа

Беседа — состояние одного собеседника в одном приложении мессенджера; всё, что переживает перезапуск, лежит в снимке. Пакет мессенджера этого не пишет, но должен понимать пределы.

- **Место.** Живое место — сообщения последнего показа живого экрана или шага; `chat-ui` решает, править его на месте или показать новым, по `edited` из итога `update` (D-UI-51). Пакет не спрашивает у беседы, «умеет ли мессенджер править».
- **Ссылки.** Вариант под сообщением несёт короткую ссылку `[a-z0-9]` до 16 знаков (`MAX_REF_LENGTH`); таблица — 256 записей, старейшие вытесняются (`MAX_REFS`, D-UI-44). `options.ref` мессенджера — число знаков ASCII, которое он вмещает в вариант: ссылка оставленного варианта длиннее него — бросок стража (дефект общей части). Предел берётся из документации мессенджера (раздел 10).
- **Ревизия.** После перезапуска нажатие сверяется по отпечатку показанного вида: совпал — ссылки переносятся на ревизию + 1, нет — `stale` ядра и экран с пометкой «Экран обновился.» (D-UI-46). Устаревшая кнопка в мессенджере остаётся нажимаемой — ответ беседа даёт сама.
- **Снимок.** `ConversationSnapshot` по `ConversationSnapshotSchema` (D-UI-45): снимок не по схеме не принимается целиком, беседа начинается заново, `warn` без данных. Хранилище — порт `ConversationStore`, одно на приложение мессенджера, доверенное. Сообщение места сверх схемы в снимок не идёт: место в снимке остаётся без него (`PlaceMessageSchema`; фрагментов до `MAX_FRAGMENTS`, текст фрагмента до `MAX_FRAGMENT_TEXT`).
- **Путь «Назад».** Снимки экземпляров: до 16 элементов (`MAX_PATH`), элемент — до 8192 знаков JSON (`MAX_STEP_LENGTH`); длиннее — в путь не кладётся (D-UI-53). Сигнал `back` пакет строит из команды или жеста мессенджера, а не из нажатия варианта.
- **Справка.** Сигнал `help` пакет строит из своей команды справки (в Telegram — `/help`, D-UI-107); текст команд беседа не разбирает. Ответ — заметка со справкой живого экрана (без него — общая), состояние беседы не меняется; текст длиннее предела мессенджера режет страж `MessageFit`. Команда справки занимает имя раньше таблицы точек — как `cancel` и `back`.
- **Ссылка на экран** (D-UI-127). Сигнал `link` пакет строит из своей команды (в Telegram — `/link`), она тоже занимает имя раньше таблицы; код ссылки из своего входа по ссылке (в Telegram — `/start <код>`) — в `enter.param`, только по `LINK_CODE`; URL кода для `ConversationsSpec.links.url` строит пакет (в Telegram — `TelegramLinks.url`). Политика беседы — [channel-package.md](./channel-package.md#4-политики-по-исходам).
- **Выход сторис приёмнику.** Порт проекта `exits.accept(exit, trace)` получает `ConversationExit` — `{ peer, person, screen, exit, data? }` — до любого показа беседы (D-UI-90). `true` — живой экран погашен: путь сброшен, прежнее последнее сообщение места уходит (`retire`; с нажатым, если выход по нажатию), место пусто, на нажатие — ответ без текста; свой экран приёмник показывает сам, новым сообщением, сообщения беседы не трогает (`MessageHandle` в порт не идёт). `false`, порта нет или бросок — по цели `ExitTargets` (D-UI-96): `back` — верх пути через `restore`, `home` — вход «в начало», адрес — экран по адресу; «в начало» — для `home`, пустого пути и невосстановленного экрана (раздел «Путь и «Назад»» [Пакета канала](./channel-package-view.md#5-представление-показ-и-граф)); текст выхода — перед видом; бросок — `error` без данных. Ссылки погашенного экрана — «Эта кнопка устарела.»; беседа без экрана — как до первого входа. `accept` исполняется в очереди собеседника: не зовёт `receive` и `deliver` узла бесед для того же собеседника (взаимная блокировка) и не медлит — ответ на нажатие ждёт его.
- **Пределы сигнала.** `id` — до 256 символов, текст — до 64 Ки, `peer` — от 1 до 256 (`MAX_SIGNAL_ID`, `MAX_SIGNAL_TEXT`, `MAX_PEER_LENGTH`); отсев повтора — 128 последних `id` (`MAX_SEEN`). Сверх предела — отказ с `warn` без данных (D-UI-43). `id` у мессенджера должен быть уникален и стабилен при повторной доставке апдейта.

## 4. Сообщение и лимиты

- **Сообщение** — данные: `TextMessage` (`FormattedText` из фрагментов `{ text, styles, link? }` и `options`). Показывается только вид `text`; остальные виды объявлены (D-UI-35). Разбор вида в пакете — с веткой `never`: новый вид должен ломать сборку.
- **Перевод в разметку мессенджера** — дело пакета: стили (`bold`, `italic`, `strike`, `code`, `codeBlock`, `quote`), ссылки, перевод строки `\n`. Строка в `text` — как есть, без экранирования: экранирует пакет под свою разметку.
- **Страж.** Беседа держит `LimitedMessenger`, а не голый порт: он подгоняет каждое сообщение и ответ на нажатие по возможностям через `MessageFit` (D-UI-39). Порядок: лишние варианты с хвоста (`error`), подписи по `options.label`, текст по `textWithOptions` при вариантах, иначе по `text`; ответ — по `pressAnswer`. Уложилось — тот же объект. Страж **не режет молча**: на каждый разрез — запись лога без текста и подписей (источник `chat-ui`; обрезка — `warn`).
- **Помощники.** `TextLength` меряет видимый текст в единице лимита; `TextTrimmer.trim` обрезает с `…` по границе графемы; `TextSplitter.split` делит на части не длиннее лимита, жадно, по разделителям (D-UI-36). Страж обрезает, но не делит: пакет, которому нужно разбиение длинного текста на несколько сообщений, зовёт `TextSplitter` сам до порта.
- **Пустой текст.** `TextSplitter.split([])` возвращает одну пустую часть, а не пустой список. Мессенджеры чаще всего отвергают пустое сообщение: пакет решает, что делать с пустой частью (подставной `MemoryMessenger` отвергает пустой текст без вариантов как `rejected`).
- **`MessengerCapabilities.text` не меньше длины `…`** в своей единице (в UTF-8 — 3 байта), иначе схема отвергнет возможности.

## 5. Уведомления и порт `peers`

Узел бесед доставляет уведомления (`Conversations.deliver`, D-UI-56): собеседника получателя даёт `peers(person)` — личный чат личности в приложении мессенджера. `peers` обязан быть обратным к `people`; пакет этого не проверяет и **доверяет порту**: при неверном `peers` уведомление уйдёт не тому. Собеседник проходит ту же проверку длины, что и у сигнала.

- Уведомление идёт в `notify` порта: у мессенджера с окном инициативы способ (обычное сообщение, шаблон) выбирает пакет. Нет права писать первым — `window`, собеседник недоступен — `blocked`.
- Недошедшее — `warn` без броска, без отсева, ссылки снимаются; уведомление не копится. Повтор по событию-причине отсеивается ключом в снимке (128 ключей, `MAX_NOTIFIED`). Подробности — [channel-package-boundary.md](./channel-package-boundary.md#9-доставка-уведомлений), раздел 9.
- DEBT-UI-21: `NotificationDelivery.deliver` не возвращает итога; DEBT-UI-22: ссылки уведомлений делят таблицу с экранными ([debt.md](../../debt.md)).

## 6. Сообщество

Включается, если у приложения есть манифесты `ChatCommunitySpec` (`signals`, `reactions`) в `ChatAppSpec.community` (D-UI-59, 60). Один и тот же объект получают граф и `Communities` — копии не нужны.

- **Манифесты.** Сигнал — вид сигнала мессенджера (`joined`, `left`, `added`, `removed`, `requested`) → command UC; `input` — поле входа UC → `community` (ключ домена) или `person` (uuid); `strangers` — вызывать и для незнакомого. Реакция — событие домена → query UC → операция (`exclude`, `invite`, `approve`; `inviteLink` объявлена, но не исполняется — DEBT-UI-25); цель — поля выхода UC `targets.community` и `targets.person`.
- **Исполнитель.** `new Communities({ app, community, messenger, dispatch, context, people, members, keys, handles, limit? })`, `receive(signal)` — вход сигнала (не бросает), `start()` — подписка реакций, возвращает отписку; повторный `start()` без остановки бросает. Домен видит только свои ключи: handle группы и личность транспорта до него не доходят — переводят четыре порта.
- **Вызывающий — `system`.** UC сигнала вызывается от `SystemCaller` узла, без человека; в `callers` UC должно быть `system`, политика — явная, `allowAll` только при `callers: ['system']` (иначе UC вызовет любой человек с чужим `userId`).
- **Query UC реакции — граница доступа.** Вызывается без субъекта, поэтому сам проверяет текущее состояние и не отдаёт целью поля своего входа.
- **Повтор события.** Сигнал отсеивается по ключу (вид, handle, участник, `id`); один апдейт на нескольких вступивших — несколько сигналов; исполненная операция реакции — по своему ключу. Отсев в памяти и после перезапуска не переживает (DEBT-UI-24); пределы — `CommunityLimits` (`signals`, `reactions`; по умолчанию 1024).
- **Данные сигнала — строки.** Числа транспорта пакет переводит `String(...)`; иначе сигнал отвергнут по пределу.
- Сигналы и операции должны быть объявлены в `capabilities.community` (CH-03, раздел 7).

## 7. Граф и правила

`ChatGraphProvider` — один на все приложения мессенджеров графа (имя `CHAT_PROVIDER`, D-UI-57); спека — `{ apps: ChatAppSpec[] }`; представлений и примеров поставщик не принимает, сборка графа синхронна (D-UI-118). Узлы и виды рёбер — `CHAT_NODE_KINDS`, `CHAT_EDGE_KINDS`.

Лимиты мессенджера (CH-01) — не правило графа, а проверка единицы: тест вызывает `ExampleLimits` (`dmg-ui/chat-ui/testing`) на сборке представлений приложения или набора с возможностями мессенджера ([channel-package.md](./channel-package.md#11-как-тестировать)). Правила, которые подключает `rules()` поставщика:

| ID | Что проверяет |
|---|---|
| CH-02 | у каждого входа беседы есть точка входа (`entryPoints`) под тем же приложением |
| CH-03 | сигнал или реакция сообщества приложения принимается или исполняется возможностями мессенджера |

**Пример поставщика пакета мессенджера** — `TelegramGraphProvider` в `packages/tg-bot`: отдельный поставщик графа (`GraphProvider`) со своим префиксом правил (`TG`, ARC-13): `rules()` отдаёт шесть правил над узлами точек входа, а узлы и рёбра общей части остаются у `ChatGraphProvider`. Свои имя поставщика и префикс правил пакет берёт сам.

## 8. Безопасность

Общие правила канала — [channel-package-boundary.md](./channel-package-boundary.md#7-безопасность-для-автора-канала), раздел 7; здесь то, что относится к пакету мессенджера.

- **`peer` и `sender`.** Узел бесед связь `peer` и `sender` не сверяет: первый отправитель в новый `peer` становится владельцем беседы. Пакет личного чата сверяет их сам и принимает только личный чат; групповой разговор не поддержан.
- **Подлинность апдейта — на проекте.** Откуда пришёл апдейт и что он не подделан, решает транспорт и проект, не `chat-ui`.
- **Ключ хранилища.** `peer` — непрозрачная строка без предела длины и набора знаков: в путь файла хранилища как есть не кладётся (хеш или экранирование).
- **Личность — только `people(sender)`.** Отправитель без личности и чужая личность беседу не трогают. Uuid в сигнал не попадает.
- **Снимок и хранилище** — доверенные: в снимке собранный вход и подписи; схема отсекает мусор, а не подделку.
- **Лог без данных.** Ни текста, ни `peer`, ни handle, ни ссылок, ни `press`: так же в записях пакета (ERR-07).
- **Дублирование действия.** Если процесс упал между исполнением UC и записью снимка, мессенджер повторит сигнал — действие может исполниться дважды (DEBT-UI-18); очереди собеседника без пределов (DEBT-UI-19).
- **Сообщество:** личность участника — из транспорта, вызывающий — `system`, query UC — граница доступа (раздел 6).

## 9. Как тестировать

- **Два подставных мессенджера.** `MemoryMessenger.editing()` — правит на месте, много вариантов, писать первым можно всегда; `MemoryMessenger.windowed(clock)` — не правит, три варианта, окно инициативы на сутки, ответа на нажатие нет (D-UI-40). Они строгие: сообщение, которое страж изменил бы, и пустой текст без вариантов отвергаются как `rejected`; `failNext` задаёт следующую недоставку; журнал — `journal`, что видит собеседник — `chat(peer)` (`ChatLine`).
- **Тест на каждый мессенджер** — `describe.each([['editing', …], ['windowed', …]])`: код, который полагается на правку или на окно, ловится на противоположном наборе. Образец — `packages/chat-ui/testing/conversation-story.test.ts`.
- **Свой мессенджер** проверяется тем же сценарием: порт пакета против подставного там, где различие в способе, а не в возможностях.
- **Граф.** `ExampleDialogArch` и учебные приложения — `dmg-ui/example`; сцену со своим мессенджером собирают по его образцу (`ArchApp` с `UiGraphProvider` и `ChatGraphProvider`), код выхода и `report.rule(id)` — `ArchReport` из `dmg-ui/testing/fixtures`.
- **Сквозной сценарий** (TST-09) — по одному на мессенджер; поверх каналов — `acceptance/`.
- **Браузерные тесты** мессенджеру не нужны; правило для страничного канала — [Web-канал, раздел 15](./web-channel-checks.md#15-как-тестировать).
- **Граница порта:** возможности не по схеме и ссылка длиннее `options.ref` — тесты на бросок при сборке; недоставка — значение, не бросок.

Цифры — из документации API на 2026-11-16; сверять с документацией API на дату работы над пакетом. WhatsApp и Slack здесь только проверка общей части: пакетов у них нет.

## 11. Чеклист нового пакета мессенджера

- Порт: пять намерений, недоставка — значением с причиной, бросок — только дефект; `update` без правки даёт `edited: false`.
- `capabilities` проходят `MessengerCapabilitiesSchema`; пределы взяты из документации API на дату работы (раздел 10); `text` не меньше длины `…` в своей единице.
- Сигналы строятся из апдейтов с уникальным стабильным `id`; `receive` не бросает; `peer` — 1–256 символов, `sender` сверяется с `peer`.
- Подлинность апдейта проверена на проекте; `people` и `peers` взаимно обратны.
- Хранилище бесед — доверенное; `peer` в путь файла не кладётся.
- Приёмник выхода `exits` (если задан): `accept` не зовёт узел бесед того же собеседника, не медлит, показывает своё новым сообщением; отказ — `false`, а не бросок.
- Разметка: стили, ссылки и экранирование под мессенджер; ветка `never` на виде сообщения; пустая часть `TextSplitter` обработана.
- Уведомления: `notify` отвечает окну инициативы (`window`, `blocked`).
- Сообщество (если есть): манифесты в `ChatAppSpec.community`, UC с `system` в `callers`, query UC — граница доступа, четыре порта перевода, `capabilities.community` объявляет всё исполняемое (CH-03).
- Граф: `ChatAppSpec` с `entryPoints` на каждый вход (CH-02), примеры в лимитах (CH-01), свой префикс правил и имя поставщика (ARC-13).
- Лог без данных (ERR-07); нейтральность: слов мессенджера нет в экранах и ядре.
- Тесты: два подставных мессенджера через `describe.each`, `ExampleDialogArch`, сквозной сценарий на мессенджер (TST-09), недоверенный вход.
