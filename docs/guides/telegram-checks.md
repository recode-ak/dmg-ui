# Telegram — отказы, тесты, непроверенное

**Назначение:** отказы Bot API, тестирование и пример, что не проверено на живом Telegram; лист гайда [Telegram](./telegram.md).

## 9. Отказы Bot API

Разбор — `BotApiFailure` ([bot-api-failure.ts](../../packages/tg-bot/src/bot-api/bot-api-failure.ts), D-UI-61); недоставка — значение `Delivery`, методы мессенджера не бросают.

| Код | Причина (`UndeliveredReason`) | Что делает пакет |
|---|---|---|
| 403 | `blocked` | собеседник заблокировал бота; недоставка и `warn` |
| 429 | `unavailable` | без повтора по `retry_after` — DEBT-UI-26 |
| 500 и выше | `unavailable` | недоставка, без отката |
| прочие (400 и др.) | `rejected` | дефект показа; `warn` |
| 400 «message is not modified» | успех | правка тем же содержимым; при правке текста и `retire` — `ok` |
| `rejected` при правке текста (кроме «not modified») | откат | новое сообщение, прежнее уводит беседа |
| отказ с `migrate_to_chat_id` | `rejected` | группа стала супергруппой — DEBT-UI-27 |
| бросок порта или ответ не по схеме | `unavailable` | `error` без данных |

В `warn` — мессенджер, операция, метод, `error_code`, описание сервера (до 200 знаков, `TELEGRAM_LIMITS.description`) и имя ошибки; ни id, ни текстов, ни `callback_data`.

## 10. Тестирование и пример

- **`MemoryBotApi`** (`dmg-ui/tg-bot/testing`) — `BotApi` в памяти с журналом вызовов; ведёт себя как Bot API: правка неизвестного сообщения — 400, правка тем же — 400 «message is not modified». `failNext`, `throwNext`, `failOn(метод, отказ)` — отказ или бросок следующего вызова; `holdOn(метод)` держит вызов до `release` — очередь сообщества без таймеров. `chat(chatId)` — сообщения глазами собеседника. Операции группы и `setMyCommands` — запись в журнал и `ok`, модели членства нет (D-UI-63). Сценарий на `MemoryBotApi` проверяет только проводку — сообщение, правку на месте, границы листания; поля карточки уже покрыты тестом кода экрана и снимком, их не повторяй (TST-08).
- **`TestUpdates`** — построитель апдейтов: `text`, `press`, `groupText`, `joined`, `left`, `botAdded`, `botRemoved`, `joinRequest`.
- **Сцены:** [telegram-story.test.ts](../../packages/tg-bot/testing/telegram-story.test.ts) — диалог, уведомление и меню; [telegram-back-story.test.ts](../../packages/tg-bot/testing/telegram-back-story.test.ts) — «Назад», `/back` и подписи без повторов; [telegram-community-story.test.ts](../../packages/tg-bot/testing/telegram-community-story.test.ts) — сообщество.
- **Адаптер на loopback.** Тест адаптера и опроса идёт на `127.0.0.1` с поддельным сервером Bot API: проверяется тело запроса на проводе, отказы, сбой транспорта без токена; внешней сети нет (D-UI-68).
- **Что показывает пример** (D-UI-105, D-UI-106, D-UI-107, D-UI-108): отключённое действие с тостом, подсказку поля, `/help` отдельным сообщением, автокнопку «Назад» и `/back`, «К моим задачам». С одним аккаунтом «К моим задачам» достижимо самоназначением: «Хлеб» → «Назначить» → свой uuid → `/assigned` → «Карточка исполнителя». Тест «подписи без повторов» — в приёмке и `telegram-back-story.test.ts`.
- **Браузерные тесты** Telegram не касаются: правило, когда они нужны, — [Web-канал, раздел 15](./web-channel-checks.md#15-как-тестировать). Что закрыто в Telegram по задачам фронта — [Задачи фронта](./frontend-tasks.md).
- **Пример `packages/example/src/runners/tg-bot`** запускается на живом Telegram: запуск, переменные, чек-лист ручной проверки, проба `bun run example:tg:probe <chat_id>` — в [README примера](../../packages/example/src/runners/tg-bot/README.md). Консоль при обычной работе молчит (в ней только `warn` и `error`, ERR-07); что уходит в Telegram, показывает трасса `EXAMPLE_TG_TRACE` — файл JSON-строк по вызову, в нём тексты и id людей, в git он не попадает. `.env.development` Bun читает без настроек.

## 11. Что не проверено на живом Telegram

Пример не имеет сообщества, а ручная проверка шла с одним аккаунтом. Эти пункты покрыты тестами на подставном порте, но живой Telegram их не подтверждал — проверить при первом подключении группы проекта:

- **Группа.**
  - `from` апдейта равен боту при ban, unban и approve — на этом держится отсев эха; опора — вывод, в документации Bot API он прямо не сказан. Если неверно, исключение вызовет `left` и петлю.
  - Бот — администратор: без него `joined` и `left` не приходят.
  - `ChatMemberRestricted.is_member` у участника с ограничениями.
  - Ban в супергруппе удаляет сообщения человека.
  - Принятие заявки без права бота `can_invite_users` — отказ.
  - Регистр входящих команд.
  - Синхронность часов сервера (срок бана 300 с).
  - Миграция группы в супергруппу (DEBT-UI-27).
- **Поручение между двумя аккаунтами.** Назначенному человеку приходит «Вам назначена задача», исполнителю — «Поручение выполнено»; чужой аккаунт получает тишину и ответ без текста на нажатие. На одном аккаунте проверена только блокировка бота: `warn` 403, без падения, доставка возобновляется после разблокировки.
- **Отключённое действие.** Замечают ли тост `answerCallbackQuery` без `show_alert` и как клиенты показывают `🚫` в подписи, в том числе «🚫 Предыдущая страница» (D-UI-105, D-UI-108; пункты Ж1, Ж2 README примера).
- **Справка и меню команд.** `/help` работает, но в меню не публикуется; ждёт ли его клиент в списке (D-UI-107; пункт Ж5).
- **Ссылка на экран.** Что `t.me/<бот>?start=<код>` у человека с уже открытым чатом шлёт `/start <код>` и как клиенты показывают URL в сообщении `/link` — проверено только на подставном порту (D-UI-127).
- **Не доходит и до учебных экранов.** Вебхук и хранилище бесед на диске (пример — `getUpdates` и память).
