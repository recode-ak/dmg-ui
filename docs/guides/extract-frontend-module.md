# Вынести фронт-модуль канала в свой репозиторий — гайд

**Назначение:** как пара «модуль × канал» — представления UI-модуля в одном канале, пакет `@<scope>/fe-<m>-<канал>` — уходит из монорепо в свой репозиторий и команду (GR-UI-01) и как туда же уходит канал целиком (GR-UI-02): что уже держит проверка структуры и что пишется руками.

> **Вживую не проверено** ([D-UI-116](../decisions.md)). Сценарии обеспечены решениями и раскладкой, машина проверяет только структуру. Ни одного фронт-модуля пакетом ещё не выносили: шаги ниже — план, а не пройденный путь. При первом выносе пакет правится по его итогам, статус сценария — [Слои фронта](../concepts/frontend-layers.md#сценарии-роста).

---

## 1. Когда применять

- Модулю в одном канале нужна своя команда и свой цикл выпуска: «школа для бота» — `frontend/school/telegram` (GR-UI-01).
- Канал целиком (весь web) уходит в свой репозиторий — §4 (GR-UI-02).
- Профиль — `monorepo`: единица выноса — пакет workspaces, имена пакетов — [naming.md §2](../reference/naming.md#пакеты-в-monorepo). В `single` единиц нет: слои фронта (UI-28…UI-34) держатся, а ARC-14 и ARC-15 `dmg-core` молчат — сначала пакеты, генератора для них нет.
- Не для раздела на другом фреймворке в том же репозитории: это свой пакет представлений раздела (GR-UI-03), выносить его не нужно. Кирпич для разделов на разных фреймворках — [shared-brick.md](./shared-brick.md).

## 2. Что уже держит проверка

Пока `bun run check` монорепо зелёный, границы ниже держит машина — `arch:check`, конструкторы реестров и тест имён:

| Граница | Правило | Что это даёт выносу |
|---|---|---|
| канал модуля видит свой модуль, свой код, базу своего модуля, описание, `kit` своего канала и базы; другой канал и чужие модули — нет | UI-31 | пакет пары уносит только свой модуль |
| чужой модуль того же канала — только `public.ts` | UI-32 | соседи видят вход `./public` пакета, а не его файлы |
| код модуля не видит каналов и чужих модулей | UI-30 | код модуля один на все каналы и не тянет представлений |
| `kit` не видит модулей фронта | UI-33 | общее канала уезжает или ставится пакетом без модулей |
| оболочка берёт код и представления модуля только через `index.ts` | UI-34 | оболочка монолита ставит пакет пары и берёт его вход `.` |
| реестр модуля полон по модулю — отказ конструктора | UI-06 | пара проверяет полноту сама, без оболочки и чужого графа |
| экраны сторис — её модуля; исход и ссылка в чужой модуль — только `start` его сторис | UI-35, UI-36 | в описании модуля нет чужих экранов; переход в чужой модуль — адрес, а не импорт |
| каждый импорт объявлен в `package.json` единицы; между единицами — имя и `exports`; описание не объявляет реализаций фронта; вход графа не доходит до кода и представлений | ARC-14, ARC-15, ARC-16 `dmg-core` | `package.json` пары полон, граф строится без её пакета |
| имя и место файлов: дерево канала модуля — дерево описания | `NM-01` (тест потребителя, `UiFileNames`) | файл пары находится по сторис так же, как в описании |

Реестр модуля ключуется по Def, а `id` экрана даёт сборка оболочки ([D-UI-118](../decisions.md)): пара не знает ни набора, ни приложения, в которые её соберут.

Не проверяется машиной: что `public.ts` отдаёт кирпичи, а не представления экранов, — ревью ([D-UI-120](../decisions.md)); пакеты npm в описании (`dmg-ui/server`, `node:*`) — ревью ([D-UI-117](../decisions.md)); лимиты мессенджера пары без оболочки — долг `DEBT-UI-60`; `extends` в `tsconfig` к корню монорепо и алиасы `paths` — как у бэка, D-108 `dmg-core`.

## 3. Шаги

1. **Проверка — машина.** `bun run check` монорепо зелёный: UI-28…UI-34, ARC-14…ARC-16, UI-06, UI-35…UI-37, `NM-01`. Красный — сначала граница, потом вынос.
2. **Состав выноса — руками.** Уходит пакет пары `frontend/<m>/<канал>`. Канал на базе тянет базу своего модуля: представления `telegram` — перекрытия над `chat` того же модуля (`<m>ChatViews.over`), поэтому пакет `fe-<m>-chat` уходит вместе с парой или ставится пакетом. Код модуля `fe-<m>` один на все каналы модуля: обычно остаётся у владельца описания и ставится пакетом.
3. **Публикация — руками.** Пара зависит от `@<scope>/ui`, `@<scope>/fe-<m>`, `@<scope>/<канал>-kit`, `@<scope>/fe-app`, `./public` соседних пар и контрактов домена. В другом репозитории их публикуют в приватный реестр: git-зависимость Bun берёт репозиторий целиком, не подпапку (D-UI-117, «Цена»; D-108 `dmg-core`).
4. **Согласованный выпуск — руками.** Правка экрана трогает описание, код и представление (D-UI-117, «Цена»); после выноса это два репозитория. Новый экран в описании без представления в паре — отказ UI-06 при старте оболочки монолита: версию `@<scope>/ui` пара поднимает вместе со своими представлениями.
5. **`tsconfig` — руками.** `extends` к корню монорепо — не импорт, проверка его не видит: у пары свой `tsconfig.json`; у web — с DOM, как у оболочки web учебного проекта (`runners/web/tsconfig.json`).
6. **Своя оболочка для разработки — руками.** Раннер в репозитории пары: приложение UI только со сторис модуля — переходы в чужие модули отрезаны составом приложения, ядро их действие не показывает (`omits`, D-UI-95); сборка реестров `AppCodeLoaders.of(app, …)` и `AppChatViews.of(app, …)` (или `AppPageViews`) — модули области называет `ModuleRegistries.required(app)`; вызов UC — `ModuleApiDispatch` к бэку по транспорту или подставное приложение из `dmg-core/testing`. Сборка — по [channel-package.md](./channel-package.md#3-сборка), образец оболочки — `runners/dialog` учебного проекта.
7. **Тесты единицы — руками, форма держится машиной.**
   - UI-06 — конструктор реестра пары в её тесте, без оболочки.
   - CH-01 — `ExampleLimits` на сборке оболочки разработки: сборки области одного модуля нет (`DEBT-UI-60`).
   - `NM-01` — `UiFileNames` с зоной `channels` пары. Пара `.view` ↔ манифест ищется в описании, а зоны `ui` и `logic` обязательны и пустыми быть не могут: тексты описания из установленного `@<scope>/ui` и кода из `@<scope>/fe-<m>` передаются тесту под путями зон `ui` и `logic` — руками, вживую не проверено.
   - Помощники тестов соседей — только через их `/testing`, объявленный зависимостью (ARC-15).
8. **Монолит — машина.** Оболочка монолита ставит пакет пары и берёт его вход `.` (UI-34). Граф строится без реализаций фронта (ARC-16), поэтому вынос пары граф не меняет; переходы в модуль пары и из него — адреса `start` сторис (UI-36), их исполняет оболочка монолита.

## 4. Канал целиком (GR-UI-02)

- **Уходят:** оболочка `runners/<r>` (приложения UI, вход графа, `.arch`, маршруты, точки входа, сборка реестров), все пары `frontend/<m>/<канал>`, `frontend/<канал>-kit`. Канал на базе — вместе с базой или с её пакетами.
- **Остаются у владельца описания и ставятся пакетами:** `@<scope>/ui`, `@<scope>/fe-<m>` всех модулей, `@<scope>/fe-app`, контракты домена и `kernel`. Описание и код экранов нейтральны к каналу (UI-28, UI-30): канал уходит без их правки.
- **Вызов UC — руками.** Оболочка в одном процессе с бэком — `ApiAppDispatch`; в своём процессе — `ModuleApiDispatch` над `ModuleApi` `dmg-core/app` и своим `CommandTransport` ([channel-package.md](./channel-package.md#3-сборка); транспорт — `node_modules/dmg-core/docs/reference/transport.md`). Реализаций транспорта в пакетах нет.
- **События — руками.** `UiNotifier` и перечитывание экранов слушают шину контекста сервера (`context.bus`); в `dmg-core` шина — только в памяти процесса. Доставку событий бэка в процесс канала пишет проект.
- **Граф и `arch:check` — в репозитории канала.** Вход графа оболочки: `def` — `AppDef` из пакета домена, `UiGraphProvider({ set, apps, channels })` с набором из `@<scope>/ui`, поставщик графа канала. `ArchApp` канала называет свои слои в `ArchApp.layers` ([naming.md §2](../reference/naming.md#2-дерево-проекта)).

## 5. Чеклист правил

- UI-28…UI-34 — слои фронта чисты до выноса.
- UI-06 — реестр пары полон сам по себе; UI-35, UI-36 — в чужой модуль только `start`.
- ARC-14 — каждый импорт пары объявлен; ARC-15 — между пакетами только имя и `exports`, помощники тестов — через `/testing`; ARC-16 — описание не объявляет реализаций фронта.
- `NM-01` — дерево пары повторяет дерево описания.

## 6. Типичные ловушки

- Имя модуля с дефисом совпадает с парой «модуль × канал» в имени пакета: модуль `x-web` и пара `x` × `web` — оба `fe-x-web` (D-UI-117, «Цена»).
- Описание обновили, пару — нет: оболочка монолита не стартует с UI-06 «нет представления для …».
- `public.ts` реэкспортирует представление экрана — проверка молчит, а соседний модуль начинает зависеть от чужого экрана: экран — граница модуля, к нему ведёт переход (D-UI-120).
- Установка `--linker hoisted`, алиас `paths` на `src` соседа, общая папка помощников тестов в корне монорепо — необъявленный импорт работает до выноса; ARC-14 и ARC-15 ловят только то, что видят по спецификатору (D-108 `dmg-core`).
- Лимиты мессенджера пары проверяются только в тесте оболочки: без оболочки разработки длинный пример уйдёт в монолит незамеченным (`DEBT-UI-60`).
