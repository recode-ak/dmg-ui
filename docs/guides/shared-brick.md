# Общий кирпич между фронт-модулями — гайд

**Назначение:** как сделать часть представления, нужную нескольким UI-модулям, — в одном канале и в разделах web на разных фреймворках (GR-UI-04): где лежит кирпич, как его берут соседи, что делать вместо чужого экрана и как обойти запрет, когда очень нужно. Что держит проверка структуры и что пишется руками.

> **Вживую не проверено** ([D-UI-116](../decisions.md)). Кирпич в `kit` и через публичный вход проверяет `arch:check` (учебный проект — `AccountStatus`, `web-kit`). Веб-компонент для разделов на разных фреймворках и карточка — план: пакет их не исполняет, `lit` в зависимостях пакета нет. Статус сценария — [Слои фронта](../concepts/frontend-layers.md#сценарии-роста).

---

## 1. Что взять вместо чужого

Чужой модуль закрыт: его код, представления, реестры и представления его экранов брать нельзя ([D-UI-120](../decisions.md)). По нужде:

| Нужно | Что делать | Где |
|---|---|---|
| весь экран чужого модуля | переход на `start` его сторис (`leads`) | описание; UI-03, UI-35 |
| часть его данных | карточка — описание кирпича (§4) | описание и каналы модуля-хозяина |
| та же логика | свой экран на тех же UC | свой модуль |
| кирпич с хозяином по смыслу | публичный вход канала модуля-хозяина (§3) | `frontend/<m>/<канал>/public.ts` |
| кирпич без хозяина | общее канала (§2) | `frontend/<канал>-kit` |
| общее кода над доменом | общее фронта | `frontend/app` |

## 2. Кирпич без хозяина — `<канал>-kit`

1. **Файл — руками.** `frontend/<канал>-kit/<кирпич>.ts`: кирпич, тема, помощники представлений одного канала. Видов UI в `kit` нет — экранов, кода, представлений (`NM-01`). Образец — `frontend/web-kit` учебного проекта (обёртка `ExampleScreenView`, помощники DOM).
2. **Что держит машина.** `kit` не видит модулей фронта и чужих каналов — только `kernel`, `fe-app`, описание, контракты домена и `kit` базы (UI-33). Канал модуля и оболочка берут `kit` без ограничений (UI-31, D-UI-117).
3. **В `monorepo`** — пакет `@<scope>/<канал>-kit`, каждый потребитель объявляет его зависимостью (ARC-14).

## 3. Кирпич с хозяином — публичный вход

1. **Файл — руками.** Кирпич лежит в канале модуля-хозяина, обычно в `shared/` (`frontend/users/chat/shared/account-status.ts`), и выходит наружу реэкспортом из `frontend/<m>/<канал>/public.ts` — только кирпичи, без представлений экранов и реестров.
2. **Потребитель.** Канал другого модуля импортирует из `public.ts` хозяина того же канала (`profile/chat/check-profile/profile-summary.view.ts` → `AccountStatus` из `users/chat/public`).
3. **Что держит машина.** Импорт чужого модуля того же канала мимо `public.ts` — UI-32; другой канал — UI-31; оболочка `public.ts` не берёт — только `index.ts` (UI-34). В `monorepo` `public.ts` — вход `./public` пакета `@<scope>/fe-<m>-<канал>` (ARC-15).
4. **Что машина не держит — ревью.** Что `public.ts` отдаёт кирпичи, а не представления экранов: экран — граница модуля, к нему ведёт переход.

## 4. Карточка — описание кирпича

Кирпич, который показывает данные модуля-хозяина в чужих разделах и в нескольких каналах, описывается как экран — один раз, нейтрально к каналу:

- **Описание** — в `platform/ui` модуля-хозяина: схема данных (выход UC или `view()`), примеры; представления — в каналах модуля-хозяина, наружу — через `public.ts`.
- **Манифеста карточки в пакете нет.** Вид Def карточки добавляется по второму использованию. До него проект может завести свой вид Def поставщиком графа (`node_modules/dmg-core/docs/guides/graph-extension.md`), но `ScreenDef` о нём не знает: связь «экран показывает карточку» объявляет сама карточка.
- **Руками и ревью:** что данные карточки совпадают со схемой, а представления карточки полны по каналам, — машина не проверяет.

## 5. Разделы web на разных фреймворках — веб-компонент

Раздел web — UI-модуль со своим пакетом представлений; соседние разделы могут быть на React, Svelte или без фреймворка (GR-UI-03). Общий кирпич для них — веб-компонент (Custom Element, например на `lit`): он работает в любом фреймворке и без него. Форма та же: без хозяина — в `web-kit`, с хозяином — в `public.ts` канала `web` модуля-хозяина.

Подводные камни — руками:

- **Реестр тегов глобальный.** Один тег — одна версия на страницу: два раздела с разными версиями кирпича не встанут рядом. Версия кирпича — общая для всех разделов страницы, тег не переименовывается под версию без нужды.
- **React до 19** не передаёт свойства-объекты и не слушает свои события Custom Element: нужны обёртки для свойств и событий.
- **Тема — CSS-переменные.** Стили раздела в Shadow DOM не проникают: кирпич читает тему через CSS-переменные, которые задаёт оболочка.
- **SSR ограничен.** Веб-компонент рендерится на клиенте; серверная отрисовка требует своей поддержки фреймворка.
- **Зависимость.** `lit` — зависимость проекта (`web-kit` или пакета хозяина), не `dmg-ui`: пакет веб-компоненты не исполняет и не проверяет.

## 6. Отступление — когда очень нужно

Взять чужой модуль того же канала мимо `public.ts` можно только записью реестра долга кода проекта ([D-UI-120](../decisions.md), ARC-12 `dmg-core`):

1. **Запись — руками.** В реестре долга кода проекта (`ArchApp.debt`) — запись с полем «Правило» `UI-32`, «Место» — glob'ы файлов-импортёров, причиной и триггером снятия.
2. **Что держит машина.** Импорт по месту записи не нарушение UI-32; glob Места без нарушения — ARC-12: запись снимается вместе с последним импортом.
3. **Не снимается записью:** UI-28…UI-31, UI-33, UI-34 — описание с реализациями, другой канал, `kit` с модулями, оболочка мимо `index.ts`; чужой код модуля (`fe-logic`) — у него нет публичного входа, общее — в `frontend/app`.

## 7. Чеклист

- Кирпич без хозяина — `<канал>-kit`, видов UI в нём нет (UI-33, `NM-01`).
- Кирпич с хозяином — в канале хозяина, наружу — `public.ts`; потребитель — того же канала (UI-31, UI-32).
- Чужой экран — переходом на `start` его сторис (UI-03, UI-35), не реэкспортом представления.
- Веб-компонент — одна версия тега на страницу, тема — CSS-переменными.
- Отступление — запись с «Правило» `UI-32` и «Место»; без записи импорт мимо `public.ts` — нарушение.
