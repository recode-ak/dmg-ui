# Процесс UI на `dmg-ui`

**Назначение:** что процесс разработки на `dmg-core` получает от слоя UI: место роли `dmg-ux` в постановке, срез UI и состав его ролей, порядок, когда домен и UI в одном срезе, что проверяет гейт. Общий процесс — уровни постановки, принципы, роли, единица работы, эскалации, модели — `node_modules/dmg-core/docs/process.md`; здесь он не повторяется. Документ не зависит от инструмента ведения задач: где лежат spec, план и постановки срезов, решает проект.

---

## 1. Роли слоя UI

Пакет доставляет две роли (`dmg-core sync`, вход `dmg-ui/dmg-core`):

| Роль | Вопрос | Когда |
|---|---|---|
| [dmg-ux](../agents/roles/dmg-ux.md) | как сделать путь человека в приложении удобнее всего | постановка: путь человека новый или меняется |
| [dmg-ui-author](../agents/roles/dmg-ui-author.md) | как выразить постановку среза UI манифестами и кодом `dmg-ui` | реализация среза UI |

Процессные роли `dmg-core` (`dmg-tech-lead`, `dmg-test-designer`, `dmg-reviewer`, `dmg-data-keeper`) — общие на все слои. Слой для них — какие листы читать и какой каталог правил применять: у UI это вход [llms.txt](../llms.txt) пакета и [каталог правил](./reference/rules.md) (`UI`, `CH`, `TG`, `PG`, `NM`); своих копий этих ролей у `dmg-ui` нет.

## 2. Постановка: место `dmg-ux`

Цепочка постановки `dmg-core` — `user` → `ux` → `product` → `architect`; роль `ux` в ней — `dmg-ux`.

- **Вызывать** — когда путь человека новый или меняется: новая цель, новый шаг, другой порядок шагов, новое уведомление, другой текст отказа.
- **Не вызывать** — когда UX не меняется: перенос экранов на `dmg-ui` с тем же путём, переименование, правка кода без смены того, что видит человек. Сценарий тогда — прежний путь, его описывает постановка среза.
- **Выход** — сценарий на языке манифестов `dmg-ui` и «было → стало» по шагам человека; вопросы к `product` — что нужно от домена.
- **Обратная петля** — как в общем процессе: домен не позволяет сценарий — `product` возвращает его `dmg-ux` с причиной; `dmg-ux` переделывает сценарий, а не домен.
- Продуктовое знание (концепция UX проекта, концепции модулей) роль получает от проекта — блоком «Знания проекта» (`roles.refs`, `node_modules/dmg-core/docs/reference/docs-format.md` § 9).

## 3. Срез UI

Срез UI — UI-модуль или одна сторис со своими экранами и каналом: описание, код модуля, представления канала, правка оболочки. Граница — граница UI-модуля: между модулями только переход на `start` чужой сторис ([Слои фронта](./concepts/frontend-layers.md)), поэтому срез одного модуля не ждёт другого.

```
dmg-tech-lead     → постановка среза: сторис, экраны, Def UC, «было → станет»
dmg-test-designer → red: код экранов, исходы действий, снимки примеров
dmg-ui-author     → описание, код, представления, оболочка → гейт
dmg-reviewer      → отчёт с ID правил UI
```

- **Домен и UI в одном срезе** — сначала домен и Def UC, которые читает и вызывает экран (`dmg-domain-author`, `dmg-api-author`), затем UI. Экран опирается на контракт UC (вход, выход, `errors`, `visible`); пока Def нет, автору UI нечего читать и вызывать.
- **UI без домена** — Def UC уже есть: срез начинается с `dmg-test-designer`. Нужен новый UC или правка контракта — эскалация в постановку, а не UC внутри среза UI.
- **`dmg-data-keeper`** — по своему триггеру: срез UI трогает снимки бесед или экземпляров, которые уже лежат у людей.

## 4. Гейт среза UI

Гейт — `check` проекта, его запускает оркестратор (общий процесс). Что из UI в нём проверяет машина:

- слои фронта и границы пакетов — `arch:check` ([Слои фронта](./concepts/frontend-layers.md), правила UI-28…UI-34 — [каталог правил](./reference/rules.md)); полнота реестров — UI-06, там же;
- граф описания — правила `UI`, `CH`, `TG`, `PG` по входу графа оболочки; UI-06 и CH-01 граф не читает — какое правило чем проверяется, в [чеклисте правил](./guides/story-screen-notification-run.md#7-чеклист-правил);
- имена и место файлов — `NM-01` тестом проекта, не `arch:check` ([Проверка имён и места](./reference/naming-check.md#7-проверка));
- код экранов и примеры — тесты и снимки ([как тестировать](./guides/story-screen-notification-run.md#9-как-тестировать)).

Числа узлов и рёбер графа (`dmg-core graph`) автор UI приносит в отчёт; ревью — только правила с проверкой `review`.
