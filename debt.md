# Технический долг пакета `dmg-ui`

**Назначение:** осознанные отступления и открытое в пакете. Файл лежит в корне репо и не является документом потребителя: это реестр разработки пакета. Правило, ограничение которого задумано, долгом не считается — такие ограничения описаны в [каталоге правил](docs/reference/rules.md) и гайдах.

**Последний выданный ID:** DEBT-UI-41

Номер новой записи — следующий после «Последнего выданного», строка правится тем же коммитом; номера не переиспользуются, закрытая запись удаляется. Серия `DEBT-UI-<n>`: голый `DEBT-<n>` принадлежит `dmg-core`. Долг тестов (лишние и дублирующие тесты) ведётся тем же реестром, в названии — «лишний тест». Решения пакета — [decisions.md](docs/decisions.md).

```
### DEBT-UI-<n>: <краткое название>
- **Место:** `<файл или класс>` — <пояснение>
- **Суть:** <что не сделано и чем это грозит>
- **Погашает:** <пакет канала или срез>   ← или **Триггер:** <условие>
```

У долга пакета почти нет кодовых маркеров, поэтому, в отличие от `dmg-core`, записи не привязаны к признакам в коде и автоматически не сверяются: проверяется только нумерация («Последний выданный ID» равен максимуму).

### DEBT-UI-1: нет правила графа «схемы входа, выхода и данных JSON-представимы»
- **Место:** `packages/core/src/runtime/json-boundary.test.ts`, `packages/web-ui/src/wire/page-wire.ts` — JSON-представимость проверяют только тест круга исполнителя через JSON-порты и схема сообщений провода страничного канала.
- **Суть:** схема, значения которой не проходят через JSON (`v.date()`, `Map`), не ловится правилом графа. `toJsonSchema` на такой схеме бросает при сборке графа исключением, а не нарушением правила.
- **Триггер:** первый канал, строящий провод вне `packages/web-ui`.

### DEBT-UI-2: `InputRejection.issues[].text` (`FieldIssue.text`) несёт сообщение valibot с введённым значением
- **Место:** `packages/core/src/schema/schema-check.ts` (`text: issue.message`), `packages/core/src/screen/action-input.ts` (`checkFields`) — замечания по полям входа действия.
- **Суть:** текст замечания берётся из `issue.message` valibot, а сообщения valibot по умолчанию повторяют полученное значение. Канал, показывающий `rejected.issues` или кладущий их в лог, выводит введённое значение. Строки полей отказа UC из `ErrorText` человеку не показываются (см. D-UI-20).
- **Погашает:** DEBT-3 пакета `dmg-core` (нейтральные тексты проблем валидации). Запись — ссылка: после правки платформы `text` перестанет нести значение, отдельной правки в `dmg-ui` не нужно.

### DEBT-UI-4: UI-18 для `from: 'query'` не сверяет ключи `input` и `fields`
- **Место:** `packages/core/src/graph/rules/recipient-fields.rule.ts` — класс `RecipientFieldsRule`.
- **Суть:** для получателей из query UC правило проверяет тип UC, `system` в его `callers` и поля payload, но не сверяет ключи `input` со схемой входа UC и `fields` с выходом UC. Опечатка в ключе обнаружится только при доставке.
- **Триггер:** первый query-получатель с расхождением.

### DEBT-UI-5: `ModuleSpecifiers` принимает комментарий с `from` за импорт
- **Место:** `checks/module-specifiers.ts` — регулярное выражение `PATTERN`.
- **Суть:** спецификаторы ищутся регулярным выражением без разбора кода, поэтому строка комментария вида `from 'x'` считается импортом и может дать ложное нарушение в `PackageDirections` и `CoreImportScanner`.
- **Триггер:** ложное срабатывание проверки.

### DEBT-UI-12: два набора UI в одном графе не поддержаны
- **Место:** `packages/core/src/graph/ui-graph-provider.ts` — класс `UiGraphProvider` с именем `dmg-ui`.
- **Суть:** имя поставщика уникально, второй набор UI в том же приложении дал бы `duplicate-provider`. Один поставщик обслуживает один набор и его приложения UI.
- **Триггер:** второй набор UI в приложении.

### DEBT-UI-13: `task-lines.ts` дублируется в двух привязках примера
- **Место:** `packages/chat-ui/testing/example/task-lines.ts`, `packages/web-ui/testing/example/task-lines.ts` — класс `TaskLines`.
- **Суть:** строки задач в теле реплики и в теле страницы строятся одной и той же логикой; общий помощник не вынесен, потому что привязки примера к каналам друг друга не знают: они в разных пакетах, а соседа импортируют только по имени входа (`PackageDirections`, `CoreImportScanner`).
- **Погашает:** вынос помощника во вход, доступный обеим привязкам (с разрешением этого входа в зонах привязок в `CoreImportScanner`).

### DEBT-UI-14: лишний тест (TST-08) в опоре на `dmg-core`
- **Место:** `packages/core/testing/dmg-core-example.test.ts:82-102` — проверки `visible` у шести UC модуля todo и `getTaskAssignee`.
- **Суть:** то же самое проверяет тест графа учебного приложения в `dmg-core` (`app-graph.test.ts`). Тест оставлен как опора на внешний пакет: он падает, если в среде окажется версия платформы без нужного признака `visible`.
- **Триггер:** следующая чистка тестов.

### DEBT-UI-18: действие может исполниться дважды
- **Место:** `packages/chat-ui/src/conversation/conversations.ts` (`Conversations`) — снимок пишется после сигнала; `packages/chat-ui/src/conversation/seen-ids.ts` — отсев повтора по id из снимка.
- **Суть:** id сигнала попадает в отсев снимка только после записи. Процесс упал между исполнением UC и записью снимка либо запись сорвалась (сбой `save`, в том числе при выгрузке) — мессенджер повторит сигнал после перезапуска, и беседа исполнит действие ещё раз: `requestId` следа новый на каждый сигнал, отсев повтора запроса платформой его не узнаёт.
- **Погашает:** правка `chat-ui` — `requestId` следа выводится из id сигнала (с именем мессенджера и приложения), и повтор запроса отсеивает платформа. Id для этого у мессенджера есть (у Telegram — `update_id`), но нужны правка контракта `requestIds` беседы (сейчас id запроса строится без сигнала) и доказательство «один сигнал — не больше одной команды» по всем путям беседы: иначе вторая команда того же сигнала получит отказ «запрос уже принят». Отсев платформы должен переживать перезапуск.
- **Триггер:** подключение мессенджера к проекту или первый замеченный дубль действия.

### DEBT-UI-19: нагрузка узла бесед без пределов
- **Место:** `packages/chat-ui/src/conversation/peer-queues.ts` (`PeerQueues`), `packages/chat-ui/src/conversation/conversations.ts` (`receive`, `unload`); те же очереди у сообщества — `packages/chat-ui/src/community/community-signals.ts` (очередь на handle), `packages/chat-ui/src/community/community-reactions.ts` (очередь на ключ сообщества).
- **Суть:** очередь собеседника не ограничена ни глубиной, ни частотой: поток сигналов одного собеседника копит задачи в памяти; у сообщества так же копятся сигналы одной группы и операции реакций одного сообщества. Выгрузка давней беседы ждётся внутри `receive` постороннего собеседника: зависший UC выгружаемой беседы держит чужое обещание, а два одновременных `unload` выгружают на одну беседу больше.
- **Погашает:** общая часть мессенджеров (`chat-ui`) — предел очереди собеседника или выгрузка в фоне: очередь у всех мессенджеров одна, у Telegram она та же, пакет мессенджера её не заменяет.

### DEBT-UI-21: доставка уведомления не возвращает итога
- **Место:** `packages/core/src/server/ui-notifier.ts` — запись наблюдателя `notified` после `deliver`.
- **Суть:** `NotificationDelivery.deliver` не возвращает итога, а наблюдатель пишет `notified` при любом возврате без броска: недошедшее уведомление (закрытое окно мессенджера, `warn` узла бесед без броска) в наблюдателе числится доставленным.
- **Триггер:** потребителю нужна точная статистика доставки.
- **Погашает:** правка контракта `NotificationDelivery` отдельным решением.

### DEBT-UI-22: ссылки уведомлений и экрана делят одну таблицу
- **Место:** `packages/chat-ui/src/conversation/ref-table.ts`, `packages/chat-ui/src/conversation/conversation-notices.ts`.
- **Суть:** ссылки уведомлений и экрана лежат в одной таблице на 256 записей: поток дошедших уведомлений вытесняет ссылки открытого экрана, нажатие на старую кнопку даёт «Такого варианта нет.». Варианты уведомления, отрезанные стражем лимита, остаются записями таблицы.
- **Триггер:** проект с частыми уведомлениями.
- **Погашает:** отдельная таблица ссылок уведомлений или доля уведомлений в общей.

### DEBT-UI-23: сборка графа с правилом лимитов — асинхронная
- **Место:** `packages/chat-ui/src/graph/chat-examples.ts` (`ChatExamples.collect`), `packages/chat-ui/testing/example/example-dialog.arch.ts` — примеры собираются `await` на верхнем уровне модуля.
- **Суть:** правило CH-01 требует видов примеров заранее, а вид экрана — `Promise`: сборка `ArchApp` с `ChatGraphProvider` получает асинхронный шаг, модуль сборки грузит код экранов при импорте. Последствия top-level `await` в `example-dialog.arch.ts`: если сбор примеров отклонён, не грузится весь вход `dmg-ui/chat-ui/testing`, в том числе для тех, кому нужен только подставной мессенджер; `require()` этого входа невозможен; цикл импорта через модули загрузчиков кода дал бы зависание загрузки.
- **Триггер:** потребитель собирает `ArchApp` синхронно.
- **Погашает:** синхронная предзагрузка `CodeLoaders` в ядре.

### DEBT-UI-24: отсев сообщества — в памяти
- **Место:** `packages/chat-ui/src/community/community-signals.ts` (`CommunitySignals`), `packages/chat-ui/src/community/community-reactions.ts` (`CommunityReactions`) — `SeenIds` по ключу сигнала (вид, handle, участник, id) и по ключу исполненной операции.
- **Суть:** отсев повторов сигналов и реакций живёт в памяти процесса: после перезапуска повтор сигнала снова вызовет UC, повтор события — снова операцию. Отсев запроса платформой для вызывающего `system` не действует (D-56 `dmg-core`); пока на повтор отвечает идемпотентность UC домена. Для реакции это граница доступа: query UC сверяет текущее состояние — повтор устаревшего события (человек ушёл и вернулся) иначе исключил бы вернувшегося.
- **Триггер:** мессенджер или outbox с повторной доставкой после перезапуска.
- **Погашает:** порт хранилища отсева сообщества.

### DEBT-UI-25: операция `inviteLink` не исполняется
- **Место:** `packages/chat-ui/src/community/communities.ts` (`Communities`) — сборка бросает «не реализовано» на реакцию с `inviteLink`.
- **Суть:** операция «выдать ссылку-приглашение» объявлена (тип, возможности мессенджера, узел графа), но ссылке некуда идти: доставка человеку (через беседу или `notify`) не спроектирована. Из четырёх операций сообщества работают три. `arch:check` реакцию с `inviteLink` пропускает (CH-03 сверяет только возможности) — падает старт исполнителя.
- **Погашает:** веха школы — решение вместе с сообщением о зачислении.

### DEBT-UI-26: отказ 429 Bot API без повтора
- **Место:** `packages/tg-bot/src/bot-api/bot-api-failure.ts` (`BotApiFailure`) — 429 переводится в `unavailable`; `packages/tg-bot/src/messenger/telegram-messenger.ts` (`TelegramMessenger`) — вызов порта один.
- **Суть:** ответ 429 (слишком много запросов) с `parameters.retry_after` даёт недоставку без повтора по `retry_after`: показ теряется, место беседы остаётся прежним, и только следующий показ его поправит. Повтор внутри вызова держал бы очередь собеседника на время ожидания.
- **Триггер:** потери показа под нагрузкой.
- **Погашает:** очередь отправки Telegram с ожиданием по `retry_after`.

### DEBT-UI-27: группа стала супергруппой без перепривязки
- **Место:** `packages/tg-bot/src/community/telegram-community.ts` (`TelegramCommunity`) — отказ Bot API с `parameters.migrate_to_chat_id` даёт `rejected` и запись «группа перенесена в супергруппу» без id.
- **Суть:** когда администратор включает в группе тему или публичную ссылку, Telegram превращает её в супергруппу с новым id; приложение знает группу по старому, поэтому исключение и принятие заявки не проходят, а связка «поток ↔ группа» остаётся прежней. Новый id пакет дальше факта не читает и проекту не отдаёт.
- **Триггер:** первая такая группа школы или веха школы.
- **Погашает:** порт проекта `migrated` и перепривязка `keys`/`handles` на связке поток ↔ группа (handle со знаком).

### DEBT-UI-28: заявку на вступление нельзя отклонить

- **Суть:** домен решил не принимать человека, а заявка так и висит у администраторов группы: ни пакет, ни приложение её не закрывают.
- **Триггер:** модель заявки на вехе школы.
- **Погашает:** операция `decline` в `chat-ui` и метод порта `declineChatJoinRequest` в `tg-bot`.

### DEBT-UI-29: превью Telegram перехватывает `ViewMessage`
- **Место:** `packages/tg-bot/testing/example/example-telegram-preview.ts` (`ExampleTelegramPreview.message`) — вид превращается в `Message` перехватом вывода на пути `DialogRenderer`, а не публичным показом.
- **Суть:** превью не повторяет беседу целиком (гайд «Telegram» это документирует): нет шапки заместителя, раскладки «Ещё» и стража `MessageFit`, берётся только последнее сообщение, ссылки вариантов — `1..n`.

### DEBT-UI-30: `warn` приёма вызова UC в ядре без предела на соединение
- **Место:** `packages/core/src/server/server-calls.ts` (`ServerCalls`) — `warn` «command UC по событию не исполняется» и `warn` отказа схемы вызова (`invalid`) пишутся на каждый вызов.
- **Суть:** страничный канал пишет `warn` раз на соединение на вид (мусор, предел вызовов, отказ подписки), а вызов, дошедший до ядра, — нет: клиент, шлющий по соединению тысячу `call` command UC с `eventId`, даёт тысячу записей лога. Пределы `CALL_LIMIT` и длины строки объём ограничивают, но не число записей.
- **Погашает:** перенос приёма вызова в `dmg-core` (D-UI-73) — `warn` приёма раз на сессию на вид.

### DEBT-UI-31: набор символов идентификаторов клиента не ограничен
- **Место:** `packages/web-ui/src/wire/page-messages.ts` (`PageId`), `packages/core/src/server/client-input.ts` (`ClientId`) — `requestId`, `eventId`, `id` вызова и подписки: 1–256 символов любого набора.
- **Суть:** ограничена только длина. Идентификатор клиента, который `dmg-core` вставляет в текст записи лога (повтор запроса по `requestId`), при текстовом логгере подделывает строки лога: перевод строки и управляющие символы проходят схему.
- **Погашает:** перенос приёма вызова в `dmg-core` (D-UI-73) — схема идентификаторов с ограниченным набором символов; идентификатор в лог — полем записи, а не текстом.

### DEBT-UI-32: обрыв во время вызова UC записан как дефект кода
- **Место:** `packages/core/src/runtime/action-run.ts` и загрузка экрана — отказ порта UC даёт запись `defect` и отказ `SERVER_INTERNAL`; `packages/web-ui/src/client/wire-ports.ts` (`WirePorts`) — отказ ожидающих вызовов на обрыве.
- **Суть:** в наблюдателе обрыв сети неотличим от дефекта кода: статистика `defect` вкладки растёт от каждого обрыва во время вызова. Человеку канал показывает свою заметку (D-UI-74), но записи наблюдателя прежние.
- **Погашает:** ядро — отказ порта UC «транспорт недоступен» отдельным видом исхода и записи.
- **Триггер:** статистика наблюдателя в бою.

### DEBT-UI-33: тихий обрыв не замечается
- **Место:** `packages/web-ui/src/client/page-socket-end.ts` (`PageSocketEnd`), провод страничного канала — пульса нет.
- **Суть:** сеть пропала без закрытия TCP — сокет браузера узнаёт об этом поздно; до того вкладка показывает данные без пометки «нет связи», а действия уходят в сокет без ответа; показ ожидаемого итога висит до ответа (D-UI-84).
- **Погашает:** пульс провода — новое сообщение и срок молчания по `PageClock`.
- **Триггер:** до выкатки страничного канала людям.

### DEBT-UI-34: схема параметров экрана с `transform` не проверяется без примеров
- **Место:** `packages/web-ui/src/url/page-urls.ts` (страж на примерах), `packages/core/src/address/address-codec.ts` (`decode`).
- **Суть:** JSON Schema не отличает `transform` от входного типа, правило графа его не видит; сборка проверяет круг «адрес → URL → адрес» только на примерах экрана. Неидемпотентный `transform` ломает восстановление адреса из снимка в любом канале: `decode` разбирает схемой экрана уже выход схемы (длина строки — отказ повторного разбора, `text + '!'` — значение меняется).
- **Погашает:** правило ядра «разбор выхода `params` даёт то же значение на примерах» или запрет `transform` в `params`.
- **Триггер:** первый экран с `transform` в `params`.

### DEBT-UI-35: помощник проб `solo` продублирован в двух тестах
- **Место:** `packages/web-ui/src/url/page-urls.test.ts`, `packages/web-ui/src/graph/page-url-rules.test.ts` — набор `soloUi` с одним проверяемым экраном.
- **Суть:** копии различаются формой: одна отдаёт экран и приложение, вторая — набор, сцену и несколько приложений; общий помощник в `packages/web-ui/testing/` потребует правки сигнатур в `page-urls.test.ts`.
- **Погашает:** один помощник в `testing/` (без экспорта из входа), оба теста его импортируют.
- **Триггер:** третий потребитель набора.

### DEBT-UI-36: вид поля входа — только строки
- **Место:** `packages/web-ui/src/view/page-form-model.ts`, `packages/web-ui/src/client/page-forms.ts` — `ActionField` ядра не несёт вида поля (число, булево, дата), поэтому все поля формы страницы — строки.

- **Погашает:** расширение `ActionField` в ядре (вид поля) отдельной записью `D-UI-N`; затрагивает мессенджеры и их снимки.
- **Триггер:** первый экран школы с нестроковым полем входа.

### DEBT-UI-37: ядро спрашивает подтверждение раньше проверки входа
- **Место:** `packages/core/src/runtime/action-run.ts` — порядок: исход `confirm`, затем `checkInput`.

- **Погашает:** правка порядка в ядре (сначала вход, затем подтверждение) с проверкой сцен мессенджеров и страницы.
- **Триггер:** первая форма школы с подтверждением и обязательным полем.

### DEBT-UI-40: два пути восстановления вкладки
- **Место:** `packages/web-ui/src/client/page-client.ts` — `resume` (восстановление из снимка) рядом с переходом по записи истории (`boot`, «Назад», D-UI-81).
